# 模板设计决策

> 本文件记录 ai-dev-template 自身的设计取舍与理由,给模板维护者与 AI 参考 —— 防止未来「优化」时无意推翻深思熟虑的决定。
> 随模板分发,初始化后**保留**(AI 读它可学到体系的取舍逻辑);目标项目自己的设计决策走 `docs/adr/`,不放这里。
> 修改本文件视为对模板的重大变更,须与模板版本号一同管理(见根 README 模板版本)。

## 1. 架构取舍

| 决策 | 理由 | 未采用的备选 |
|---|---|---|
| spec 与 tasks 拆为两份,同前缀配对 | 文档生命周期匹配读者:spec 是稳定契约(评审用,Active 后少动),tasks 是动态执行(勾选、交付记录回填) | 单一大「施工计划」文档:稳定契约与动态执行混在一份,修订时互相污染 |
| 单一状态注册表(docs/README.md) | 单一更新义务,查询一次到位 | 每目录一个 README 索引:索引分散必然漂移,维护义务随目录数翻倍 |
| tech/ 聚合高频技术事实 | AI 改代码的路由一次到位(tech-stack + architecture + concepts) | 按知识类型分散到各目录:检索路径变长 |
| AGENTS.md 单入口,150 行硬上限 | 上下文经济:每次会话都读它;详细规范按需加载,路由表指路 | 大而全根配置;或每工具一份私有配置(CLAUDE.md / .cursor/rules):维护与漂移成本 |
| research/ 只读不回改 | 调研是结论快照,回改破坏引用它的 spec 的证据链 | 活文档式调研:无法追溯当时结论 |
| STATUS.md 承载会话交接 | 任何时刻中断可恢复;工作日志只追加,是「上次停哪」的唯一依据 | 拆 STATUS / WORKLOG / HANDOFF 多件套:职责重叠,多处维护 |
| archive/ 不建初始目录 | 空目录 git 存不住;新项目无物可归档;规则(按需建)已够 | 初始建 .gitkeep 占位:噪音 |

## 2. 命名修正

| 决策 | 理由 |
|---|---|
| `briefs/`(初版 product/) | 目录名 = 内容类型(specs↔spec、rfcs↔RFC);product 与 `*.brief.md` 脱节,找回文件多一步间接 |
| `conventions/`(初版 guides/) | 内容全是 MUST 级规则;「指南」暗示可看可不看,弱化约束力 |
| `adr/` 不改 `decisions/` | 引用格式 `ADR-NNNN` 已与目录名对齐,改名收益仅为语义自解释 |
| `briefs/` 保留 `.brief` 类型后缀(rfcs/adr/design 不加) | brief 常与其 spec 同 slug 而编号独立(各流独立取号),后缀跨目录标记类型避免同名歧义;单类型目录中后缀与目录名信息重复故省 |

## 3. 机制设计

| 决策 | 理由 |
|---|---|
| 多任务 PR 用 merge commit,小改用 squash | 交付记录回填的 commit hash 依赖任务粒度,squash 压扁使回填失效;与「已推送不 rebase/amend」配套 |
| 再变更永远新建 spec,不改旧文 | 旧 spec 是当时的验收契约与审计记录;完全取代 → Superseded 互链,部分修改 → 旧 spec 文件头注记、正文不动 |
| spec:tasks 恒 1:1,大功能 Phase 分组 | 配对检索与 DoR 核对依赖 1:1;拆多份 tasks 破坏机制;Phase 组收口时系统可运行 |
| UI 设计三路径 | 轻 → spec「接口设计」内嵌;重 → 独立设计稿(design/)且定稿先于 spec Active;设计与开发同会话 → tasks 的 P0;唯一反模式 = 拆第二份 tasks |
| 设计说明是唯一入口,资产同编号归档 | 未被引用的资产 = 不存在,防目录变垃圾场;文本资产进 git、二进制外托管;原型与生产分离(生产 token 落代码目录) |
| 多文件调研 = 平铺主文档 + 同 slug 证据目录;调研清单全量登记(MUST) | 调研身份与链接面不变(入站链接零迁移),「不编号/主题命名/只读」三规则零改动;证据与主文档在目录列表相邻;清单表若只强制多文件会半登记、不可信,检索者仍需回落逐文件确认 —— 索引的可信度取决于完整性,故单文件同样 MUST 登记 | 未采用:`<slug>/index.md`(主文档身份从文件变目录,再调研规则与入站链接全要改);`research/assets/<slug>/`(research 无编号,assets 层无检索收益);证据只记外链(R9 证据链依赖外部托管存续);单文件 MAY 登记(半登记索引不可信) |
| 再变更判断口诀:改行为 → 新编号;改文档 → 修订 | 修订仅用于修正文档自身错误;新 spec 现状盘点引用旧 spec 形成行为链 |
| 一句话安装 / 初始化提示词用完整 URL | 目标项目的 AI 会话无法解析模板的本地相对路径;URL 让 AI 直接 fetch README |
| 安装分「新建 / 并入」两场景 | degit 建新仓与复制并入现有仓的命令完全不同;并入需冲突表(README 不覆盖、.gitignore 不自动并入) |
| 模板治理隔离:meta/ 放治理档案 + manifest.txt 白名单校验 | 修改规范 = 重大变更,审议档案须留档;但 `docs/rfcs/` 属于分发面,模板自己的 RFC 会随 degit 进入所有下游项目且清理规则(按编号文件推断归属)破坏安装幂等。meta/ 给出物理边界(场景一初始化时与 install.md 一同删除,场景二按清单从不复制),manifest.txt + `verify-docs.js --template` 把「治理文件放错位置」从静默泄漏变为校验失败;清单维护义务仅在分发面变化时发生 | 未采用:治理 RFC 直接进 docs/rfcs/(污染下游且清理不幂等);仅 manifest 无 meta/(degit 无子集拉取,反向删除逻辑进安装流程,多一步出错空间且漂移无感知);dist/ 发布目录(纯文本模板无构建步骤,复制式 dist 必漂移,degit 不支持子目录) |
| tech/ 活文档可增补(如 testing.md),增补项在 tech-stack.md「项目惯用法」声明;verify-docs --strict 活文档清单动态收集 | 规范列举半开放(无 MUST NOT)与校验硬编码三件套全封闭不一致,下游增补即成治理盲区(占位残留不被 CI 拦截);声明义务与代码目录条款(structure.md 第 1 节)同构,`ls docs/tech/` 与 tech-stack.md 互为对照 | 未采用:三件套封闭(测试策略等异粒度主题两难:违规放置或另建目录碎片化);动态清单延伸覆盖自建目录(自建目录自治,登记义务由项目 README 自建清单承担) |
| 章节引用按对象三分(规范活文档「第 N 节」/ 流水产物标题文字式 / 文件内省文件名);代码关键引用双形式 SHOULD;存量体例豁免登记 + 编号存量尾插不重排 | 流水产物无节号,原「文件名 第 N 节」对之永远无根据,真空被下游自行发明填满且写错(下游豁免声明覆盖面误写实例);双形式(文字 `:行号` + 目标 `#L` 锚)同时满足 grep 惯例、人点击、机器剥锚校验;编号重排两难(重排断锚点、尾插脱序),条目级 FR/ER(append-only)才是流水产物的稳定锚 | 未采用:全文档强制编号(重排两难 + 维护税,下游尾插约定即实证);§N 简写(两套等价写法并存,脱语境指代不明);锚点链接(中文 slug 渲染器不一、剥锚后不校验,静默死链);@path 前缀(IDE 会话语法,markdown 无语义,静态文档对 AI 与人均零增益) |
| research 证据目录结构语义豁免:verify-docs 死链与占位检查跳过 research/ 下同 slug 证据目录(目录 X 与主文档 X.md 并存即认定) | 证据是第三方引用原文,相对链接以原作者仓库为根,检查必误报(下游实测 9 个);判据复用 structure.md 5.2 既有形态,零配置零标记,脚本保持模板原版,下游升级 = 整文件替换;主文档出站链接与登记义务(检查 6)照常 —— 豁免不等于失踪 | 未采用:声明式忽略清单(配置面是第二份会漂移的声明,当前无真实需求);文件内标记(违反 5.2 只读,加标记即改写证据);下游各自硬编码豁免(分发面分叉 + 项目路径进通用工具 + 语义无档) |
| 流水编号各流独立取号,spec 编号不沿用 brief/RFC;跨流关联以注册表「来源」列 + 文件头「来源」字段为权威,slug SHOULD 一致;spec → tasks → design 保留同号链 | brief 与 spec 独立开始独立推进,沿用目标号被 RFC 来源/自发/多 spec 占据是常态,回落使编号双语义(同号有时同线程有时无关)且规则示例呈理想态;编号回归流内序号单一语义后取号零判断;spec→tasks/design 恒 1:1 无占用,保留同号检索便利零成本 | 未采用:沿用 + 撞号回落条款(每次取号查占用的判断负担,双语义认知税永久);复合编号 0003.1(破坏 4 位零填充与命名检查);design 一并解耦(1:1 无占用,解耦无收益) |
| git 安全动作纪律:提交暂存(精确路径 add、暂存区自查)+ push / 合并 / 销毁性操作须用户当次授权;授权粒度进可调参数 | 补齐「动作层」空档:AI 习惯 `git add -A` 在多会话并行时夹带他会话改动;双检制没有「AI 不自行 merge」的动作兜底形同虚设;`reset --hard` 等销毁未提交工作是 AI 会话第一数据事故来源 —— 授权权在人,授权不跨会话延续 | 未采用:按分支名分级授权(main / dev,分支名是实例配置非模板内容,dev 与 trunk-based 冲突);依赖工具层权限拦截(跨工具不一、allowlist 可绕过,「先列出丢弃内容再确认」是权限弹窗给不了的行为规范);只做 CI 门禁与分支保护(拦 merge 拦不了本地销毁操作) |
| Schema 演进十条纪律入 dev-standards(演进只走迁移、只增不改、版本名不复用、命名保序、幂等与兜底、兼容存量数据、失败不静默、多目标一致、测试同源、快照与增量分离);机制细节由 tech-stack.md「项目惯用法」声明 | 版本名复用丢变更、字典序反序、测试与生产 schema 脱节是项目无关的通用事故形态,分级信号只答「走什么流程」不答「迁移怎么写」;模板锁「防静默丢变更」下限,机制能力差异归项目声明 —— 与 dev-standards / tech-stack 既有分工一致;落点在「施工」路由必读文件,不新增规范文件 | 未采用:独立 conventions 文档(条款量级不足以成文,且脱离施工必读路径);只下放 tech-stack 声明(无下限约束,分层倒置);维持现状(事故形态无防线,违背「上下文全部经文档交接」定位) |
| 设计稿标注纪律与实现回标(视觉值落到 token / px / 类名可判定粒度;实现偏离两级处理:微调记变更记录,实质偏离就近加「实现说明」引用块且不删原稿) | 设计稿是「FR 依赖视觉细节」类 spec 转 Active 的前置,前置物自身须与 FR 同等可判定;spec 侧有「部分行为被 SPEC-NNNN 修改」注记机制而设计稿无对应物,定稿即终点使设计文档随实现漂移 —— 回标使设计文档随实现演进;两级处理匹配模板轻量定位,微调不逐节标注 | 未采用:义务全上收 workflow.md(文档结构义务归模板自身,表单模板自带指导语是既有先例);独立设计状态活文档(第二份要维护的文档,同 reviews/ 不采纳理由);design-template 加 Implemented 状态机(检索入口归 spec 链接,状态机归 spec) |
| Phase 拆分判据(跨层必拆、单 Phase 量级线、外部卡点独立成期写降级路径;阈值进可调参数)与测试基线数(开工实测 passed 基数,交付记录逐阶段对照,低于基线须说明) | 「任务较多或跨层」无可判定线,跨层塞单 Phase 的半破状态只能事后追责;交付记录只记绝对通过数,跨会话长工程测试数静默减少无环节可发现 —— 基线是阶段锚点而非逐任务强制;「低于基线须说明」而非绝对禁止,避免「养死测试保数字」的反向激励 | 未采用:判据只进 tasks-template 指导语(注释是填写指导非纪律来源,可被实例化者删改);机器校验测试数不回退(文档自检工具不读项目测试框架输出,跨语言计数无统一入口);基线写入 tasks 字段表(字段表属立项会话,基线属施工会话实测,混淆职责) |
| 施工执行协议增补(续作定位读 tasks 勾选与最新交付记录;未覆盖细节先定案、回填 tasks、再施工;清理义务扩至测试数据) | 三个缺口均在会话边界:中断恢复靠猜、未覆盖细节先斩后奏是「代码先走文档后补」的漏网变体、测试数据残留无条款;定案不打断执行 —— 知情走档痕(tasks 回填)与人工评审,实时知会让用户确认不可判定的写法选择,走私由实质偏离通道与开工分级声明兜底 | 未采用:spec 级进度写入 STATUS.md(与 tasks 交付记录双写必然漂移,违反单一更新义务);未覆盖细节一律停问(重大歧义与实现细节不分级,碎片化打断执行流) |
| 错误契约集中表(对外错误路径 ≥ 3 条触发,场景 / HTTP / 错误码 / 附加字段唯一格式口径)与 Phase 交付边界声明(每组「做到哪算完」,与任务验收点构成边界 / 证明两层) | 错误格式是接口契约中唯一没有集中可判定载体的部分,消费方与测试计划各自从 ER 文字提取必然漂移;Phase 有收口条件无完成边界,分组粒度裁量留给会话 —— 与 FR「可判对错」纪律对齐;两机制均条件触发,轻量 spec 自然豁免 | 未采用:独立错误契约模板(第二份要维护与互链的文档,同 reviews/ 不采纳理由);交付边界进 tasks 字段表(字段表是 spec 级全局字段,装不下 Phase 级组声明);错误契约对全部功能开发强制(来源项目粒度,与本模板轻量定位不符) |
| verify-docs 为 ESM 单文件(verify-docs.mjs,扩展名自证模块类型,`node:` 前缀导入,Node ≥ 20.11),不配任何 package.json 或构建步骤 | 分发面脚本嵌入任意宿主项目,模块类型不能依赖「最近 package.json」(宿主 `"type": "module"` 实测使自检加载失败,PR 自检硬依赖之);`.mjs` 跟随文件自身、布局无关,与 Node 生态方向一致(CJS 遗留化、require(esm) 收敛);零依赖原生 node 直接执行契约保留 | 未采用:docs/package.json `{"type":"commonjs"}`(下游实测有效,但免疫方向与生态相反、目录布局敏感、隐性约定,治标不治本);`.js` + ESM 语法不改名(模块类型仍由宿主决定,CJS 宿主即坏);TypeScript / 构建产物(破坏零依赖原生执行契约) |
| spec 拆分判据(多功能各自可独立验收 MUST 拆多 spec;不可独立验收留同 spec 按 Phase 分组;共享约束上浮 tech,集成场景立集成 spec) | 补 spec 层粒度判据空白(Phase 判据只管 tasks 内分组);1:N 形态(下游 plan)的拒绝出口 —— 拆 spec 不拆 tasks,恒 1:1、独立收口与完整性机器核对全保留 | 未采用:受控 1:N 功能级施工文档(见第 4 节);判据只进模板指导语(注释可被实例化者删改,同 Phase 判据落点理由);验收可分性设量化阈值(判断对象是契约性质非工作量,量级超线由 Phase 判据在 tasks 层兜底) |
| 自建活文档登记义务与门禁(README「自建活文档清单」每份 MUST 登记(与文件创建同一 commit);TF1 / DoD 第 4 条 / PR 自检枚举泛化「登记的自建活文档如有」;verify-docs 检查 8 双向校验(登记即合法,design/ 仅查顶层)、检查 9(--template)兜 meta/rfcs 注册表) | 决策树允许自建目录(deploy/design/plan)但五道关卡(DoD/TF1/3.6 merge/PR 自检/verify-docs)全盲,漂移机制必然(下游计划文档两连漏、靠人工盘点发现且补漏再漏;本仓 meta/rfcs 注册表漏登 RFC-0013);RFC-0002 预设「登记义务由项目 README 自建清单承担」由此兑现;勾选状态与交付的一致性属语义判断不机器强制,合入前核对由枚举泛化以人在场提醒承担 | 未采用:仅枚举泛化与义务条款(登记发生在目录自建、不经任何收尾任务,首因环节无兜底,MUST 无核对点承载);仅机器兜底(拦失踪不拦过期,下游病灶是过期);固定目录词汇封闭清单(重演枚举盲区、与 design 规则冲突、存量批量误报);计划职能并入 STATUS.md(当下快照与跨季度时间线粒度不匹配,deploy/design 不适用,收窄决策树逼出另建文件的地下行为) |

## 4. 明确不采纳(及原因)

| 不采纳 | 原因 |
|---|---|
| 活规格层(delta spec + 归档合并成当前行为真相源) | 合并 delta 是持续义务;中小项目 architecture + concepts + Superseded 已覆盖该需求;需要该层的项目适合直接用专门的 spec 框架 |
| reviews/ 评审目录 | 评审落在三载体:GitHub PR(评论持久化)+ PR 模板清单 + tasks 自检与交付记录;不产生第二份要维护的文档 |
| PRD 层 | PRD ≈ brief + spec 需求侧合集;拆开后各自生命周期与读者匹配,AI 单会话难维护持续演进的巨型文档 |
| 强制 TDD(先写测试、删码重写) | 不适合界面、脚手架类改动;体系是结果导向(行为有覆盖) |
| git worktree、subagent 派发 | 个人工具技巧 / 会话内部策略,不改变协作契约,不进模板 |
| 会议纪要目录 | 结论应沉淀进 brief / ADR,独立成档必漂移 |
| 用户文档 / API 文档目录 | 产品交付物,非开发文档 |
| issue 模板 | 体系是 brief 驱动,brief 即需求入口 |
| CI / 工作流配置模板 | 完成定义靠 PR 自检与评审约束;需要强制门禁的项目自建 CI,模板不绑定平台 |
| 示例实例(填好的 demo spec / brief) | 示例随规范演进过时,维护义务持续;模板 HTML 注释指导语已覆盖填写方法;用文档体系时看注册表示例行即可 |
| 中文文件名 | 跨工具检索、markdown 链接 URL 编码、与 kebab-case 规范冲突 |
| spec:tasks 1:N 关联(功能级施工文档,下游 plan 形态) | 拆 spec 以零机制改动获得其全部收益:功能级需求各自编号立 spec(恒 1:1),独立收口、并行无冲突、独立回滚;spec 级收口下 1:N 兑现不了按功能独立交付(母 spec 等最慢功能);FR 子集映射靠人工登记,完整性不可机器核对(1:1 天然全 FR);「功能可独立交付」恰证明契约可分,正解是拆 spec 而非拆 tasks(判据见 workflow.md 第 3.2 节) |
