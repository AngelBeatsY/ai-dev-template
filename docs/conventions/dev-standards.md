# 开发规范(语言无关)

本规范定义与语言、框架无关的代码质量要求。**只定「必须达到什么」**;「具体怎么做」由 [tech-stack.md](../tech/tech-stack.md) 的项目声明决定(linter 配置、命名惯例、框架惯用法)。流程与提交规范见 [workflow.md](workflow.md) 与 [git-workflow.md](git-workflow.md)。

## 1. 通用代码质量

- 命名表达意图:读到名字就知道它是什么、做什么;不用缩写(通用缩写如 `id`、`config` 除外)。
- 函数单一职责,长度以「一屏能完整读完」为度;超过时优先拆分,不追求具体行数指标。
- 注释解释 **why** 而非 what:代码已说明 what,注释补充背景、约束与取舍。没有信息量的注释删除。
- 不留死代码与被注释掉的代码;需要找回时用 git 历史。
- 相同逻辑出现第三次之前抽取;不为「将来可能用到」预留抽象(YAGNI)。
- 遵循项目既有风格;与 tech-stack.md 声明的惯例冲突时,以 tech-stack.md 为准并更新之。

## 2. 错误处理

- 不吞异常:禁止空 catch、禁止捕获后仅打日志继续(除非该场景明确设计为容错并注释原因)。
- 错误信息必须可操作:包含发生上下文(什么操作、什么输入)与下一步(哪里失败、怎么处理)。
- 边界取舍:内部边界 fail fast(尽早暴露编程错误),外部输入容错(校验后给出用户可理解的错误)。
- 错误分类传递:可预期的业务错误与不可预期的系统错误使用不同类型/通道,不混用字符串比较判断错误。

## 3. 日志与可观测性

- 级别语义固定:

| 级别 | 含义 |
|---|---|
| DEBUG | 排查细节,生产环境默认关闭 |
| INFO | 关键路径节点(任务开始/完成、状态迁移) |
| WARN | 可自动恢复的异常情况,需要关注 |
| ERROR | 需要人工介入的失败 |

- 不打敏感信息:密码、token、密钥、身份证件号、完整支付信息,任何级别都不打。
- 日志面向排障而非转储:一条日志说清一件事,包含足以定位的上下文(trace/request id),不倾倒整个对象。
- 日志消息为静态字符串 + 结构化字段,不把变量拼进消息文本(便于检索聚合)。

## 4. 调试纪律

修复缺陷与排查问题遵循系统化流程,**禁止随机试改**(反复修改直到测试碰巧变绿):

1. **稳定重现**:先构造最小可复现场景;无法稳定重现的,先解决重现问题。
2. **定位根因**:用最小改动验证假设(二分注释、临时断点或日志),定位到具体原因而不是「大概在这附近」;临时调试代码与临时数据验证后删除。
3. **修根因,不修症状**:修复产生问题的原因,而不是在下游加防护掩盖;确需修症状的场合(外部系统无法改)MUST 注释说明并记为已知边界。
4. **修复后验证(完成前验证)**:声称「已修复」MUST 附证明 —— 重跑原失败场景确认通过、全量测试通过、补一条修复前会失败的回归测试。没有验证的「应该好了」不算修复。

AI 协作特别约束:连续两次修复尝试仍失败时 MUST 停下来,向用户报告已验证的事实与未验证的猜测,而不是继续盲目尝试。

## 5. 测试策略

- 金字塔:大量单元测试,适量集成测试,少量端到端测试。
- 三类场景 MUST 覆盖:
  1. 公共接口的行为(对外契约)。
  2. 边界与错误路径(与 spec 的 ER-N 对应)。
  3. 回归 bug —— 修复前先写失败测试,再修复使其通过。
- 测试命名表达场景:`<被测对象>_<条件>_<预期结果>`,读测试名即可理解行为。
- 测试验证行为而非实现细节;重构不应导致测试修改。
- 测试之间相互独立,可任意顺序运行;不依赖执行顺序与共享可变状态。
- 覆盖率是参考不是目标;不为凑数写无断言的测试。
- 修复 bug 的 PR MUST 包含回归测试,否则不予合并。

## 6. 安全基线

- 外部输入(用户输入、API 请求、环境变量、文件内容)一律校验后才使用;校验发生在系统边界,不在深层逻辑中分散判断。
- 密钥与凭证只进环境变量或密钥管理服务;MUST NOT 出现在代码、配置文件、日志与文档中。
- 遵循最小权限:文件与目录权限、数据库账号、部署凭据按需授予。
- 谨慎处理来自外部的数据结构:反序列化输入限制类型与深度。
- 依赖漏洞告警响应:高危漏洞 7 天内评估,可利用的尽快修复。

## 7. 依赖管理

- 新增依赖前 MUST 自问:标准库或既有依赖能否满足?不能时才引入。
- 评估维度:维护活跃度(近半年有发布)、许可证兼容、传递依赖规模、替代成本。
- 锁文件 MUST 提交到仓库。
- 新增或升级**运行时**依赖属于重大级改动(触发 RFC,见 workflow.md 第 2.3 节);开发依赖为常规级。
- 不使用的依赖及时移除。

## 8. Schema 与数据演进

涉及持久化 schema(数据库表结构、索引等)的项目适用;无持久化 schema 的项目删除本节,并在 tech-stack.md「项目惯用法」中省略对应声明。迁移工具、目录与执行时机由 tech-stack.md「项目惯用法」声明。

- **演进只走迁移**:schema 变更 MUST 以版本化迁移文件承载;应急手工改库后 MUST 补迁移对齐,不留「库与迁移资产不一致」状态。迁移按稳定顺序执行一次并记录版本,已应用版本跳过。
- **只增不改**:已提交的迁移文件 MUST NOT 修改或重命名 —— 下游环境可能已应用旧文件,改动即漂移;修正 schema 一律新增迁移。
- **版本名不复用**:迁移版本标识(文件名)MUST NOT 复用,已删除的同样不复用 —— 版本记录按名跳过,同名新内容永不执行,静默丢变更。
- **命名保序**:执行序由文件名字典序决定时,命名 MUST 保证字典序 = 交付序。统一 `YYYY-MM-DD-NN_<语义>` 格式(SHOULD):NN 两位零填充(一位序号在同日第 10 个文件出现时,`-10` 会按字典序排到 `-1`、`-2` 之前),禁止带序号与无序号文件混排,日期写建档实际日期、禁止预写未来日期占位。
- **幂等与兜底**:迁移 SHOULD 幂等(重复执行无害,如 `IF NOT EXISTS`);无法幂等的操作(改名、删列、重建)MUST 依赖版本记录保证只执行一次,并在文件头注明。
- **兼容存量数据**:新增 `NOT NULL` 列 MUST 带 `DEFAULT` 或在同迁移内回填;删列删表前 MUST 确认无存活引用。
- **失败不静默**:迁移失败 MUST NOT 被跳过或忽略后继续对外服务 —— schema 不完整不对外;执行机制 SHOULD 做到单版本失败整体回滚、修复后可安全重试(实际行为在 tech-stack.md 声明)。
- **多目标一致**:同一变更覆盖多个部署目标(多数据库方言、多环境)时 MUST 逐目标落地,缺一即漂移;跨方言差异(幂等语法支持、默认值可用函数、partial index 支持)MUST 在 tech-stack.md 登记。
- **测试同源**:涉及 schema 的测试,其建表来源 MUST 与生产同源(同一基线 + 迁移,或与之对齐的 DDL),防止「测试全绿、生产缺列」。
- **快照与增量分离**:存在初始化快照(基线 SQL / seed)时,快照冻结为历史时点,MUST NOT 随每次变更改写 —— 全新环境走「快照 + 全量迁移」收敛到当前结构;快照唯一合法的更新通道是受控 squash(确认全部环境已应用相关迁移 → 并入快照 → 删除已并入的迁移文件)。

## 9. 重构

- 重构行为不变:有测试覆盖的前提下小步进行,每步可验证。
- 重构与功能改动 MUST NOT 混在同一个 PR。
- 提交前跑全量测试 + lint。

## 10. 完成定义(DoD)

一项开发任务「完成」MUST 同时满足以下全部条目(与 PR 模板「提交者自检」清单同源,本节为权威版本):

1. 新增/修改的行为有测试覆盖,且全量测试通过。
2. 关键链路已冒烟验证(端到端真实运行,结果记入交付记录)。
3. lint 通过。
4. 相关文档已同步:tech-stack.md(新增依赖/命令/惯例)、architecture.md(结构变化)、受影响的 spec,以及 docs/README.md「自建活文档清单」中受影响的条目(如有,见 [workflow.md](workflow.md) 6.3)。
5. `docs/README.md` 注册表已更新(如有状态变化)。
6. tasks 清单逐项勾选,交付记录已回填(如有)。
7. 不包含密钥、凭证、敏感信息。
8. 不包含与本任务无关的改动。
9. 兼容性影响已在 spec 或 PR 中说明。

## 11. 与技术栈声明的衔接

本规范的每一条是「必须达到的要求」;各项目在 `docs/tech/tech-stack.md` 的「项目惯用法」一节声明落地方式:

- 使用的 linter / formatter 及配置位置。
- 语言的错误处理惯例(异常、Result、错误码)。
- 日志库与调用方式。
- 测试框架与运行命令。
- 目录分层与命名惯例。

AI 在本仓库写代码时,实现层细节以 tech-stack.md 为准;两者冲突时报告冲突,不自行取舍。
