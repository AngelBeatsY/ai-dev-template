# 文档书写规范

本规范定义本仓库所有文档的语言、格式与语气约定。每种文档的章节骨架见对应 `*-template.md`,内容质量标准见 [workflow.md](workflow.md) 各阶段定义;文件命名规则见 [structure.md](structure.md) 第 4 节。修改本文件视为重大变更,须走 RFC 流程。

## 1. 语言

- 正文使用中文书写。
- 以下内容保留英文原文,不翻译:技术术语、代码、命令、文件名、目录名、状态值(如 `Accepted`)、专有名词。
- 中文与英文、数字之间加一个空格,例如:`使用 Git 管理版本`、`预计 3 人日`。
- 中文标点与英文标点不混用:正文用中文标点,代码与命令用英文标点。
- 术语以 [tech/concepts.md](../tech/concepts.md) 为准:**新术语先入表再使用**;同一概念全篇同一用词,不混用近义词。

符号细则:

- 强调与术语引用用「」;不使用斜体表强调(中文斜体排版效果差)。
- 破折号用「——」,省略号用「……」;不用单杠、波浪线代替。
- 列表统一用 `-` 引导。

## 2. Markdown 格式

- 每篇文档只有**一个 H1**(即文件标题),标题层级不跳级(H1 → H2 → H3)。
- 标题使用名词或名词短语,不加标点结尾。
- **章节编号**分两类:规范与活文档(conventions/、tech/)的 H2 从 `1` 连续编号(`## 1. 标题`),小节 `### 1.1`,插入新节时重排后续编号;表单类文档(从 `*-template.md` 实例化的流水产物)章节**不编号**,按模板骨架顺序。
- 并入已有项目时,成稿早于模板的存量文档可保留原体例,MUST 在 `docs/README.md` 注册表声明豁免范围与各自实际状态(保留编号 / 已适配 / 本就同构)。保留编号的存量流水产物后续新增章节一律尾插取下一号,不中间插入、不重排 —— 节号互引与锚点依赖编号稳定。
- 列表项不超过两行;超过两行说明该写成段落或小节。
- 成组出现的对比信息使用表格,不使用连续的平行列表。
- 代码块必须标注语言(``` ```bash ```、``` ```mermaid ``` 等);无法标注语言的仅限纯文本示意。
- 超过 200 行的文档,开头放置目录(链接到各 H2)。
- 文件保存为 UTF-8(无 BOM),换行符不作强制。

## 3. 语气与精确性

- 使用陈述句与可执行的指令句,不使用感叹号,不使用营销语气。
- 禁用模糊量词:`尽量`、`大概`、`适当`、`一些`、`比较好的`。要么给出可判定的条件,要么删除该句。
- 规范类语句使用 RFC 2119 语义,含义固定如下:

| 关键词 | 含义 |
|---|---|
| MUST / MUST NOT | 绝对要求,违反即为错误 |
| SHOULD / SHOULD NOT | 强烈建议,偏离须说明理由 |
| MAY | 真正可选 |

- 中文行文中等价表述:MUST 对应 `必须`,SHOULD 对应 `应当`,MAY 对应 `可以`;关键条款直接使用英文关键词以突出强度。

## 4. 链接与引用

- 文档间链接使用相对路径。章节引用按对象分三类:
  - 引用规范与活文档(章节有编号):「文件名 第 N 节 / 第 N.M 节」,如「workflow.md 第 3.2 节」;
  - 引用流水产物(章节不编号):「`SPEC-0002`『Marker 语法』节」标题文字式 —— 标题随落档不回改,即稳定锚;禁止对不编号文档写「第 N 节」;
  - 同一文件内部引用他节:省文件名,写「见第 N 节」(仅适用于带编号文档)。
- 章节引用统一用「第 N 节」文字,不使用 `§N` 符号简写:两套等价写法并存徒增认知成本,且 `§7` 脱离就近语境后指代不明。
- 引用工作流产物必须使用带编号的交叉引用格式:`BRIEF-0001`、`SPEC-0002`、`RFC-0003`、`ADR-0004`。
- 设计稿不设编号引用格式(不入注册表),引用用相对路径链接。
- 引用仓库内代码位置用 `文件路径:行号`(如 `src/app.ts:42`),跨多行用 `src/app.ts:42-58`;作为证据引用时 MUST 带行号。
- 作为评审依据的关键代码引用,SHOULD 用双形式:链接文字保持 `:行号` 惯例(可 grep、与 stack trace 一致、AI 可读),链接目标用 `#L` 锚(GitHub 可点击跳行),如 [verify-docs.mjs:103-104](../verify-docs.mjs#L103-L104);死链检测剥锚后仍校验文件存在性。一般引用维持纯文字即可,存量引用不要求改造。
- 禁止裸写`见某文档`、`见之前的设计`;必须给出编号或相对路径链接,保证可检索。

## 5. 统一用词

流程词汇全项目统一,不使用近义表述(防多会话、多作者用词漂移);项目领域术语另见 [tech/concepts.md](../tech/concepts.md)。

| 统一用词 | 含义 | 弃用的近义表述 |
|---|---|---|
| spec | 功能规格,含验收标准与接口设计 | 规格书、方案书、设计文档 |
| tasks | 任务拆解清单,与 spec 同前缀配对 | 任务书、施工计划、工作分解 |
| 交付记录 | 任务/阶段完成后回填的记录(hash、结果、交接要点) | 施工记录、进度日志 |
| 偏差 | 实现与 spec 的不一致 | 出入、不一致点 |
| 分级 | 小改/常规/重大的判定与声明 | 分类、定级、规模判定 |
| 门禁 | 测试与 lint 等自动化质量检查 | 质量检查、CI 检查 |
| 冒烟 | 关键链路端到端真实运行验证 | 手测、快速测试 |
| 收口 | 阶段的工作与账面结清到终态、不留中间态:Phase 收口(可运行关口)、收口复查(送审前)、状态收口四动作与回填(合并时)、工作区收口(会话结束) | 收尾、结项 |
| 现状盘点 | spec 中附证据的现状清单 | 背景调研、现状分析 |
| 验收标准 | 可判定的 FR 条目 | 需求点、功能点 |
| 立项 | brief(自发可免)→ spec → tasks 的产出过程 | 开题、启动、开工 |
| 就绪(DoR) | 施工会话开工前的核对清单 | 准入、开工条件 |

## 6. 占位约定

- 模板中待填内容统一使用前缀 `TODO(template):`,保证全局可搜索。
- 项目初始化完成的验收标准:全局搜索 `TODO(template):` 结果为零。
- 运行期临时待办使用 `TODO:` 前缀(与模板占位区分),并附负责人与上下文。

## 7. 图表

- 优先使用 Mermaid 内嵌代码块,随文档一起版本化。
- 每张图后面必须跟一段文字摘要,说明图的要点 —— 照顾纯文本环境阅读与 AI 解析。

## 8. 日期

- 一律使用 `YYYY-MM-DD` 格式,例如 `2026-08-20`。

## 9. 文档评审 checklist

发布或合入任何文档前逐项检查:

1. 目标读者明确,开篇能回答「这篇文档是给谁看的、解决什么问题」。
2. 无未解释的缩写(首次出现给出全称)。
3. 要求与验收标准可判定,不含模糊量词。
4. 无 `TODO(template):` 残留(模板本体除外)。
5. 所有相对链接有效,交叉引用带编号(`node docs/verify-docs.mjs` 自动检查)。
6. 只有一个 H1,标题未跳级,章节编号符合第 2 节规则。
7. 代码块标注了语言。
8. 图表配有文字摘要。
9. 流程用词符合第 5 节统一用词表。
10. 与既有文档无矛盾;如有覆盖关系,已注明取代对象。
11. 日期格式为 `YYYY-MM-DD`。
