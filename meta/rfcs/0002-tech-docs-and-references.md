## 摘要

首个下游项目的追溯期暴露三处规范缺口:① structure.md 对 `docs/tech/` 采用三件套封闭列举,而第 5 节决策树允许「持久的技术事实」进入 tech/,下游增补第四活文档(testing.md)时规范文本半开放、机器校验(verify-docs.js `--strict` 的 LIVE_DOCS 硬编码三件套)全封闭,两者不一致形成治理盲区;② writing-style.md 第 4 节的章节引用规则「文件名 第 N 节」只对带编号的规范/活文档可用,引用流水产物的章节、同一文件内部的章节互引均无规定;③ 代码位置引用 `path:42-58` 不可点击,而 GitHub 支持 `#L` 行锚,可低成本兼得。本提案修改 structure.md 一行、writing-style.md 两条并新增两条、verify-docs.js 一处,全部为新增或细化,不改既有条款语义。

## 背景与动机

**证据一(tech/ 活文档盲区,已发生)**:某下游项目增补 `docs/tech/testing.md`(测试策略:golden-file 回归、round-trip、保真度 manifest 等)。按决策树「持久的技术事实 → docs/tech/」归类方向正确,且已按 writing-style 第 2 节履行 H2 编号;但:

- structure.md 第 2 节 tech/ 行列举「tech-stack.md、architecture.md、concepts.md」,无 MUST NOT 措辞 —— 半开放;
- verify-docs.js 第 69 行 `LIVE_DOCS` 硬编码三件套 + STATUS,`--strict` 的 TODO 清零义务对增补活文档不设防 —— 全封闭。

规范与校验不一致意味着:下游增补活文档是否合规无判定依据,且占位残留不会被 CI 拦截。同类先例:structure.md 第 1 节已要求代码目录「MUST 在 tech-stack.md『项目惯用法』一节声明」,tech/ 增补活文档缺同构的声明义务。

**证据二(章节引用真空,已发生)**:writing-style 第 4 节规定跨文档引用统一写「文件名 第 N 节」,但节号只存在于规范与活文档(第 2 节连续编号);流水产物章节不编号,「SPEC-0006 第 3 节」这种引用永远无根据 —— 如何引用一份流水产物的某一章,规范无规定。文件内部互引同样无规定。下游代价已经显形:

- 某下游项目 README 注册表中的体例豁免声明把「spec 保留编号 / brief 成稿即同构 / ADR 已追溯适配」三种实际状态误写为「brief/spec/ADR 均保留编号章节体例」—— 引用与体例规则真空下,下游自行发明声明并写错,且 verify-docs 五项检查均不涉及,机器不拦;
- 下游存量 SPEC-0001 正文大量使用「见 §7」「见 §8」节号互引(threadId、cwd 字段定义依赖跳转),证明长 spec 的章节互引是真实刚需,规则真空会被下游自发行为填满。

**证据三(代码引用不可跳转)**:writing-style 第 4 节现行 `src/app.ts:42-58` 纯文字,信息完备但不可点击;GitHub 对 `#L42-L58` 行锚原生支持跳转与区间高亮,而 verify-docs 死链检测剥锚(`split('#')[0]`)后仍校验文件存在性 —— 双形式(链接文字用 `file:42-58`、链接目标用 `file#L42-L58`,完整形态见 1.3)可以同时满足 grep 惯例、人点击、机器校验,当前规范未提供这一选项。

## 目标

- 收口 tech/ 活文档的「规范半开放 vs 校验全封闭」不一致:列举改为「三件套必选 + 可增补」,增补须声明;LIVE_DOCS 动态化。
- 补齐章节引用规则的真空:明确「第 N 节」的适用范围,规定流水产物章节引用与文件内互引的写法。
- 为代码关键引用提供双形式 SHOULD(文字可 grep + 链接可点击)。
- 吸收下游追溯期经验,规定存量文档体例豁免的登记义务与编号存量的维护方式。

## 非目标

- 不改变「规范与活文档编号、流水产物不编号」的两分法(writing-style 第 2 节)。
- 不引入 `§N` 符号简写与 `@path` 引用语法。
- 不强制改造存量引用为链接形式。
- 不处理 specs/ 编号配对(spec 无 tasks)的检查缺口 —— 机器校验「防多不防缺」属 verify-docs 独立议题,暂不扩项。

## 提案详述

### 1.1 structure.md 第 2 节 tech/ 行(替换)

```
| `docs/tech/` | 技术事实活文档:tech-stack.md、architecture.md、concepts.md 三件套必选,可按项目需要增补同粒度活文档(如 testing.md),增补项 MUST 在 tech-stack.md「项目惯用法」一节声明 | 流程规范、工作流产物 |
```

与第 1 节「代码目录结构 MUST 在 tech-stack.md『项目惯用法』声明」同构:目录职责的扩张点集中在 tech-stack.md 声明,`ls docs/tech/` 与 tech-stack.md 互为对照。

### 1.2 writing-style.md 第 4 节章节引用条目(替换现行「跨文档引用章节统一写…」一条,扩为三条)

```
- 文档间链接使用相对路径。章节引用按对象分三类:
  - 引用规范与活文档(章节有编号):「文件名 第 N 节 / 第 N.M 节」,如「workflow.md 第 3.2 节」;
  - 引用流水产物(章节不编号):「`SPEC-0002`『Marker 语法』节」标题文字式 —— 标题随落档不回改,即稳定锚;禁止对不编号文档写「第 N 节」;
  - 同一文件内部引用他节:省文件名,写「见第 N 节」(仅适用于带编号文档)。
- 章节引用统一用「第 N 节」文字,不使用 `§N` 符号简写:两套等价写法并存徒增认知成本,且 `§7` 脱离就近语境后指代不明。
```

### 1.3 writing-style.md 第 4 节代码引用条目(在现行「引用仓库内代码位置…」条后追加)

```
- 作为评审依据的关键代码引用,SHOULD 用双形式:`[verify-docs.js:53-60](docs/verify-docs.js#L53-L60)` —— 链接文字保持 `:行号` 惯例(可 grep、与 stack trace 一致、AI 可读),链接目标用 `#L` 锚(GitHub 可点击跳行);死链检测剥锚后仍校验文件存在性。一般引用维持纯文字即可,存量引用不要求改造。
```

### 1.4 writing-style.md 第 2 节新增存量豁免条(置于「章节编号」两条之后)

```
- 并入已有项目时,成稿早于模板的存量文档可保留原体例,MUST 在 `docs/README.md` 注册表声明豁免范围与各自实际状态(保留编号 / 已适配 / 本就同构)。保留编号的存量流水产物后续新增章节一律尾插取下一号,不中间插入、不重排 —— 节号互引与锚点依赖编号稳定。
```

### 1.5 verify-docs.js:LIVE_DOCS 动态化

`LIVE_DOCS` 由硬编码数组改为运行时收集:`docs/STATUS.md` + `docs/tech/` 下全部非 `-template.md` 的 `.md` 文件。`--strict` 语义不变(活文档 TODO(template) 清零),覆盖面自动跟随 tech/ 增补。同步修改头部注释第 6 行措辞「四个活文档」→「STATUS.md 与 docs/tech/ 全部活文档」。第 81 行的 total 统计引用同一数组,自动跟随,无需单独改。

### 配套修改

- **meta/README.md**:RFC 注册表加行(随本 RFC 同一 commit)。
- **下游项目侧**(不受本 RFC 约束,引用为证):其 README 豁免声明的修正与「尾插不重排」约定由项目自行落实,1.4 条生效后与本模板条款对齐。

## 备选方案

| 维度 | 方案 A(本提案:可增补 + 声明义务 + 动态校验) | 方案 B:tech/ 维持三件套封闭 | 方案 C:全部文档强制章节编号 | 方案 D:章节引用一律锚点链接 |
|---|---|---|---|---|
| 成本 | structure 一行 + writing-style 四条 + 脚本一处 | 零 | 零文本改动,但全体下游付维护税 | 存量引用全量改造 |
| 风险 | 低:均为新增/细化 | 高:下游增补即违规或无处安放 | 高:编号重排两难 | 高:锚点失效不校验,静默死链 |
| 可逆性 | 高(删条即回滚) | — | 低 | 低 |

**方案 B(维持封闭)**:未入选。测试策略、部署拓扑等主题与「用什么技术」确不同粒度,决策树已经开放入口,封闭列举使下游两难(违规放置或另建目录碎片化)。

**方案 C(全文档强制编号)**:未入选。编号要求「连续有序」,插节要么重排(断锚点、断互引、diff 噪音)要么尾插(编号与阅读顺序脱节);流水产物「落档不回改」使重排根本不该发生,编号退化为装饰。流水产物已有更稳定的定位体系:条目级编号(FR-N / ER-N,append-only 永不重排)。已有下游保留编号的五份 spec 被迫追加「尾插不重排」约定,正是这笔维护税的实证。

**方案 D(锚点链接)**:未入选。中文标题锚点各渲染器 slug 规则不一;verify-docs 剥锚后锚点不校验;可点击性换来静默失效的链接。标题文字式纯文本可 grep,落档后标题即稳定。

**引入 `§N` 简写**:未入选,理由见 1.2 条款内文。**引入 `@path#L` 前缀**:未入选 —— `@` 是 IDE/AI 会话的 mention 语法,markdown 无语义渲染为字面文本;静态文档中的 `@` 不会触发任何自动加载,对 AI 与人均无增益,徒增第三套语法。

## 影响与风险

- **verify-docs.js 行为变化**:`--strict` 对 tech/ 增补活文档的 TODO 占位开始报错 —— 这是修复目的本身;模板仓库自身 tech/ 仅三件套,`--template` 模式不受影响。
- **存量文档**:四条 writing-style 条款均为新增或细化,不改既有「文件名 第 N 节」引用的合法性;1.3 为 SHOULD 且明确存量不改造,零迁移。
- **下游已增补 tech/ 活文档的项目**:需补 tech-stack.md「项目惯用法」声明,一行成本;--strict 新覆盖面在占位已清零的项目无感。
- **学习成本**:章节引用从一条变三条,按对象分类(规范活文档 / 流水产物 / 文件内),分类维度与既有「三类文件区分」(structure.md 第 3 节)一致,无新概念。

## 迁移与回滚计划

不适用(非破坏性变更):全部条款为新增或细化;回滚 = 删条与还原脚本硬编码,无数据迁移。存量引用在回滚后依然合法。

## 开放问题

- [x] install.md 场景二(并入现有项目)是否同步指引「存量体例豁免在 docs/README.md 注册表声明」?→ 加一句,与 1.4 条呼应,避免下游只看 install.md 时漏掉登记义务(2026-08-26 决议,已落地)。
- [x] LIVE_DOCS 动态化是否延伸覆盖自建目录(plan/、deploy/)的活文档?→ 不延伸:自建目录自治,登记义务由项目 README 自建清单承担(已有下游自建 plan 清单表),模板不预设自建目录的内容形态(2026-08-26 决议)。
- [x] verify-docs 死链检测只剥围栏代码块、不剥行内代码(第 52 行 `scanText` 仅 replace 三反引号块),行内代码中出现完整链接形态会被误报死链 —— 本 RFC 起草时已实际触发一次(证据三段落,最终改为描述化写法绕开)。→ 小修:死链检测在剥围栏后追加剥行内代码段;行内代码语义即「字面文本而非链接」,剥除后不再检查恰为期望行为,规范文档中展示链接写法的行内示例(如 1.3 类条款)亦应免检(2026-08-26 决议,已落地)。
