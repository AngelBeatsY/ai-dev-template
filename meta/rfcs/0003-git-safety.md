## 摘要

现行规范只约束「提交内容层」(Conventional Commits、禁止混合提交)与「历史层」(已推送不 rebase/amend),「动作层」—— push、merge、销毁性操作谁有权执行 —— 完全空白。本提案吸收维护者在多会话并行实操中沉淀的 git 安全规则草案,按「原则吸收、实例配置不预设」原则落为分支无关的 MUST 级条款:① 提交暂存纪律(提交前核对当前分支、`git status` 核对后精确路径 `git add`、暂存区自查、禁 `--no-verify`);② 对外与不可逆动作的授权语义(push 逐次授权、禁 force push、合并须人工评审通过且经用户授权、销毁性操作先列出丢弃内容再确认);③ 会话收尾工作区交接与合并后本地同步。授权粒度做成 workflow.md 第 8 节可调参数。草案中绑定具体分支名(main / dev)的部分不采纳:分支名是实例化时的项目配置,且 dev 长期分支与 git-workflow.md 第 1 节已选定的 trunk-based 模型直接冲突。

## 背景与动机

**证据一(暂存动作零约束)**:全仓库检索 `git add` / `暂存` 零命中。AI 工具习惯性 `git add -A` 扫入全部改动,在多会话并行场景(本模板明确支持,共享 `docs/STATUS.md` 账本)会把他会话未提交的改动夹带进自己的提交。DoD 第 7 / 8 条(不含密钥、不含无关改动,dev-standards.md 第 9 节)是完成定义层面的检查,提交时点没有防线。

**证据二(push 与合并无授权语义)**:git-workflow.md 第 1 节「小改也走分支 + PR,不直接推送主分支」是分支模型约束,不是授权语义;push 是对外可见、难撤销的动作,规范却未规定其须经用户授权。合并同样:workflow.md 第 3.5 节要求人工评审双检制,但全文未规定谁执行 merge —— 技术上 AI 可以在评审通过前自行合并,双检制在动作层无兜底。force push 仅被第 4 节「已推送的提交 MUST NOT rebase / amend」隐含覆盖;`git reset --hard`、`git clean -fd`、`git branch -D` 等直接销毁未提交工作或分支的操作零约束 —— 这是 AI 会话第一数据事故来源,危害高于 push。

**证据三(会话收尾无工作区交接义务)**:workflow.md 第 6.2 节只管 STATUS 日志,未约束工作区状态。会话中断时未提交改动裸留给下一会话去猜;stash 作为替代手段对后续会话不可见、易丢失。

**触发源**:维护者提交的分支推送授权规则草案(main 逐次授权 / dev 会话级授权、commit 前核对与精确路径暂存、不夹带并行会话改动),审读后拆解为「原则」与「实例配置」两部分,前者构成本提案主体,后者不采纳(见备选方案 B)。

## 目标

- 把 commit / push / merge / 销毁性操作的执行纪律写成分支无关的 MUST 级条款,补齐「动作层」空档。
- 授权权明确归属用户:AI 只有执行权,授权不跨会话延续;授权粒度做成可调参数,默认从严。
- 补齐会话收尾的工作区交接义务,与 STATUS.md 交接机制衔接。

## 非目标

- 不改变分支模型(trunk-based 不动),不预设 main / dev 等具体分支名。
- 不引入分支保护规则或 CI 门禁模板(README FAQ 已明确模板不绑定平台;保护规则由各项目在托管平台自行配置)。
- 不约束人本身的操作:本规范对 AI 是硬约束,人的操作自由度不受影响(授权权在人即此意)。

## 提案详述

### 1.1 git-workflow.md 第 2 节增补(Commit 规范,追加四条)

```
- 提交前 MUST 核对当前分支:任务改动 MUST NOT 直接 commit 到主分支(小改也走分支,见第 1 节)。
- 暂存用精确路径 `git add <path>`,只暂存本任务 / 本会话产出的文件;禁用 `git add -A` 与 `git add .`,不夹带并行会话的改动(含 `docs/STATUS.md` 中他会话追加的行)。
- 提交前过一遍 `git diff --staged` 自查:无调试残留(打印语句、临时脚本)、无密钥凭证(R7 在提交时点的检查)。
- 禁止 `--no-verify` 绕过 pre-commit 钩子;钩子失败时修复根因。
```

### 1.2 git-workflow.md 新增第 4 节「推送、合并与危险操作」(原第 4 / 5 节顺延为第 5 / 6 节)

```
push、合并与销毁性操作对外可见或不可逆,授权权在人:

- **推送授权**:`git push` MUST 在每次执行前获得用户当次明确授权,先前授权不跨会话延续;团队可在 workflow.md 第 8 节把非主分支放宽为会话级授权。
- **禁止 force push**(含 `--force`):已推送历史 MUST NOT 改写(见第 5 节);确需覆盖自己刚推错的功能分支,先获用户明确授权。
- **合并授权**:合并 MUST 在人工评审通过后(workflow.md 第 3.5 节)经用户当次授权执行,或由用户自行执行 —— AI 不自行合并,包括自己实现的 PR。
- **危险操作确认**:`git reset --hard`、`git clean -fd`、`git checkout/restore -- <path>`、`git branch -D` 等丢弃未提交内容或分支的操作,MUST 先列出将被丢弃的对象与内容,获用户确认后执行。
```

### 1.3 git-workflow.md 第 1 节尾部增补一条;第 5 节(原第 4 节)扩一条

```
- 换分支前工作区 MUST 干净;会话结束或中断前以干净工作区或 WIP commit 收口,交接点记入 `docs/STATUS.md`。跨会话不用 stash 保存工作(对后续会话不可见、易丢失)。
```

```
- 合并后删除分支,切回主分支并同步本地(`git pull`),清理已合并的本地分支。
```

### 1.4 AGENTS.md

硬性规则新增 R10;第 5 节摘要追加一行;头部「最后更新」改 2026-09-01:

```
- **R10** push、合并 PR、force push 与丢弃未提交改动的 git 操作 MUST 经用户当次明确授权;授权不跨会话延续。
```

```
- commit 前核对当前分支与暂存区(`git status` + `git diff --staged`),精确路径 `git add`,禁用 `git add -A` / `git add .`。
```

### 1.5 workflow.md 第 8 节可调参数加一行

```
| 推送授权粒度 | 每次推送均须用户授权 | 可放宽为会话内一次授权(主分支除外);合并与危险操作不在放宽范围(git-workflow.md 第 4 节) |
```

## 备选方案

| 维度 | 方案 A(本提案:原则吸收,分支无关 + 授权可调) | 方案 B:按原草案落 main / dev 双分支授权梯度 | 方案 C:依赖工具层权限拦截 | 方案 D:只加 CI 门禁与分支保护 |
|---|---|---|---|---|
| 成本 | git-workflow 六条 + AGENTS 两条 + 可调参数一行 | 零改写成本,但与既有规范冲突 | 零文本成本,逐工具配置 | 各项目自建,模板零成本 |
| 风险 | 低:全为新增,编号顺延无引用破坏 | 高:规范自相矛盾,实例被分支名绑架 | 高:配置跨工具不一,allowlist 可绕过 | 高:拦 merge 拦不了本地销毁操作 |
| 可逆性 | 高(删条即回滚) | 低(绑死后难解耦) | — | — |

**方案 B(按分支名分级)**:未入选。分支名是实例化时的项目配置,不是模板内容 —— 模板仓库自身主分支为 `master`,写死 `main` 当场不成立;dev 长期分支与第 1 节 trunk-based「不使用长期存在的 develop 分支」直接冲突,原样落入规范自相矛盾;「发布分支逐次 / 开发分支会话级」的梯度依附 dev 的存在,dev 拿掉后通用化为一条 + 可调参数即可。

**方案 C(工具层权限)**:未入选。AGENTS.md 的受众是全部 AI 工具(Claude Code、Cursor、Copilot 等),权限模式跨工具不一致且可被 allowlist 配置绕过;「先列出将被丢弃的内容再确认」是行为规范,权限弹窗给不了。工具层与规范层互补而非互替。

**方案 D(只做 CI 门禁)**:未入选。README FAQ 已明确模板不绑定平台、不内置 CI;分支保护拦得住 merge 拦不住本地 `reset --hard`,动作纪律不可被门禁替代。

## 影响与风险

- **AI 会话流程成本**:push / merge 前多一次授权确认 —— 这是修复目的本身,非成本。
- **已初始化项目**:git-workflow.md 第 4-6 节编号顺延;全仓库已核实无「git-workflow.md 第 N 节」形式的编号引用,下游项目如有自行添加的编号引用需跟随。
- **AGENTS.md 行数**:95 → 98 行,低于 150 硬上限。
- **共享账本的现实约束**:`git add` 是文件粒度,无法只暂存 `STATUS.md` 中本会话追加的行 —— 条款以「不夹带他会话追加的行」表述,实操含义见开放问题二。

## 迁移与回滚计划

不适用(非破坏性变更):全部条款为新增或细化,不改变既有条款语义;回滚 = 删条并还原节编号,无数据迁移。

## 开放问题

- [x] 授权粒度默认值:逐次授权 vs 草案的会话级?→ 默认逐次(从严);放宽入口收敛到 workflow.md 第 8 节可调参数,主分支与合并不在放宽范围 —— 授权梯度保留为拨盘而非预设(2026-09-01 决议)。
- [x] 「只暂存本会话产出的文件」对 `STATUS.md` 这类共享账本如何执行?→ `git add` 文件粒度做不到行级隔离,实操规则:本会话的账本行会话内及时提交;发现工作区含他会话未提交的行时停下询问,不自行取舍(2026-09-01 决议)。
- [x] 「危险操作确认」是否含 `git stash drop` / `git stash clear`?→ 含义上属销毁性操作,但 stash 已被第 1 节新条劝退,出现频率趋零,不为穷举而扩条;执行时按同原则处理即可(2026-09-01 决议)。
