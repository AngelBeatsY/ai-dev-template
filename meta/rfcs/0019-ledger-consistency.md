## 摘要

某下游项目一次全仓账面对账(此前所有验收的「docs 交叉一致」核对均为本次改动相关面,从未做过全仓比对)一次抓出 8 类状态/日期类账面漂移、30+ 处实例,而结构类检查(死链 / 命名 / 编号配对 / 登记)全部通过——漂移最长静默 13 天零检出。病灶的模板侧根因有三:**① 载体字面互相矛盾**——「spec 状态」在文件头与注册表两次呈现,workflow.md 第 3.6 节写了双动作,而 tasks 模板 TF2 把「spec 状态转 Implemented」折叠进「更新注册表」的括号里,实测中遵从 TF2 的收口只改注册表、遵从第 3.6 节的成孤例——两个核对载体教出两种动作,矛盾在模板自身;**② 字段无语义且两面字面各自自洽**——「更新日期」字段存在于 spec/brief 模板却无定义,注册表侧(6.1「状态变化时更新」→ 合并日)与文件头侧(字段名自然语义 → 修订日)各自遵从字面仍互相对不上;**③ 隐性改规范通道未封**——实践与规范字面冲突时无处置条款,某下游以工作日志拍板「不回改」并经后续会话逐环引用先例固化,规范被架空而非被修订。本提案以文字条款收口:双面同步写死(转状态四动作同一 docs commit)、TF2 字面修订、更新日期语义定案(最后修订日 + 谁改谁刷 + git 实测纪律)、状态行裸枚举词(MUST,整格机器强制)与「呈现面 = 核对面」原则、变更记录扩为迁移历史之家、自建活文档条目完成式注记标准、DoD 与 PR 自检补双面同步及 STATUS 核对行、元规则「禁止隐性改规范」、ADR append-only 豁免扩「更新日期行」、rfc/adr 模板补日期字段。机器兜底(verify-docs 检查 12)由 [RFC-0020](0020-registry-status-check.md) 承载,与本提案同批落地——检查与规则同批,否则存量常红逼人绕过。

## 背景与动机

**证据一(载体矛盾,执行会话无责的字面缺陷)**:收口会话实际在手边的核对载体是 tasks 的固定收尾任务 TF2,其现行字面为「更新 `docs/README.md` 注册表(spec 状态转 Implemented)」——转状态动作被挂在注册表更新的括号内,文件头状态行完全缺席;而 workflow.md 第 3.6 节的字面「spec 状态转 Implemented 并更新注册表」支持双动作。下游实测两字面各有遵从者:按 TF2 行事的收口留下一整批文件头滞后(18 份状态滞后 1~13 天),按第 3.6 节行事的那份成孤例无人察觉。模板双载体矛盾即规范缺陷的定义,责任不在执行会话。

**证据二(字段无语义,两面字面各自自洽)**:spec/brief 模板的「更新日期」字段无任何定义;注册表维护规则(第 6.1 节)字面为「任何状态变化时更新该行状态与日期」——按此自然填合并日;文件头字段按名称自然语义填正文修订日。下游实测 5 处注册表与文件头日期不一致,其中双方各自都能援引一条模板字面自辩——两面字面规定了两种口径,属规范自身的口径冲突。衔接行(文件头注记)算不算修订、注册表日期跟谁走,字面均无答案,每次填写都是自由裁量(另实测 8 份 spec 被衔接行修改后文件头日期未刷新)。

**证据三(隐性改规范通道)**:R4/R8 只保护规范文本不被修改,不禁止「实践与字面持续分歧 + 日志记档 + 惯例引用固化」。下游漂移链的固化形态:冲突被会话以工作日志拍板消化 → 后续会话逐环引用先例(无一环回到规范字面)→ 唯一按字面执行者成孤例 → 又退回惯例。workflow.md 第 3.5 节「不通过修改 spec 来迁就实现」的原则只覆盖 spec 面,未覆盖 conventions 面;先例链存续期间,每一环引用都无任何条款可判违规。

**病灶强度如实标注**:证据来自单一下游项目的一次对账(N=1),且暴露条件是高频接力场景(短周期内多份 spec 跨会话接力交付)——轻度使用可能长期不暴露。但缺陷存在条件不依赖活跃度:载体矛盾与语义缺失在模板字面里,轻度使用只是没触发,不是没缺陷。本提案修字面(RFC-0020 兜执行),两者分工见该 RFC。

## 目标

- **G1 双面同步写死**:workflow.md 第 3.6 节明确「文件头状态行与注册表为同一状态的两次呈现,转状态时 MUST 同一 docs commit 内同步修改」;TF2 字面修订为转状态四动作;第 3.2 节显式化「转 Active 归属立项会话」。
- **G2 更新日期语义定案**:「更新日期 = 本文件最后修订日(任何修改,含状态行、衔接行、账面追补)」;文件头与注册表同语义;**谁改文件谁刷新**该文件双面账面;日期 MUST 取 `git log` 实测,禁止凭记忆填写。
- **G3 状态行格式与「呈现面 = 核对面」原则**:状态行 MUST 为裸枚举词(不带任何日期与后缀,机器强制,检查 12 判据① 整格精确匹配);修订时点归「更新日期」、迁移历史归「变更记录」,一载体一语义;原则成文于 6.1——呈现面与核对面一一面配对,核对面 = 呈现面全格,机器不核对的语义格式不携带。
- **G4 变更记录扩为迁移历史之家**:兑现 docs/README.md 生命周期节既有承诺(「状态迁移的历史记录在文档自身的变更历史中」)——变更记录字面扩为「正文修改与状态迁移均记行」。
- **G5 自建活文档条目注记标准**:条目内施工完成记录 MUST 以完成式合入注记收尾,不留「待合并」中间态。
- **G6 核对点补行**:dev-standards.md DoD 与 PR 模板自检——注册表行字面扩为「与文件头同步」,新增 STATUS 行(义务在 6.2 已有,核对点双缺席)。
- **G7 元规则「禁止隐性改规范」**:workflow.md 第 2.5 节新增第 4 条,定位为**事后处置依据**(验收 / 评审 / 复盘时判定违规),非过程拦截。
- **G8 字段补齐**:rfc-template、adr-template 补「更新日期」字段行;ADR append-only 豁免行扩「更新日期行」;meta/rfcs 全部存量补行并对账(迁移节;含本两份,届时计 20)。

## 非目标

- **不立「修复时全仓同类扫描」条款**(下游建议之六):点修复行为正是 AGENTS.md R6「只改相关文件」教出来的;可机器查的类由 RFC-0020 落地后每次门禁自动全量扫描,不可机器查的类(注记颗粒度)立扫描义务无核对点承载(0018 维度八教训)——两头都有归宿,独立条款是负资产。
- **不立「里程碑全仓对账」条款**(下游建议之七):检查 12 落地后每次跑门禁即全仓对账,独立条款为零收益流程税。
- **tasks 模板不加日期字段**:tasks 是动态执行文档,生命周期由交付记录承载,无注册表行(恒 1:1 归检查 4),双面一致性语义对它不成立。
- **不扩注册表列**:「部分行为被 SPEC-NNNN 修改」注记(第 3.2 节再变更)在注册表无对应呈现是既有设计边界(注册表只记当前状态),本提案显式不扩,防覆盖面越界。
- **AGENTS.md 不加条款**:150 行硬上限(第 9 节),账面义务细节归 workflow.md,R5 已指向 DoD 权威清单。
- **机器检查本体不入本提案**:归 RFC-0020(同批),本提案只立义务与语义。

## 提案详述

### 1.1 双面同步与转状态四动作(workflow.md 第 3.6 节、tasks-template TF2、第 3.2 节)

第 3.6 节「合同时 MUST 完成」修订为(逐项同一 docs commit):

> - tasks 全部勾选;
> - **spec 状态收口四动作(同一 commit)**:①文件头状态行转 Implemented(裸枚举词);②变更记录记状态迁移行;③文件头「更新日期」刷新(git 实测最后修订日);④注册表行状态与「更新日期」同步。①-④ 中文件头状态行与注册表为同一状态的两次呈现, MUST 同步,不同步视为未完成(verify-docs 检查 12,RFC-0020);
> - 由 RFC 派生的改动回填 RFC 决议记录中的 spec 编号。
>
> 收口的全部账面义务并置清单:注册表(6.1)、STATUS(6.2)、自建活文档条目(6.3)——本节不重抄,收口时逐面核对。

TF2 字面改为:

> `- [ ] **TF2**:spec 状态收口四动作(同一 commit,见 workflow.md 3.6):文件头状态行 / 变更记录迁移行 / 更新日期 / 注册表行同步。`

第 3.2 节「通过标准」补半句:「状态转 Active 由**立项会话**在评审清单全绿的同一 commit 执行,四动作同上(状态行 / 迁移行 / 更新日期 / 注册表)」——钉死归属,防施工会话开工时发现仍是 Draft 而「顺手转」的二次裁量。

### 1.2 更新日期语义与来源纪律(模板注释、workflow.md 6.1、docs/README.md 维护规则)

四份模板(spec/brief/rfc/adr)「更新日期」字段行补注释:

> 本文件最后修订日(任何修改,含状态行、衔接行、账面追补),MUST 取 `git log -1 --format=%ad -- <本文件>` 实测,禁止凭记忆填写(与交付记录 commit hash 来源纪律同构,workflow.md 3.4)。

workflow.md 6.1 维护时点表「任何状态变化时 | 更新该行状态与日期」修订为:

> 任何状态变化或文件修订时 | 同步文件头与注册表行(状态、更新日期,双面同语义),由修改该文件的会话同一 commit 执行(**谁改谁刷**)

workflow.md 6.1 表后补「呈现面 = 核对面」原则句(权威落点,对应 G3):

> 状态行与「更新日期」是双面呈现(文件头 / 注册表),受 verify-docs 一致性检查——**呈现面与核对面一一面配对,机器不核对的语义不新增呈现面**;新增字段的提案 MUST 同时给出核对点。

docs/README.md 注册表维护规则同步改写(日期语义与双面同步义务),引用 6.1 不重抄原则——防第二份会漂移的声明。

「谁改谁刷」使跨文档修改的职责唯一:衔接行是后续 spec 收口动作的一部分,被衔接 spec 的双面日期刷新即该收口任务范围的**内含部分**(非 R6「范围外顺手修」)。

### 1.3 状态行格式、互链载体与变更记录扩字面(spec/brief/rfc/adr 模板、workflow.md 第 3.2 节)

状态行注释(四份模板统一):

> 状态值 MUST 为裸枚举词(生命周期见 docs/README.md),不带任何日期与后缀——当前态之外的时间线各有其家:修订时点见「更新日期」,迁移历史见「变更记录」,取代互链见状态区注记行。状态值整格受 verify-docs 检查 12 判据① 校验(裸词且在词表内),尾注形态即报错。

取代互链载体钉死(workflow.md 第 3.2 节「注册表与文件头互相标注」的执行字面):`Superseded by SPEC-NNNN(YYYY-MM-DD)` 记文件头状态区**注记行**(与「部分行为被 SPEC-NNNN 修改」注记同形态),状态单元格保持裸词 `Superseded`;注册表侧取代关系不入状态列(docs/README.md 维护规则既有),零改动。

spec-template 变更记录注释「状态转 Active 后修改正文必须在此记行」扩为:

> **状态迁移与正文修改**(Active 后)均在此记行:日期、内容(迁移 / 修改)、原因。Draft 期正文自由修改不记行。

### 1.4 自建活文档条目注记标准(workflow.md 6.3)

义务表下补一句:

> 条目内的施工完成记录 MUST 以完成式合入注记收尾(「已随 <commit> 合入 master(日期)」形态),不留「待合并」中间态——收口即终态,颗粒度以同表条目互见一致。

### 1.5 核对点补行(dev-standards.md 第 10 节、PR 模板)

- DoD 第 5 条「`docs/README.md` 注册表已更新(如有状态变化)」扩为「注册表与对应文件头已同步(状态与更新日期,双面一致)」;新增一条「STATUS.md 已按 6.2 更新(合入前:当前状态 / 进行中 / 下一步)」。
- PR 模板自检清单同步两行(与 DoD 同源)。

### 1.6 元规则第四条(workflow.md 第 2.5 节)

> 4. **禁止隐性改规范。** 会话发现实践与规范字面冲突时 MUST 二选一:按字面执行并修正既成偏差;或走规范修订流程(重大级)。MUST NOT 以工作日志拍板、惯例引用等方式形成与规范字面不一致的持续实践。违反本条的经验收、评审与复盘时作为缺陷处置依据——本条为处置依据,非过程拦截(冲突识别依赖在场者自觉,如实声明)。

### 1.7 字段补齐与 ADR 豁免(workflow.md 第 5 节、rfc/adr 模板)

- rfc-template、adr-template 字段表补 `| 更新日期 | YYYY-MM-DD |`(注释同 1.2)。
- workflow.md 第 5 节 append-only 铁律「允许更新的只有状态行与 superseded-by 链接」扩为「只有状态行、更新日期行与 superseded-by 链接」。

### 配套修改

- **meta/rfcs 存量**:全部文件头补「更新日期」行(git 实测取值;含本两份,届时计 20)+ meta/README 注册表日期列对账(现值为「状态变化日」口径产物,逐一核对刷新)——见迁移节;
- **meta/README.md**:RFC 注册表加行(随本 RFC 同一 commit);
- **decisions.md**:第 3 节机制决策行(双面同步、呈现面 = 核对面、谁改谁刷、元规则定位)+ 第 4 节「每工具路由 shim(CLAUDE.md 等)」不采纳分发行(本地 shim 合法,走点前缀通道如 `.claude/CLAUDE.md`,不入 manifest;本次讨论同期定案,随批落);
- **根 README**:版本条目(落地时,与 RFC-0020 同批)。

## 备选方案

| 维度 | 方案 A(本提案:双面同步写死) | 方案 B:注册表唯一权威(文件头状态行删除或停于立项态) | 方案 C:仅加格式建议,不写死同步 | 维持现状 |
|---|---|---|---|---|
| 呈现面数 | 2(均有核对点 + 机器兜底) | 1(零同步义务) | 2(无同步义务) | 2(无同步义务、字面互相矛盾) |
| DoR 正确性 | 文件头即核对对象,天然为真 | DoR 须改读注册表(跨文件跳转;开工评审记录与文件头自洽性断裂) | 不保 | 不保 |
| 迁移代价 | 一轮双面补齐(git 可核) | 删 19 份文件头状态行 + 改 DoR 字面 | 零 | — |
| 可逆性 | 高(条款删除即回) | 低(消费方已改) | 高 | — |

**方案 B 未入选**:meta 治理面已是单面形态(注册表即唯一状态面)且无恙,证明 B 并非不可行——但它成立的条件是**无跨会话 DoR 消费者**;分发面 spec 的文件头状态行是施工会话 DoR(第 3.4 节「spec 状态 Active」)与立项交付核对的直接输入,文件头停于立项态 = DoR 核对假状态,消费方改造成本与风险均高于双面同步。
**方案 C 未入选**:下游建议之一仅给推荐格式、不同步义务——实测已证明格式建议无法阻止载体矛盾驱动的行为(病灶正是「知道格式」与「改哪个面」的脱节);无核对点的格式建议是第二份会漂移的声明。
**维持现状未入选**:双载体矛盾是模板自身缺陷,每多一份下游接力交付即放大一批存量,与「唯一状态注册表」的核心承诺(README 文档中心定位)相悖。

## 影响与风险

- **收口动作税**:转状态从 2 动作变 4 动作(仍同一 commit 同一只手)——增量是变更记录一行与日期刷新,由 TF2 字面与检查 12 兜底;持续成本最大项是严口径下衔接行场景的双面日期刷新,「谁改谁刷」使职责唯一,无枚举场景表。
- **仪式化风险**:DoD / PR 自检新增核对行存在「勾了没核」的长期退化(0018 局限声明同款)——缓解 = 检查 12 机器兜底核对行所指向的事实,仪式化的代价上限是人工核对失效、机器层仍在。
- **元规则的事后性**:G7 不提供事中拦截,冲突识别依赖在场者自觉;其价值形态是**先例链失效**——每环「按先例不回改」的引用自此有明文可判违规(下游实测的漂移链固化形态即此通道)。
- **裸枚举词为 MUST(机器强制)**:判据① 整格精确匹配,呈现面 = 核对面全额兑现(无前导词启发式);封死无对价——后缀形态的留痕功能已由变更记录迁移行(G4)承接,`Superseded by …` 互链移状态区注记行(既有注记模式,非新机制);存量修正由唯一下游一次性完成(已接受修史,量级约 21 文件,git 可核),上游 meta 面全部状态行本为裸词(含本两份 Draft),零格式迁移。
- **存量下游升级**:一轮双面补齐 + 日期刷新(git 可核,一次性);升级前不报错(检查 12 随本批才存在)。
- **模板仓库自身**:meta 面迁移后上游自吃门禁(--template 模式检查 12 含 meta 面),治理与实践合一。

## 迁移与回滚计划

与 RFC-0020 同批发版(条款先行、检查随后在同一版本内生效,满足「检查与规则同批」前提):

1. **条款落地**:第 1.1-1.7 节全部字面修订 + 四份模板注释(rfc/adr 补字段);

4. **RFC-0020 落地开启检查 12**,上游默认 + `--template` 双模式全绿后收口。

存量下游(已初始化项目):升级 = 整文件替换规范与模板 + 一轮双面补齐(状态行 / 更新日期 / 注册表,git 实测取值)+ 状态单元格清写为裸枚举词(唯一下游,已接受修史;`Superseded by …` 旧形态移状态区注记行)。回滚 = 还原条款字面与模板注释(补齐的字段行与数据可留,无害);检查 12 由 RFC-0020 自带回滚口径。

## 开放问题

- [x] 状态行是否携带日期?→ 不携带(裸枚举词)。状态行内日期与「更新日期」行构成第三呈现面,复演本次复盘批判的「多面无同步规则」;时间线归「更新日期」(修订时点)与「变更记录」(迁移历史),一载体一语义;下游样本的日期内嵌属追补场景痕迹需求,不进模板推荐格式(2026-09-16 起草前讨论定案)。
- [x] 元规则的定位?→ 事后处置依据,非过程拦截——冲突时刻无任何环节在场(下游实测),拦截形态会制造无核对点承载的过程义务;其生效形态是先例链失效:每环惯例引用自此有明文可判违规(2026-09-16 起草前讨论定案)。
- [x] 转 Active 的归属?→ 立项会话(评审清单全绿的判定人),第 3.2 节显式化,防施工会话开工时「顺手转」的二次裁量(2026-09-16 起草前讨论定案)。
- [x] 裸枚举词的规范强度?→ 初稿设 SHOULD(前导词宽容、存量零强制回改);评审讨论以维护者新事实(下游唯一、接受修史)推翻其成本支柱,定 MUST + 机器强制(判据① 整格精确匹配)——「能低成本机器校验的错误不依赖 AI 自觉」原则全额适用,呈现面 = 核对面完全兑现;`Superseded by …` 互链载体随之钉死到状态区注记行(2026-09-16 评审讨论定)。
