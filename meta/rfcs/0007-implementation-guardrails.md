## 摘要

workflow.md 第 3.3 节有「怎么分组 Phase」(每组收口系统可运行、测试与 lint 全绿)但无「何时必须拆」的可判定判据 —— 「任务较多或跨层时按 Phase 分组」的「较多」无线,跨层长链是否拆 Phase 依赖会话自行判断;第 3.4 节 DoR 与交付记录有「全量测试通过」但无数字基线 —— 跨会话长工程中测试数静默减少(删用例、跳过失败用例)无任何环节能发现。本提案吸收一份外部项目施工计划书写 / 实施规范中的两个机制:**Phase 拆分判据**(跨层链路必拆;单 Phase 量级线;外部依赖卡点独立成期并写降级路径,阈值进可调参数)与**测试基线数**(开工实测全量 passed 基数,交付记录逐阶段对照,低于基线必须说明),落 workflow.md 第 3.3 / 3.4 节与第 8 节可调参数,tasks-template.md 指导语同步。来源项目特定内容不采纳:冒烟脚本形态、错误契约表、提交信息带 Phase 号的项目惯例。

## 背景与动机

**证据一(拆分无线)**:workflow.md 第 3.3 节拆分原则:「单任务 ≤ 半天工作量、只做一件事」「任务较多或跨层(如数据层 → 后端 → 前端)时按 Phase 分组:每组收口时系统 MUST 可运行」—— 「较多」无可判定线,「跨层」未禁止塞进单 Phase。对照第 2 节分级体系:小改有 3 文件线、小改累计有 10 文件升级线,Phase 层无对应线 —— 分级与拆分两道闸,后者无闸。跨层链路塞进单 Phase 的半破状态,「收口可运行」条款只能事后追责、不能事前阻止。

**证据二(无数字基线)**:tasks-template.md「交付记录」节格式为「测试与 lint:<通过数 / 结果>」—— 记录绝对数但无比较基准;workflow.md 第 3.4 节 DoR 五项无基线项;dev-standards.md 完成定义要求「全量测试通过」—— 只保证当下全绿。跨会话长工程中,前一会话 120 passed、后一会话 118 passed 且全绿的场景(删了 2 个用例或跳过了失败用例),现行规范无任何环节能发现 —— 「测试数只增不减」的回归保护完全依赖会话自觉。

**证据三(触发源)**:维护者调研一份外部项目的施工计划实施规范,其开工前置第 4 步(实测记 passed 基数,各阶段不低于基线、只增不减;与计划写的基线不一致时以开工实测为准并在首个交付记录注明)与书写规范 Phase 拆分判据表(跨层 / 规模 ~15 文件 ~40 用例 / 外部依赖卡点)系项目无关的通用实践,提炼为本提案主体;绑定其项目形态的部分(冒烟脚本形态、错误契约表、commit 带 Phase 号)不采纳。

## 目标

- Phase 拆分从「自行判断」变为可判定判据:跨层必拆、量级线触发、外部卡点独立成期并写降级路径;阈值进 workflow.md 第 8 节可调参数,各项目可调。
- 测试基线成为跨会话防回归锚点:开工实测记数、交付记录逐阶段对照、低于基线必须说明原因。

## 非目标

- 不改「单任务 ≤ 半天」的任务粒度定义 —— Phase 判据管分组,任务判据管拆任务,两层并存、互不替代。
- 不引入覆盖率数字目标(dev-standards.md 测试策略「覆盖率是参考不是目标」不变)。
- 不要求每个任务都重跑全量测试 —— 门禁按触发条件执行(dev-standards 与 AGENTS.md 摘要既有口径),基线是阶段比较锚点而非逐任务强制。
- 冒烟、收口复查、交付记录四要素等既有机制不动。

## 提案详述

### 1.1 workflow.md 第 3.3 节拆分原则新增一条(「按 Phase 分组」条之后)

```markdown
  - Phase 拆分判据(满足任一 MUST 拆):链路跨多层(数据 → 后端 → 前端等)时按依赖层拆分,禁止塞进单个 Phase;单 Phase 预计改动超过 15 个文件或新增测试用例超过 40 个(阈值见第 8 节可调参数);部分内容被外部依赖卡住(第三方联调、权限、DNS 等)时,无依赖部分先行交付,卡点部分独立成 Phase 并写明禁用态降级路径。
```

### 1.2 workflow.md 第 8 节可调参数加一行

```markdown
| Phase 拆分线 | 单 Phase > 15 文件或 > 40 新增用例 | 见第 3.3 节拆分判据;与小改线(3 文件)、累计升级线(10 文件)性质不同 —— 分组线非分级线,按项目规模调整 |
```

### 1.3 workflow.md 第 3.4 节 DoR 清单加一项(末尾)

```markdown
- [ ] 全量测试已实测跑通并记录 passed 基线;与 tasks 文档记录的数字不一致时以开工实测为准,首个交付记录注明。
```

### 1.4 workflow.md 第 3.4 节 AI 执行协议交付记录句增强

现句「每个任务/阶段完成后在 tasks 回填**交付记录**(commit hash、测试与 lint 结果、交接要点);交付记录与代码 MUST 同一 commit,禁止代码先走、文档后补。」括号内改为:

```markdown
(commit hash、测试与 lint 结果及与开工基线的比较、交接要点)
```

### 1.5 tasks-template.md 指导语同步(两处)

「任务清单」节 Phase 分组注释句后追加:

```markdown
拆分判据见 workflow.md 第 3.3 节:跨层按依赖拆、单 Phase 超过拆分线、外部卡点独立成期并写降级路径。
```

「交付记录」节注释追加:

```markdown
首个交付记录注明开工测试基线(全量 passed 数);后续条目与基线对照,低于基线 MUST 说明原因(合并冗余用例、移除失效用例等正当删减照实说明即可)。
```

## 备选方案

| 维度 | 方案 A(本提案:判据 + 可调参数 + 基线进 DoR 与交付记录) | 方案 B:判据只写 tasks-template 指导语,不进 workflow | 方案 C:维持现状 | 方案 D:测试数不回退做机器校验(verify-docs 扩展) |
|---|---|---|---|---|
| 成本 | workflow +4 行 + tasks-template 注释 +3 行 | 零规范改动 | 零 | 工具开发,跨语言测试计数无统一入口 |
| 风险 | 低:判据与既有分级线同构,阈值可调 | 中:模板注释是填写指导而非纪律来源,被绕过时无规范可引 | 高:半破 Phase 与静默减测试在跨会话场景无防线 | 高:模板不读项目测试框架输出,机器化不可行 |
| 迁移代价 | 零 | 零 | 零 | 各项目自建 |
| 可逆性 | 高 | 高 | — | — |

**方案 B(只进模板注释)**:未入选。tasks-template 的 HTML 注释是填写指导,指导语说「应拆」而规范不说「MUST 拆」时,判据无约束力;且模板注释可被实例化者随意删改,纪律来源必须在 conventions。

**方案 C(维持现状)**:未入选。本模板立项与施工明确支持跨会话分工(workflow.md 第 3.4 节),两个事故形态 —— 跨层塞单 Phase 的半破交付、测试数静默减少 —— 都发生在会话边界上,恰是「上下文全部经文档交接」机制覆盖不到的盲区。

**方案 D(机器校验)**:未入选。verify-docs.js 是文档自检工具,不读项目测试框架输出;测试计数跨语言无统一入口(Jest / pytest / go test 格式各异)。行为规范先行,需要强制的项目自建 CI(dev-standards 完成定义与 PR 门禁已有挂点)。

## 影响与风险

- **workflow.md 约 +4 行,tasks-template.md 注释 +3 行**:无节号变化,无交叉引用同步。
- **15 / 40 阈值是外部项目经验值,本模板无实证数据**:做成可调参数后由使用反馈调整 —— 风险为「定值不准」,有拨盘兜底;且与小改线(3 文件)、累计升级线(10 文件)形成 3 / 10 / 15 递进,性质各异(分级线 / 升级线 / 分组线),不互相冲突。
- **「低于基线必须说明」不禁止正当删减**:合并冗余用例、移除失效用例照实说明即可(§1.5 条文已内置),避免「为保数字而养死测试」的反向激励。
- **纯文档任务(TF1-TF3)与基线无关**:基线是阶段锚点,门禁仍按触发条件执行,不新增逐任务全量重跑义务。

## 开放问题

- [x] 15 / 40 定值依据:外部项目经验值,本模板无使用实证 —— 推荐按外部值落地(进可调参数),由使用反馈调整;是否需要更保守的初始值?→ 按外部值落地,阈值进 workflow.md 第 8 节可调参数,定值不准有拨盘兜底(2026-09-02 决议)。
- [x] 「低于基线」的强度:推荐「MUST 说明原因」而非「MUST NOT 低于基线」—— 删测试是正当操作,绝对禁止会产生「养死测试保数字」的反向激励;条文已按「说明即可」写。→ 按条文:MUST 说明原因,正当删减照实说明即可(2026-09-02 决议)。
- [x] 基线的持久化位置:推荐 tasks 首条交付记录注明(跨会话可查、零模板字段变更);DoR 项管会话内核对。不新增 tasks 模板字段表行 —— 字段表由立项会话填写,基线属施工会话开工实测,写入段会混淆两个会话的职责。→ 按推荐:首条交付记录注明,不加模板字段行(2026-09-02 决议)。
