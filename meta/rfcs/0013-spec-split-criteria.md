## 摘要

下游实践出现 spec:tasks 的 1:N 形态(plan 为 tasks 的下游类似物:一份 spec 对应多份功能级施工文档,如 `0001-login-page.spec` → `0001-login-page.login.plan` + `0001-login-page.password-reset.plan`(下游实况为中文命名,此处转写为模板合式命名),命名通式 `NNNN-<需求slug>.<功能>.plan`)。本提案经推演**不采纳** 1:N,同时补上规范里真实存在的空白 —— spec 层拆分判据:1:N 想承载的三类收益(按功能独立交付 / 多路并行无冲突 / 独立回滚审计),由**功能级需求各自编号立 spec(恒 1:1 不变)**以零机制改动全额获得且更强(独立 spec 独立收口);1:N 反而兑现不了独立交付 —— spec 级收口下母 spec 永远等最慢的功能。判据落 workflow.md 第 3.2 节,与第 3.3 节 Phase 拆分判据分层:Phase 判据答「一份 tasks 内怎么分组」,spec 判据答「一个需求拆成几个 spec」。

## 背景与动机

### 下游实践(1:N 的真实形态)

某下游项目以 plan 为 tasks 的类似物运行 1:N 关联,一份 spec 挂多份功能级施工文档。这不是想象形态,是使用方现状 —— 与 design 流规则当年「同构推演、模板仓库自身无实例」(RFC-0004)相比,本次有真实实证,「值得认真对待」的义务更重。

### 规范空白(判据缺位)

grep 全 docs 证实:模板只有 Phase 拆分判据(workflow.md 第 3.3 节,管 tasks 内分组),**spec 层「一个需求该拆成几个 spec」的判据不存在**。「恒 1:1」条款(decisions.md 第 3 节;workflow.md 第 3.3 节)有禁令(「不建第二份 tasks」)无出口 —— 下游 spec 偏大、想按功能切施工文档时,规范只说不行,没说该怎么办,空白被下游自行发明填满(plan 形态即其产物),与章节引用规则立项时「真空被下游自行发明填满且写错」(RFC-0002)的动机同构。

### 推演结论(为何不采纳 1:N)

1. **1:N 兑现不了它的主收益**:收口复查是 spec 级的(workflow.md 第 3.5 节)—— tasks_登录 全绿而 tasks_密码找回 未动时,母 spec 的 FR 未全部实现,不能收口,永远停在中间态等最慢的功能。「按功能独立交付」须新增「部分收口 / 子收口」状态机才成立,机制改动再加一层。
2. **完整性核对降级**:1:1 下「一份 tasks 覆盖全部 FR」天然成立、机器可核对;1:N 引入「父 spec FR 集 ↔ 各施工文档子集」的人工映射,是模板第一个机器不可核对的完整性缺口。
3. **逻辑挤压**:「功能可独立交付」恰证明契约可分;契约真正不可分的需求(强整体端到端),功能也无法独立交付 —— 1:N 的两个触发判据(功能独立交付、母需求整体性)自相挤压,不可替代场景交集极小。残存的「母需求整体性」场景,拆 spec 亦有归宿:共享约束上浮 tech/ 活文档,集成场景立独立集成 spec。
4. **门槛错位**:「恒 1:1」是已登记决策(decisions.md 第 3 节),收 1:N 是 Superseded 级变更,需同时改命名通式、check 4 / check 7、注册表多对一语义、FR 子集登记、DoR 与收口对象、收口状态机 —— 为的是获得拆 spec 零成本就有的能力。

## 目标

- 补上 spec 层拆分判据:「一个需求拆成几个 spec」有可判定口径,与 Phase 判据分层互补。
- 1:N 形态的拒绝理由与正解出口留档(decisions.md 第 4 节),下游同类提案不再重新推演。
- 恒 1:1、命名通式与全部既有检查(verify-docs.mjs check 4 / check 7)零改动。

## 非目标

- 不改 spec:tasks 恒 1:1、命名通式、注册表结构与 spec 状态机(不引入部分收口)。
- 不强制已按 plan 形态运行的下游迁移(下游本地约定自治,按需 cherry-pick)。
- 不给「可独立验收」设量化阈值(见开放问题)。
- 不把判据写进 spec-template 指导语(同 RFC-0007 落点理由:注释是填写指导非纪律来源,可被实例化者删改)。
- 不为 spec 的上游来源(brief / RFC / 自发)增设拆分判据 —— 判据的作用点是交付契约粒度(与 DoR / 收口 / tasks 配对的机制代价挂钩的层);brief 是捕获层,宽粒度零机制代价且被预期(需求集、场景集累积,RFC-0011),brief → spec 天然 1:N 由注册表来源列重复登记承载,粒度切分由本判据在 spec 层一次完成,两层重复口径必然漂移(违反单一更新义务)。

## 提案详述

### 1.1 workflow.md 第 3.2 节新增条款(「谁写」条之后)

```
- **spec 拆分判据**:需求含多个可独立验收(各自有可判对错的 FR 集)的功能时,MUST 拆为多个 spec(各自编号,slug MAY 带母需求前缀,如 `login-page-login`);不可独立验收的内容留在同一 spec 内,施工粒度诉求由 tasks 的 Phase 分组承担。跨 spec 共享约束(统一视觉规范、公共错误处理等)上浮 tech/ 活文档后引用,不在多个 spec 重复;母需求的端到端集成场景立独立集成 spec,不散入子 spec。禁止以功能级施工文档实现一份 spec 对多份 tasks(见第 3.3 节恒 1:1)。
```

### 1.2 workflow.md 第 3.3 节「恒 1:1」条句尾补出口指回

```
- **spec 与 tasks 恒 1:1**:每份进入实现的 spec 有且仅有一份同前缀 tasks;大功能在 tasks 内按 Phase 分组,**不建第二份 tasks**(破坏配对检索与 DoR 核对);按功能切分施工粒度的诉求由第 3.2 节 spec 拆分判据承担 —— 拆 spec,不拆 tasks。夭折于 Draft 的 spec 可无 tasks。
```

### 1.3 decisions.md

第 3 节机制设计加行:

```
| spec 拆分判据(多功能各自可独立验收 MUST 拆多 spec;不可独立验收留同 spec 按 Phase 分组;共享约束上浮 tech,集成场景立集成 spec) | 补 spec 层粒度判据空白(Phase 判据只管 tasks 内分组);1:N 形态(下游 plan)的拒绝出口 —— 拆 spec 不拆 tasks,恒 1:1、独立收口与完整性机器核对全保留 | 未采用:受控 1:N 功能级施工文档(见第 4 节);判据只进模板指导语(注释可被实例化者删改,同 Phase 判据落点理由);验收可分性设量化阈值(判断对象是契约性质非工作量,量级超线由 Phase 判据在 tasks 层兜底) |
```

第 4 节明确不采纳加行:

```
| spec:tasks 1:N 关联(功能级施工文档,下游 plan 形态) | 拆 spec 以零机制改动获得其全部收益:功能级需求各自编号立 spec(恒 1:1),独立收口、并行无冲突、独立回滚;spec 级收口下 1:N 兑现不了按功能独立交付(母 spec 等最慢功能);FR 子集映射靠人工登记,完整性不可机器核对(1:1 天然全 FR);「功能可独立交付」恰证明契约可分,正解是拆 spec 而非拆 tasks(判据见 workflow.md 第 3.2 节) |
```

- **verify-docs.mjs**:零改动(check 4 同编号配对、check 7 命名模式均与 spec 数量无关;判据是立项判断,不产生新文件格式)。

## 备选方案

| 维度 | 方案 A(本提案:spec 拆分判据 + 留痕) | 方案 B:受控 1:N(条件触发的功能级施工文档) | 维持现状 |
|---|---|---|---|
| 独立交付/收口 | 天然(独立 spec 独立收口) | 须新增部分收口状态机,否则母 spec 等最慢功能 | 判据缺位,诉求无出口 |
| FR 完整性核对 | 机器可核对(每 spec 全 FR) | 人工子集映射,不可机器核对 | 同 A |
| 机制改动 | 0(仅规范条款与决策行) | 命名/check 4/check 7/注册表/DoR/收口/状态机 | 0 |
| 与既有决策关系 | 完全符合(恒 1:1 加强) | Superseded「恒 1:1」 | 同 A |

**方案 B** 未入选:即本提案推演中途一度倾向、后被推翻的方案 —— 见背景推演结论四条,核心是它兑现不了「按功能独立交付」这个引入主因,却为获得拆 spec 零成本就有的能力付出 Superseded 级机制改动。**维持现状** 未入选:规范只有禁令没有出口的空白真实存在,且已被下游自行发明填满;推演产出的新论据不落档,同类提案必然重新推演甚至翻错(本次推演中途即翻错过一次)。

## 影响与风险

- **verify-docs.mjs**:零改动零影响。
- **下游迁移**:零。判据是立项判断指引,不改变任何文件格式;已按 plan 形态运行的下游可选迁移(功能级 plan 升格为独立 spec,共享约束上浮 tech,集成场景立集成 spec),模板不强制。
- **spec 计数膨胀**:判据的正确结果而非副作用 —— 计数膨胀 ≠ 内容膨胀(N 个小 spec 总内容 ≈ 1 个大 spec,共享约束上浮后更少);真实代价是 spec 级流程开销 ×N(DoR / 收口 / 注册表行),由「不可独立验收 MUST NOT 拆」护栏约束碎片化,Phase 分组承接不拆的部分。
- **认知迁移**:「大功能 = 一份 spec + 多份施工文档」的直觉需改为「多功能 = 多份 spec + 各一份 tasks」;缓解:判据给出可判定口径(验收标准的可分性),注册表行数变化当场可见。

## 迁移与回滚计划

非破坏性变更:文件格式、目录结构、既有检查全部不变,变的只是立项时的拆分判断口径。回滚 = 还原 workflow.md 两处条款文本与 decisions.md 两行;判据生效前后拆出的 spec 均合规(1:1 配对不变),无数据迁移。

**验证口径**:① 模板仓库 `node docs/verify-docs.mjs` 默认与 `--template` 双模式全绿;② grep 全仓无「功能级施工文档」「1:N」的规则性表述残留(decisions.md 不采纳行、本 RFC 档案与 workflow.md 拆分判据条款的禁令表述除外);③ 判据与 Phase 拆分判据分层无重叠:前者判「拆成几份 spec」,后者判「一份 tasks 内怎么分组」,文本互不侵入对方对象。

## 开放问题

- [x] 「可独立验收」是否设量化阈值(同 Phase 判据的 15 文件 / 40 用例)?→ 不设:spec 拆分的判断对象是验收标准的可分性(契约性质),不是工作量量级;量级超线由 Phase 判据在 tasks 层兜底,两层判据各答各的问题(2026-09-03 起草时定)。
- [x] slug 母需求前缀(`login-page-login`)是 MUST 还是自由命名?→ MAY 级纯偏好:slug 本就是自由 kebab-case 词,母子语境的权威载体是文件头与注册表(同 RFC-0011「关联不靠命名解析」口径),前缀仅承担目录内阅读便利(2026-09-03 起草时定)。
