## 摘要

spec 与 tasks 的模板在「可判定性」上有两处缺口:其一,**错误口径无集中权威表** —— 错误路径以 ER-N 逐条分散在「边界与错误路径」,「接口设计」对错误码只有一词提及;多端点 spec 中同一错误的 HTTP 状态与响应格式要从 ER 文字中提取,消费方对接与测试计划各自提取,格式漂移靠评审人眼发现。其二,**Phase 无完成边界声明** —— tasks 的 Phase 分组有拆分判据与收口条件(RFC-0007),但「该组做到哪算完」无声明,同一组内容可以「契约就绪」收口也可以「前端接完」收口,分组粒度的裁量留给会话;任务级有验收点,Phase 级无对应物。本提案吸收一份外部项目施工计划书写规范中的两个机制:**错误契约集中表**(场景 / HTTP / 错误码 / 附加字段,对外错误的唯一格式口径)与 **Phase 交付边界声明**(该组完成时可验收的边界,与任务验收点呼应),落 spec-template.md 与 tasks-template.md 的指导语。来源项目特定内容不采纳:错误契约章设为所有功能开发必备的强制粒度、依赖层 401 行的具体先例、施工计划十章结构。

## 背景与动机

**证据一(错误口径分散)**:spec-template.md「边界与错误路径」的 ER-N 逐条描述「场景 → 系统的行为与用户可见的错误」,「接口设计 → API / 函数签名」指导语仅「端点、参数、返回值、错误码」一词带过。多端点 spec 中,同一错误码的 HTTP 状态、响应体格式只能从各 ER 条目文字中提取;BFF / 前端对接与测试计划各自提取,无唯一权威表 —— 对照 spec 自身纪律(FR「可判对错」、现状盘点「附证据」),错误格式是接口契约中唯一没有集中可判定载体的部分。

**证据二(Phase 无边界)**:tasks-template.md 的 Phase 分组指导语(RFC-0007 后)含拆分判据(跨层 / 量级线 / 外部卡点)与收口条件(系统可运行、测试 lint 全绿),但收口条件只回答「什么状态可以收」,不回答「这组做到哪算完」—— 后端契约就绪可收、前端消费完也可收,分组粒度的裁量留给施工会话。对照任务级:每个任务带验收点;Phase 级缺同构的边界声明,「边界说做到哪,验收说怎么证明」的两层结构在 Phase 层断档。

**触发源**:维护者调研一份外部项目的施工计划书写规范,对应机制:必备章「错误契约(后端唯一口径)」—— 场景 / HTTP / error_code / extra 全场景表;Phase 划分表「交付边界」列 —— 该 Phase 完成时可验收的边界,与验收标准呼应。提炼为本提案两条;其「错误契约章对所有功能开发必备」的强制粒度不采纳(本模板以错误路径数量设豁免线,匹配轻量定位)。

## 目标

- 对外错误路径较多的 spec 获得集中错误契约表:HTTP / 错误码 / 附加字段的唯一格式口径,ER-N 引用而不重复定义,消费方与测试计划以表为准。
- Phase 分组获得交付边界声明:每组「做到哪算完」可判定,与组内任务验收点构成「边界 / 证明」两层结构。

## 非目标

- 不改 ER-N 逐条列举的既有形态 —— 错误契约表是格式口径的集中,不是错误路径的迁移;两节分工在指导语中划清。
- 不设统一错误码命名规范(error_code 风格归项目 tech-stack.md 声明)。
- 不给 tasks 字段表加「交付边界」行 —— 字段表是 spec 级全局字段,交付边界每 Phase 一个,归分组小节。
- 错误路径少于豁免线的轻量 spec 不承担义务(条件前缀自然豁免)。

## 提案详述

### 1.1 spec-template.md「接口设计 → API / 函数签名」指导语替换

现指导语「`<!-- 端点、参数、返回值、错误码;与现有接口的风格一致。 -->`」替换为:

```markdown
<!-- 端点、参数、返回值、错误码;与现有接口的风格一致。
对外错误路径 ≥ 3 条时,在此集中「错误契约」表:场景 / HTTP / 错误码 / 附加字段,
作为对外错误的唯一格式口径;「边界与错误路径」的 ER-N 引用表内错误码描述触发场景与系统行为,
不重复定义格式;消费方对接与测试计划以本表为准。 -->
```

### 1.2 tasks-template.md「任务清单」Phase 分组指导语追加(拆分判据句之后)

```markdown
每个 Phase 声明「交付边界」:该组完成时可验收的边界(如「契约可用」「页面可达」),写在分组小节开头;组内任务验收点说明如何证明边界达成。
```

## 备选方案

| 维度 | 方案 A(本提案:指导语内嵌两机制) | 方案 B:错误契约独立模板文件 | 方案 C:交付边界做 tasks 字段表行 | 方案 D:维持现状 |
|---|---|---|---|---|
| 成本 | 两处注释改写 | 新模板 + 实例化物 + 登记义务 | 字段表加行 | 零 |
| 风险 | 低:条件前缀豁免轻量 spec | 中:第二份要维护的文档,decisions.md 不采纳 reviews/ 同理由 | 中:字段表是 spec 级全局字段,装不下 Phase 级内容 | 高:错误格式漂移与 Phase 裁量无载体 |
| 迁移代价 | 零 | 全部新建 | 零 | 零 |
| 可逆性 | 高 | 高 | 高 | — |

**方案 B(独立错误契约模板)**:未入选。错误契约与接口设计同生同灭(同一 spec 的同一组端点),独立成档制造第二份要维护与互链的文档;来源项目也是作为施工计划内的一章而非独立文档。spec 内集中即可。

**方案 C(交付边界进字段表)**:未入选。tasks 字段表(对应 Spec / 创建日期)是 spec 级全局字段,交付边界是每 Phase 一个的组级声明,粒度不匹配;写进分组小节才能与该组任务验收点相邻。

**方案 D(维持现状)**:未入选。两个缺口同属「可判定性」断档 —— spec 自身纪律要求 FR 可判对错、验收点可证明,而错误格式与 Phase 完成线这两处恰恰没有可判定载体,体系不自洽。

## 影响与风险

- **两个模板均为注释指导语改动**:渲染输出不变;实例化时按指导语执行,无新增必填节(错误契约表条件触发,交付边界仅 Phase 分组的 tasks 适用)。
- **错误契约表与 ER-N 的双写风险**:指导语已划清分工 —— 表管格式口径(HTTP / 错误码 / 附加字段),ER-N 管触发场景与行为并引用表内错误码;「不重复定义格式」为显式禁令。
- **「≥ 3 条」豁免线的裁量**:线内轻量 spec 的错误口径仍由 ER-N 承载,不因豁免而缺失;线值进开放问题决议,不做成可调参数(模板指导语内的经验线,非流程阈值)。

## 迁移与回滚计划

不适用(非破坏性变更):指导语替换与追加,存量流水产物不追溯;回滚 = revert 对应 commit。

## 开放问题

- [x] 「≥ 3 条错误路径」豁免线的定值:来源项目无此线(错误契约章对所有功能开发必备);本模板轻量定位下设线豁免小 spec,推荐 ≥ 3(两条以内 ER-N 文字足以承载)。→ 按推荐定 ≥ 3,指导语内经验线,不做可调参数(2026-09-02 决议)。
- [x] 错误契约表是否强制覆盖依赖层错误(如上游 401 透传的对外呈现):来源项目表含「依赖层 401 行」;推荐不强制点名 —— 依赖层错误的对外呈现由 ER 分析自然覆盖,指导语不穷举场景。→ 按推荐:不强制点名,指导语不穷举场景(2026-09-02 决议)。
- [x] 交付边界的表达形式:推荐分组小节开头一行文字(Phase 数通常 2–4,表格过重);若团队偏好表格,「Phase / 内容 / 交付边界」三列表为备选形态。→ 按推荐:分组小节开头一行文字(2026-09-02 决议)。
