## 摘要

现行 research 规范只支持单文件调研:结论落档为一个 markdown,只读不回改。实际使用中,一次深挖调研会同时产出结论与大量证据(原始 API 响应、先例项目源码原文、取证脚本)—— 已发生的真实案例产出 60+ 个证据文件,现行规范无处安放。本提案在不改动「不编号、主题命名、只读」三大既有规则的前提下,引入与 design/ 资产目录同构的组织方式:主文档仍平铺 `docs/research/<slug>.md`,证据归档到同 slug 子目录 `docs/research/<slug>/`,并配套证据清单、进 git 范围与登记规则。

## 背景与动机

**问题的证据(真实发生)**:memento 项目(AI 会话互操作工具,基于本模板初始化)在可行性调研阶段对 8 个先例工具做了源码级取证,产出:

```
docs/research/prior-art/
├── findings.md      主文档(结论,含模板字段头)
├── fetch-src.js     取证脚本(GitHub API / npm registry 拉取,可复跑)
├── raw/             31 个原始 JSON(gh-meta-*.json、npm-*.json)
├── readmes/         8 个 README 摘录
└── src/             30 个先例项目源码原文(openmemory-*.ts 等)
```

共 60+ 个证据文件,总量 < 1 MB,全部为文本。这些证据是 AGENTS.md R9「结论 MUST 附证据」的实体支撑:主文档标注「confirmed = 直接读自仓库/源码」时,证据原文必须在仓库内可被引用,否则 R9 沦为口号。同时 verify-docs.js 死链检查遍历全部 markdown 相对链接 —— 主文档引用证据文件,要求证据随仓库分发。

现行规范(structure.md 第 2、4 节)对 research 只定义了单文件形态,没有多文件的规定,导致:

1. 证据文件散放 research/ 顶层会破坏「一个主题一个文件」的检索面;
2. 证据不进 git、只记链接,则外部托管失效后 R9 证据链断裂;
3. 各项目自行发明组织方式(memento 即自行建了 prior-art/ 子目录),模板失去「复制即治理」的价值。

**为什么现在改**:模板刚发布 v1.0.0,尚无第二个长期使用的项目,memento 是唯一已发生的实例,趁规范无存量包袱时收口成本最低。

## 目标

- 为多文件调研定义唯一推荐形态,与 design/ 5.1 风格一致(条款式、MUST/SHOULD/MAY)。
- 明确证据进 git 的范围、清单登记粒度、与只读规则的衔接。
- 单文件调研的形态、链接、检索面完全不变(非破坏)。
- research-template.md 同步增加「证据清单」节。

## 非目标

- 不改变 research「不编号、主题命名、只读」三大规则。
- 不引入 research 编号注册表(research 不是编号流水产物)。
- 不规定证据目录内部的固定子目录名(raw/、readmes/、src/ 是示例不是强制)。
- 不处理超量证据的外部托管方案细节(只给阈值与记链接的要求)。

## 提案详述

structure.md 修改三处(1.1 替换第 2 节 research/ 行、1.2 替换第 4 节 research 命名条目、1.3 新增 5.2 节):

### 1.1 第 2 节 docs/ 子目录职责表 research/ 行(替换)

```
| `docs/research/` | 调研记录(按 [research-template.md](../research/research-template.md) 实例化);**只读:结论落档不回改,新结论追加新文件**;多文件调研的组织见 5.2 节 | 待验证的猜想、无结论的笔记 |
```

### 1.2 第 4 节命名总则 research 条目(替换)

```
- 调研记录不编号:按主题命名,如 `docs/research/claude-code-format.md`;文件头带日期与「状态」(有效 / 被后续调研取代)。多文件调研的同 slug 证据子目录见 5.2 节,子目录名 MUST 与主文档 slug 完全一致。
```

### 1.3 新增 5.2 节(置于 5.1 之后、「6. 归档」之前)

```markdown
### 5.2 research/ 多文件调研组织

调研记录(markdown)是主文档与**唯一入口**,始终平铺在 `docs/research/<slug>.md`。当一次调研在结论之外还需留存证据(原始数据、源码摘录)或取证脚本时,按同 slug 子目录归档:

docs/research/
├── claude-code-format.md          # 单文件调研:无子目录
├── prior-art.md                   # 多文件调研主文档:结论、证据清单在这里
└── prior-art/                     # 与主文档同 slug 的证据目录
    ├── fetch.js                   # 取证脚本:证据怎么拉的,可复跑
    ├── raw/                       # 原始数据(gh-meta-*.json 等)
    └── src/                       # 源码原文

- **判据**:调研结论之外需留存 >1 个证据文件,或 ≥1 个取证脚本时 SHOULD 建子目录;只有结论(0-1 个附件)时 MUST 保持单文件,不建目录。证据目录内 MAY 再按证据类型分子目录(raw/、readmes/、src/ 等,名称不强制)。
- **主文档职责不变**:MUST 含模板字段头(日期/状态/起因/被取代)与四节正文;状态标注在主文档头部,子目录无独立状态。
- **证据清单**:主文档 MUST 设「证据清单」节,列出证据目录的内容与用途。粒度:取证脚本与少量(≤5 个)独立证据逐文件登记;批量同类证据按子目录登记一行,注明数量与单条内容。
- **进 git 的范围**:文本类证据(json/md/源码原文)与取证脚本进 git(与 design/ 5.1「文本资产进 git」一致);二进制与超量文本(单次 >5 MB 或 >500 文件)不进 git,外部托管并在清单记链接与获取方式(与 AGENTS.md R7 一致)。
- **只读规则的延伸**:证据目录与主文档一样落档后不回改 —— 修正证据错误时追加新文件并互链,不覆盖旧文件;未被主文档引用的证据应删除;证据文件不带版本号。
- **再调研**:同一主题再调研时新建平铺主文档(如 `<slug>-2.md` 或新主题 slug),需要新证据时新建同 slug 证据目录;两份主文档头部互相链接,既有规则不变。
- **登记**:多文件调研 MUST 在 `docs/README.md` 的 research 文件清单表中登记一行(主文档链接 + 证据内容一句说明);单文件调研 MAY 登记。
```

### 配套修改

- **research-template.md**:头部注释追加一句「多文件调研:主文档仍为 `docs/research/<主题>.md`,证据放同 slug 子目录,组织规则见 structure.md 5.2」;「方法与范围」节后新增「证据清单」节(表格:路径/内容/用途;无证据目录时删除本节)。
- **docs/README.md**:文档地图 research/ 行描述扩一句;文档地图下方新增「research 文件清单」表(列:文件/目录、内容),初始仅表头。

## 备选方案

| 维度 | 方案 A(本提案:平铺主文档 + 同 slug 证据目录) | 方案 B:`research/assets/<slug>/` | 方案 C:`<slug>/index.md` 主文档进目录 | 维持现状(证据不进 git,只记链接) |
|---|---|---|---|---|
| 成本 | structure.md 加一节 + 模板加一节 | 同左,多一层 assets/ 目录 | 三大规则表述全部要改 | 零 |
| 风险 | 低:主文档路径不变,无死链风险 | 中:目录层级深一层,主文档与证据不相邻 | 高:入站链接路径变更、slug.md 与 slug/ 不能共存 | 高:R9 证据链依赖外部托管存续 |
| 迁移代价 | 零(纯新增,无存量) | 零 | 既有平铺调研全部要迁 | — |
| 可逆性 | 高(删节即回滚) | 高 | 低 | — |

**方案 A(本提案)**:主文档平铺不动,证据按同 slug 子目录归档;主文档与证据目录在目录列表中相邻,`ls research/` 一眼看清主题与证据的对应。

**方案 B(research/assets/\<slug\>/)**:与 design/ 5.1 完全同构,统一 assets/ 中间层。未入选理由:design/ 用 `assets/NNNN-<slug>/` 是因为编号前缀保证排序与配对检索;research 不编号,assets/ 层只是把同 slug 目录挪深一层,无检索收益,反让主文档与证据不相邻。

**方案 C(\<slug\>/index.md 或 \<slug\>/\<slug\>.md)**:调研记录的唯一身份从文件变成目录。未入选理由:(1)「同一主题再调研追加新文件」需要新命名规则,只读/互链规则表述全部要改;(2) 从 spec、AGENTS.md 路由表指向调研的入站链接路径全部变更;(3) `<slug>.md` 与 `<slug>/` 文件系统不能共存,目录形态反过来约束主文档命名;(4) index.md 语义弱,`ls` 看不到主题名。

**维持现状**:证据不进 git,主文档只记外部链接。未入选理由:直接削弱 R9 —— 证据必须可被评审者当场打开;外部托管有存续与权限问题,verify-docs.js 死链检查覆盖不到;memento 实例证明 60+ 文本证据进 git 完全可行(总量 < 1 MB)。

## 影响与风险

- **verify-docs.js**:零影响。死链检查按 `path.resolve(path.dirname(f), target)` 解析相对链接,主文档平铺意味着链接路径形态不变;主文档引用证据(`prior-art/raw/gh-meta-x.json`)是普通相对链接,天然被检查覆盖。无需改脚本。
- **既有平铺调研**:零影响。判据条款允许单文件调研永远保持单文件。
- **AGENTS.md**:不动。路由表按目录引用已覆盖;形态细节属 structure.md 职责。
- **docs/README.md**:新增一张清单表。风险:人工维护可能漏登 —— 缓解:多文件调研登记列为 MUST,PR 自检时与注册表同一时点核对。
- **仓库体积**:文本证据进 git 可能膨胀。缓解:阈值条款(单次 >5 MB 或 >500 文件外部托管)+ 未引用证据应删除 + 二进制禁入。
- **学习成本**:新增一节规范 + 一个判据;与 design/ 5.1 同构,已理解 design/ 的人零额外成本。

## 迁移与回滚计划

不适用(非破坏性变更):纯新增条款,不修改既有条款语义;既有单文件调研天然合规。回滚 = 删除 5.2 节与模板新增节,已按新规范创建的证据目录仍可读、链接不断,无数据迁移。
