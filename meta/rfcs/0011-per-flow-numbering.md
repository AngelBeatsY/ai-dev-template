## 摘要

现行规则要求「spec 编号沿用来源(brief 或 RFC)」,structure.md 第 4 节示例呈现 `0001-user-auth` 全链同号的理想态。实践中 brief 与 spec 独立开始、独立推进(某个时点 briefs 在 0002、specs 已在 0007 是常态),沿用目标号被 RFC 来源或自发 spec 占据时只能回落 specs/ max+1 —— 回落一旦发生,编号即成**双语义**(同号有时意味着同一需求线程,有时毫无关联),且规则文本与实践长期脱节。本提案改为**各流独立取号**:编号回归「流内序号」单一语义;spec 与来源 brief/RFC 的关联由文件头「来源」字段与注册表「来源」列承载(既有机制,升格为权威);slug SHOULD 跨流一致承担检索关联。spec → tasks → design 的同号链**保留**(恒 1:1,spec 是唯一编号锚,无占用问题)。verify-docs.js 零改动;已按回落形态运行的下游零迁移。

## 背景与动机

**实践形态(维护者自述,多个项目一致)**:brief 与 spec 基本独立开始 —— spec 常从 RFC 或讨论直接立项,brief 常在 spec 之外累积(需求集、场景集);两条流的取号速度天然不同步。此时「沿用来源编号」规则:

1. **撞号是常态而非例外**:specs/ 的号被三个源头填充(RFC 来源 spec 用 RFC 号、自发 spec 用 max+1、一 brief 多 spec 的首份),后到的 brief 来源 spec 命中空闲号的概率随项目推进快速下降;命中时还会产生**乱序补位**(specs 已到 0007,0003 才出现),破坏「编号 ≈ 时序」的目录直觉;
2. **回落导致双语义**:`specs/0003` 有时与 `briefs/0003` 同线程(沿用成功),有时无关(回落)—— 同一文件名形态两种含义,只能靠记忆区分,这是永久的认知税;
3. **示例误导**:structure.md 第 4 节与 workflow.md 第 3.2 节的 `0002-x` 全链示例呈现的是几乎不出现的理想态,下游要自己发现规则在实践中不可维持并自行发明回落(已有下游五份 spec 共享单一 brief 来源,全部回落取号并在注册表注明理由)。

**关联需求的既有载体已被低估**:「全链沿用」想提供的一号贯一条需求线程,已由两个不依赖撞号运气的机制承担 —— 文件头「来源」字段 + 注册表来源登记(显式、权威),slug 跨流一致(grep 关联)。编号沿用是三者中唯一会失效的机制。

**为什么保留 spec → tasks → design 同号链**:tasks 与 spec 恒 1:1(decisions.md 第 3 节),design 挂靠唯一 spec 且迭代收敛在单文档内(structure.md 5.1)—— 两者来源唯一、无第二个源头抢号,沿用无撞号问题,保留检索便利零成本。需要解耦的只有 brief → spec 这一跳。

## 目标

- 编号语义单一化:NNNN 一律是「流内序号」,跨流永不承载数据。
- 跨流关联权威化:来源列 + 文件头「来源」字段为唯一权威,创建同一 commit 填写。
- 下游零迁移:文件命名格式不变,已按回落取号运行的项目即已合规。

## 非目标

- 不改 spec/tasks/design 同号链(见上,无占用问题)。
- 不改各流状态机、评审流程与注册表其余结构。
- 不给 verify-docs 增加跨流校验(编号不再承载关联,机器无从也无须从文件名校验来源;来源列人工核对与 PR 自检覆盖)。
- 不强制 slug 跨流一致(SHOULD 级,见开放问题)。

## 提案详述

### 1.1 structure.md 第 4 节核心规则(替换「spec 编号沿用来源…」一条)

```
- 各流独立取号:编号在各自目录内取 max+1,不跨流沿用 —— brief 与 spec 独立开始、独立推进,编号相同不蕴含关联,不乱序补位(破坏「编号 ≈ 时序」的目录直觉)。spec 与来源 brief/RFC 的关联记入文件头「来源」字段(BRIEF-NNNN / RFC-NNNN / 无)并在注册表「来源」列登记,与文件创建同一 commit;slug SHOULD 与来源 brief 一致,不强制(规格聚焦点常窄于 brief)。
```

### 1.2 structure.md 第 4 节示例块(替换)

```
docs/briefs/0001-user-auth.brief.md      # briefs/ 流内取号;编号不跨流,关联记注册表来源列
docs/specs/0007-user-auth.spec.md        # specs/ 流内取号;文件头「来源: BRIEF-0001」
docs/specs/0007-user-auth.tasks.md       # tasks 与 spec 同号(恒 1:1)
docs/design/0007-user-auth.md            # design 与来源 spec 同号同 slug
docs/rfcs/0003-replace-storage-engine.md # 单类型目录,不加类型后缀(判据见上)
docs/adr/0002-use-postgresql.md
```

### 1.3 structure.md 第 4 节 design 条与第 52 行 .brief 后缀理由(替换)

```
- design 编号与来源 spec 同号同 slug(spec 是 tasks/design 的唯一编号锚,恒 1:1 无第二个源头抢号);设计稿定稿先于 spec Active(见 [workflow.md](workflow.md) 第 3.2 节)。无来源 spec 的视觉探索不进 design/,按 [workflow.md](workflow.md) 第 2 节探索规则处理,留存结论进 docs/research/。
```

第 52 行 `.brief` 后缀保留理由改写(规则不变,理由不再依赖同号成链):

```
- 类型后缀仅在同目录存在多种流水类型时使用(specs/ 的 spec 与 tasks);单类型目录(rfcs/、adr/、design/)目录名即类型,不加后缀;briefs/ 固定 `.brief`:brief 常与其 spec 同 slug 而编号独立,后缀跨目录标记类型,避免同名歧义。
```

### 1.4 workflow.md 第 3.2 节「谁写」条(替换编号句)

```
- **谁写**:spec 负责人(通常由实现负责人担任,AI 可代笔)。从 [spec-template.md](../specs/spec-template.md) 实例化到 `docs/specs/NNNN-<slug>.spec.md`,**编号在 specs/ 内取 max+1,不沿用来源编号**(brief 与 spec 独立推进,跨流编号无关联语义);来源(BRIEF-NNNN / RFC-NNNN / 无)写入文件头「来源」字段并在注册表「来源」列登记。tasks 与 design 随来源 spec 同号:spec → 同号 tasks(恒 1:1)→ 同号同 slug design(有设计稿时)。文件头互相引用;slug SHOULD 与来源 brief 一致。
```

### 1.5 spec-template.md「来源」字段值域(替换)

```
| 来源 | BRIEF-NNNN / RFC-NNNN / 无(自发;编号即 specs/ 内 max+1) |
```

### 1.6 docs/README.md Specs 注册表加「来源」列

Specs 表头与示例行加「来源」列(Briefs/RFCs/ADRs 表不动 —— 它们不是跨流汇聚点);维护规则补一句:

```
spec 行 MUST 填「来源」列(与文件头「来源」字段一致,创建同一 commit 填写)—— 跨流关联以本列为权威,编号不承载关联语义。来源列只填需求侧来源(BRIEF-NNNN / RFC-NNNN / 无,多 spec 同源时重复填写);再变更的取代关系由 Superseded 状态与文件头互链承载,不入本列。
```

### 配套修改(落地时同步)

- **docs/decisions.md**:第 3 节机制决策行(编号流内单一语义、来源列权威、spec 锚链保留;未采用:沿用 + 撞号条款、复合编号);第 1 节 `.brief` 后缀行的理由句同步。
- **根 README**:模板版本 v1.11.0 条目。
- **verify-docs.js**:零改动(检查 4 同前缀配对、检查 7 命名模式均与编号语义无关)。
- **tasks-template.md / design-template.md**:零改动(「与对应 spec 同前缀」「同号同 slug」在新规则下原样成立)。

## 备选方案

| 维度 | 方案 A(本提案:各流独立取号) | 方案 B:维持沿用 + 撞号回落条款 | 方案 C:复合编号(0003.1) | 维持现状 |
|---|---|---|---|---|
| 编号语义 | 单一(流内序号) | 双语义(同线程或无关,靠记忆) | 单一但破坏 4 位约定 | 双语义 |
| 取号动作 | 永远 max+1,零判断 | 先查目标号空闲与否,再回落 | — | 同 B |
| 示例与实践 | 一致 | 示例仍是理想态 | — | 脱节 |
| 下游迁移 | 零(回落形态即合规) | — | 全量改造 | — |

**方案 B** 未入选:撞号条款把「查占用 → 回落 → 注册表注明」变成每次取号的判断负担,且双语义认知税永久保留 —— 编号仍不能安全地当作「流内序号」或「线程 ID」中任何一个使用。**方案 C** 未入选:破坏 4 位零填充约定与 check 7 命名模式,排序混乱,无补偿收益。**维持现状** 未入选:规则文本与实践脱节,每个下游都要自行发现、自行发明回落并自行注明 —— 已有下游走过的弯路即是实证。

## 影响与风险

- **verify-docs.js**:零改动零影响(两项相关检查均只看格式与 specs/ 内部配对)。
- **下游迁移**:零。文件命名格式不变;已按回落取号运行的项目即合规。历史上沿用成功的同号 spec(恰好命中空闲号)无需改号 —— 编号不回收,其来源列照常登记,语义由来源列而非编号表述。
- **下游可选项(非义务)**:按回落形态运行的下游可同步为注册表 Specs 表补「来源」列;原注册表中的回落说明措辞可从「偏离注记」简化为合规陈述(新规则下回落形态即本来的形态)。
- **认知迁移**:老用户需更新「同号即同线程」的直觉;缓解:来源列显式化后,误读会被注册表当场纠正。
- **slug 漂移**:解耦后 brief 与 spec 的 slug 可能分化(SHOULD 不 MUST)。关联检索不受损(来源列权威);slug 一致性退化为纯检索便利,PR 自检可顺带核对。

## 迁移与回滚计划

非破坏性变更:文件命名格式、目录结构、既有检查全部不变,变的只是**取号时的选择动作**(永远 max+1 vs 先查沿用)。回滚 = 还原四处条款文本;回滚前已按新规则取号的文件完全合规(两种规则对同一组文件的判定一致),无数据迁移。

**验证口径**:① 模板仓库 `node docs/verify-docs.js` 默认与 `--template` 双模式全绿;② 文档层面核对:grep 全仓无「沿用来源编号」残留表述,示例块与规则一致;③ 下游对照:按回落形态运行的下游项目在两版规则下检查结果一致(零迁移声明成立)。

## 开放问题

- [x] slug 跨流一致取 MUST 还是 SHOULD?→ SHOULD:关联权威在来源列,精确性不依赖 slug;spec 聚焦点常窄于 brief(如 brief `user-auth` → spec `login-lockout`),MUST 会制造无谓改名(2026-09-02 起草时定)。
- [x] design 编号是否也解耦为流内取号?→ 不解耦:spec → design 恒 1:1(design 挂靠唯一 spec,迭代收敛在单文档内),spec 号即唯一锚,沿用无占用问题,保留同号同 slug 检索便利零成本(2026-09-02 起草时定)。
