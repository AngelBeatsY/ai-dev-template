## 摘要

workflow.md 第 3.4 / 3.5 节的施工执行协议存在三个「会话边界」缺口:其一,**续作定位无显式动作** —— AGENTS.md 只说「读 STATUS.md 恢复上下文」,具体 spec 的施工进度真相源(tasks 勾选状态与交付记录)没有被指为续作入口,中断恢复依赖会话自行判断;其二,**未覆盖细节无处置条款** —— 偏离两级处理管「实现与 spec 的不一致」,而「tasks 没写到、但属于当前任务范围」的细节不构成偏离,先写完再补文档的行为无约束,是「代码先走、文档后补」的变体;其三,**清理确认只覆盖脚本** —— 冒烟验证「临时脚本跑完即删」,测试数据残留无条款。本提案吸收一份外部项目施工计划实施 / 书写规范中的对应机制,三条增补:DoR 新增续作定位项;执行协议新增未覆盖细节处置(先定案、回填 tasks、再施工);冒烟句与 dev-standards 调试纪律的清理义务同步扩至测试数据。来源项目特定内容不采纳:头部五字段状态块、第 0 步实测章形态、禁用态词汇体系。

## 背景与动机

**证据一(续作定位)**:AGENTS.md 第 2 节「任何会话开始先读 `docs/STATUS.md` 恢复上下文」是项目级账本;workflow.md 第 3.4 节开工提示词只说「先完成开工就绪核对,再开始第一个任务」。单个 spec 的施工进度记录在 tasks 勾选状态与交付记录里,「续作时读哪个文件、按什么定位进度」无显式动作 —— STATUS.md 的工作日志是全局视角,spec 级「停在第几个任务、交付记录最后一条说了什么」需要会话自行拼装,与 workflow.md 第 6.2 节「任何时刻中断都能恢复上下文」的目标在 spec 层缺一环。

**证据二(未覆盖细节)**:workflow.md 第 3.4 节偏离两级处理的前提是「实现与 spec 不一致」—— 有既定写法才谈得上偏离;「tasks 没写到、但属于当前任务范围」的细节(边界情况的兜底写法、辅助函数的落点)无既定写法,不属于偏离。现状:AGENTS.md R6 只管范围外(报告而不顺手修),范围内未覆盖细节由会话自行发挥 —— 先写完再说,文档回填滞后,恰是第 3.4 节「禁止代码先走、文档后补」所防行为的变体。

**证据三(清理确认)**:workflow.md 第 3.5 节冒烟验证「临时脚本跑完即删、不进提交」只约束脚本;dev-standards.md 调试纪律「临时调试代码验证后删除」同样只覆盖代码。冒烟驱动真实调用链与调试验证常伴随测试数据(临时用户、临时记录),数据残留不入任何条款 —— 仓库可以干净,环境与数据库不会。

**触发源**:维护者调研一份外部项目的施工计划实施 / 书写规范,对应机制:续作「先读头部状态、待回填勾选与最新一份交付记录定位进度,再从下一 Phase 接续」;「计划未覆盖的细节:先定案、回填计划(含定案理由),再施工」;前置实测记录含「清理确认(临时数据删除,注明跑完即删、无残留)」。提炼为本提案三条;其项目特定形态不采纳。

## 目标

- 续作(中断恢复)的进度定位动作显式化:tasks 勾选与交付记录被指为 spec 施工进度的真相源。
- 范围内未覆盖细节获得处置条款:先定案、回填 tasks、再施工,堵住「代码先走、文档后补」的变体通道。
- 清理义务从脚本扩展到测试数据,冒烟与调试两处口径一致。

## 非目标

- 不改 DoR 既有六项与开工提示词模板的形态(续作定位以新增项进入,条件前缀使首次施工会话自然跳过)。
- 不给 STATUS.md 增加 spec 级进度字段 —— tasks 交付记录已是真相源,双写违反单一更新义务。
- 不改变 AGENTS.md 第 7 节「必须停下来询问」的触发范围:实现细节定案不打断执行,触及契约 / 边界的仍走实质偏离修订 spec 的既有通道。

## 提案详述

### 1.1 workflow.md 第 3.4 节 DoR 清单加一项(末尾)

```markdown
- [ ] 续作(中断后恢复)时:已读 tasks 勾选状态与最新一份交付记录定位进度,从下一未完成任务接续。
```

### 1.2 workflow.md 第 3.4 节 AI 执行协议「偏离两级处理」条之后加一条

```markdown
  - tasks 未覆盖但属于当前任务范围的实现细节:先定案、回填 tasks(含定案理由)再施工 —— 不允许先写完再补文档;触及契约、数据结构、边界、范围的,按实质偏离先修订 spec。
```

### 1.3 workflow.md 第 3.5 节冒烟句清理义务扩展

现句「MAY 用临时脚本驱动真实调用链(mock 只打在外部依赖边界),脚本跑完即删、不进提交」中「脚本跑完即删、不进提交」改为:

```markdown
临时脚本与测试数据用后即删、不进提交
```

### 1.4 dev-standards.md 调试纪律同步(清理口径一致)

第 4 节第 2 步「临时调试代码验证后删除」改为:

```markdown
临时调试代码与临时数据验证后删除。
```

### 配套修改

- **meta/README.md**:RFC 注册表加行(与本 RFC 同一 commit)。
- **README.md**:Accepted 落地时模板版本加 v1.8.0 条目。
- **docs/decisions.md**:第 3 节「机制设计」加行。
- **AGENTS.md**:不动 —— 三条增补均在「施工 / 改代码」路由必读文件(workflow.md、dev-standards.md)内。

## 备选方案

| 维度 | 方案 A(本提案:DoR 续作项 + 未覆盖细节条款 + 清理口径扩展) | 方案 B:spec 级进度写入 STATUS.md | 方案 C:维持现状 | 方案 D:未覆盖细节一律停下问用户 |
|---|---|---|---|---|
| 成本 | workflow +3 行 + dev-standards 一词 | STATUS 结构变更 + 双写义务 | 零 | 无文本成本,执行流频繁打断 |
| 风险 | 低:读向动作与回填义务,不改既有结构 | 中:与 tasks 交付记录双写,漂移必然 | 高:三个缺口均为会话边界事故形态 | 中:重大歧义与实现细节不分级 |
| 迁移代价 | 零 | STATUS 模板与维护规则改写 | 零 | 零 |
| 可逆性 | 高 | 中 | — | — |

**方案 B(spec 级进度进 STATUS)**:未入选。tasks 交付记录已是该 spec 的进度真相源(勾选 + hash + 交接要点),STATUS 再记一份是双写,两处必然漂移;正确方向是让会话知道「去 tasks 看」,即 DoR 的读向动作,成本一行。

**方案 C(维持现状)**:未入选。三个缺口都发生在会话边界 —— 中断恢复、细节遇缺、数据清理,正是「上下文全部经文档交接」机制最薄弱处;且未覆盖细节的「先写完再补」是被第 3.4 节显式禁止行为的漏网变体,现状规范自相矛盾。

**方案 D(一律停问)**:未入选。AGENTS.md 第 7 节的停问情形是重大歧义与验收冲突;实现细节(兜底写法、辅助函数落点)停问会碎片化打断执行流。「定案 + 回填 + 继续」既留下档痕又保持节奏,触及契约边界的自然落入实质偏离通道,分级已内建。

## 影响与风险

- **workflow.md 约 +3 行,dev-standards.md 一词**:无节号变化,无交叉引用同步。
- **DoR 六项变七项**:核对成本微增;续作项带条件前缀,首次施工会话不适用即跳过。
- **「定案回填再施工」的节奏成本**:每个未覆盖细节多一次一句话回填 —— 这是修复目的本身(档痕),且实质细节被分流到 spec 修订通道,不打断节奏的只有实现细节一级。
- **清理口径扩展的执行面**:原本就要删脚本,数据同理;对「测试数据即生产数据」的只读验证场景,用后即删本就是惯例,不新增负担。

## 迁移与回滚计划

不适用(非破坏性变更):全部为新增条款、新增 DoR 项与两处措辞扩展;回滚 = revert 对应 commit。

## 开放问题

- [x] 未覆盖细节的定案权:推荐实现细节由执行会话定案并回填(档痕可追溯,不打断执行);触及契约 / 边界的走实质偏离通道(那条路本就要求修订 spec)。是否需要「定案后知会用户」的附加动作?→ 无实时知会义务:知会由档痕(tasks 回填、偏差记录)与人工评审 / 收口复查承担 —— 「实现细节」的定义即不影响验收标准的写法选择,实时知会让用户确认不可判定之事,形式主义且打断执行;走私风险由实质偏离通道、拿不准升一级与开工分级声明兜底(2026-09-02 决议)。
- [x] 清理口径扩展是否同步到 dev-standards 调试纪律(§1.4):推荐同步 —— 冒烟与调试两处清理义务一致,只改冒烟侧会造成「调试数据可以残留」的反向解读。→ 同步,§1.4 保留(2026-09-02 决议)。
- [x] 续作定位项放 DoR 还是开工提示词:推荐 DoR(与现状盘点漂移检查并列的核对项);开工提示词是立项会话输出的引导语,不宜承载续作条件动作。→ 落 DoR(2026-09-02 决议)。
