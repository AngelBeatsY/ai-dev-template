## 摘要

维护者会话对根 README 与 AGENTS.md 的审计发现五处入门面与已 Accepted 规范脱节(发现序号见背景节,此处 ② / ③ 指 README「日常使用」块号):README ③ 施工提示词缺「与开工评审」(v2.6.0 同步只落了 workflow.md);README ② 立项链路无 design 环节(设计稿定稿是 spec 转 Active 的前置,workflow 3.2);根 README 目录树残留 RFC-0004 已废除的「设计先行时用」措辞;验收链无独立验收位置(常规级及以上 MUST,R11 合并前置);README ② 把 brief 呈现为无条件必产(spec 来源值域「无(自发)」在提示词层无出口)。逐条溯源发现共性根因:**README 提示词复制规范细节,复制面必漂移** —— 而逐条对照证实提示词内容几乎全部已由系统侧承载,唯二例外是「逐份确认」与「探索方案数」两个交互偏好。本提案据此重设计提示词形态:README 只承载**动作 + 参数**(`立项 <需求一句话>`、`施工 SPEC-NNNN`),读什么文档、做什么判断、守什么顺序全部收口 AGENTS 路由与 workflow;AGENTS 侧补三件系统设施(用户指令动作映射、产出物确认协议、路由行补 design 与 tasks 线索)。第二轮全量审计(流程性文档与模板通读)再发现五处,经维护者决议并入本提案:workflow 3.6 错别字(「合同时」)、structure.md 决策树「设计先行」第二处残留、AGENTS R2 未覆盖设计稿、install.md 场景二删除语义自相矛盾、workflow 3.5「逐层不可省」缺纯个人豁免括注 —— 均为不触条款语义的勘误与系统面补全(1.7-1.11)。第三轮全量审计(全仓流程性与系统提示词性质文本通读)再发现六处,经维护者决议并入:git-workflow 第 4 节合并授权缺纯个人豁免括注(与 E 同族)、structure.md 与 PR 模板两处 verify-docs 检查集括注停在旧版(复述面漂移)、AGENTS 路由「验收 / 评审 PR」行必读缺 tasks(独立验收输入面)、README 给人场景二命令与 install.md 命令不同步、install.md 第 5 步待删章节名与 README 实际章节不对应、README 目录树缺 meta/ 与 manifest.txt 治理文件行 —— 同为不触条款语义的勘误与系统面补全(1.12-1.17)。brief 可选性流程表述收口与规范侧字面勘误(3.3 枚举、6.2 时点、量词统一等)分立 RFC-0022。

## 背景与动机

**五处脱节(第一轮,证据)**:

- **发现一(逐字漂移)**:workflow.md 3.4 开工提示词模板(v2.6.0 起)含「开工就绪核对**与开工评审**」;README ③ 代码块是旧文案,v2.6.0 版本记录「开工提示词同步」只落了 workflow.md。README ③ 标题自称「直接用②输出的开工提示词」,两处复制面彼此也不一致。
- **发现二(design 缺位)**:② 提示词链路「brief、spec、tasks」无 design 位;workflow 3.2 要求设计稿定稿先于 spec Active,3.3 立项交付要求会话结束时 spec 已 Active —— FR 依赖视觉细节的功能照字面走即违规。AGENTS 路由「新功能立项(写 brief/spec/tasks)」同样无 design。
- **发现三(措辞残留)**:RFC-0004 因字面歧义(「设计先行」读成「先于 spec 存在,编号来源无解」)在 structure.md 第 2 节与 docs/README.md 文档地图统一改掉「设计先行时用」,落地清单漏列根 README。
- **发现四(独立验收无位)**:流程主线与 ④ 三个提示词均无独立验收入口;它是常规级以上 MUST(workflow 3.5、R11),纯个人项目豁免人工评审时是唯一补偿性检查。
- **发现五(brief 无条件化)**:② 三处把 brief 呈现为必产;spec-template 来源值域「无(自发)」与 RFC-0011 记录的「spec 常从 RFC 或讨论直接立项」实践在提示词层无出口。

**形态根因**:README 自述「每一步把对应提示词发给 AI 即可」,提示词因此被当成规范细节的载体,逐句复述 workflow 义务 —— 逐条对照显示这些复述几乎全部冗余。复述面一旦存在,规范每次演进都要同步 N 个复述点,v2.6.0 漏面即实证。初稿曾按「逐句对齐」路线起草,起草中确认对齐无法终结漂移,故改为形态重设计:规范细节单点住在系统侧,README 只留动作与参数。

**短形态的前提与兜底**:AGENTS.md 单入口是模板核心理念一,主流工具(Claude Code、Cursor、Copilot)自动加载它,动作词映射放 AGENTS 第 2 节(必读位)即可被识别;不自动加载的工具由 README 一行 fallback 兜底(指令前加「阅读 AGENTS.md」)。

**第二轮审计并入项(A-E,经维护者决议并入)**:

- **A(错别字)**:workflow 3.6 「**合同时** MUST 完成」应为「合并时」—— 恰在收口四动作这一关键段落。
- **B→分立(措辞残留第二处)**:structure.md 第 5 节决策树行「设计先行的项目」与发现三同源(RFC-0004 漏改面);全仓 grep 确认「设计先行」在活文档中共两处(根 README 目录树 + 此处)。
- **C(AGENTS R2 缺设计稿)**:R2「新建 brief/spec/RFC/ADR MUST 从模板复制 + 同 commit 更新注册表」未覆盖设计稿(同为模板实例化的编号流水产物),且「更新注册表」义务对 design 本不适用(不入注册表),例外未写。
- **D(install.md 自相矛盾)**:场景二复制命令明确包含 `install.md`,第 8 步却称「场景二没有本文件」。按文件自身「模板自举文件,使命完成即删」原则,收口为两场景初始化后都删除,联动 README 目录树行与 structure.md 第 2 节 install.md 行的「场景一删除」表述。
- **E(一般条款缺范围)**:workflow 3.5「三层检查……逐层不可省」与同节末「纯个人项目豁免人工评审」并存,一般条款未给自己划范围,入门读者先撞字面冲突。

**第三轮审计并入项(F-K,经维护者决议并入)**:

- **F(git-workflow 合并授权括注缺位)**:第 4 节「合并 MUST 在人工评审通过后(workflow.md 第 3.5 节)经用户当次授权执行」—— 纯个人项目豁免人工评审后该前置字面不可满足,而 3.5 只读纪律段明确验收人经用户当次授权可执行合并;1.9 只括注了 workflow 3.5 内部,git-workflow 这处姊妹面未跟。
- **G(检查集括注过时,两处)**:structure.md 第 2 节 verify-docs.mjs 行括注列 4 项检查、PR 模板自检行括注列 3 项,实际 12 项(脚本头部注释为权威)—— 括注是复述面,v2.3.0 至 v2.7.0 检查演进从未同步;按本提案根因(复制面必漂移)收口为指向脚本头部权威。
- **H(AGENTS 路由验收行缺 tasks)**:独立验收输入是「tasks 交付记录与 spec 验收标准」(workflow 3.5),「验收 / 评审 PR」行必读列只有 workflow 3.5 与对应 spec,验收会话被路由引导跳过交付记录核对与「独立验收」落档节。
- **I(README 给人命令不同步)**:场景二命令复制集(AGENTS.md、.github、docs 三项)与 install.md 场景二命令(另复制 install.md、.gitattributes、.gitignore)已漂移;README 路线装入的项目本地无 install.md,「安装并初始化」两动词分步执行失去载体。
- **J(install.md 第 5 步章节名失配)**:所列待删章节「模板使用」「安装」「初始化」与 README 实际章节名(核心理念、安装与初始化等)不对应,靠「等」字兜底。
- **K(目录树缺治理文件)**:README 目录树以仓库名为根却不列 meta/ 与 manifest.txt,而 install.md 第 8 步、meta/README.md、decisions.md 均引用它们;缺行使仓库全貌缺一角。

## 目标

- README「日常使用」提示词全部改为「动作 + 参数」形态,规范细节不再出现在提示词中。
- AGENTS.md 补三件系统设施(动作映射、确认协议、路由行补 design 与 tasks)并修订 R2 覆盖设计稿;新增约 17 行,当前 99 行(实测),低于 150 上限。
- 流程主线行与目录树行同步既有规范(发现二 / 三 / 四 / 五的信息面)。
- 十二项并入勘误落地(1.7-1.18:第二轮五项、第三轮六项、第五轮一项排版),全部不触条款语义。
- workflow.md / structure.md / git-workflow.md 仅纯勘误触点;PR 模板(.github/)仅 1.13 检查集括注删减一处;docs/ 各流水产物模板(*-template.md)与 verify-docs.mjs 零改动;brief 流程表述收口分立 RFC-0022。

## 非目标

- 不修改任何规范条款的**语义**:五处入门面脱节与十二项并入勘误的目标形态在规范面均已成立;本提案对 workflow.md、structure.md 与 git-workflow.md 的触点限于错别字(1.8)、措辞统一(1.7、1.16)、范围括注(1.9、1.12)、删除语义对齐(1.11)、检查集括注收口(1.13)、标点勘误(1.18),逐项见提案详述。涉及语义的 brief 流程表述收口分立 RFC-0022,不以本提案夹带。
- 不建「规范变更 → 入门面同步」的清单义务或机器检查:重设计后 README 不再复制规范细节,漂移面结构性消失,机制失去对象;按「呈现面 = 核对面」原则(RFC-0019)入门面亦无机器语义可查。
- 不统一各工具的自动加载行为:fallback 一行说明即止,工具适配细节不进模板。
- 不动 workflow 3.4 开工提示词模板本身:它是立项会话 → 施工会话的交接载体,与用户指令形态无关,维持原样(其逐字文本即权威,README 不再复制它)。

## 提案详述

### 1.1 流程主线行(README「日常使用」首行;文档性内容,解决发现二 / 四 / 五的信息面)

现行:

```
流程主线:**立项(分级 → brief → spec → tasks)→ 施工(DoR 核对 → 逐任务)→ 验收(收口复查 → 冒烟 → 评审)→ 合并收口**。小改跳过立项直接修;重大级先 RFC。每一步把对应提示词发给 AI 即可:
```

改为:

```
流程主线:**立项(分级 → brief(自发可免)→ spec → tasks;FR 依赖视觉细节时设计稿定稿先于 spec Active)→ 施工(DoR 核对与开工评审 → 逐任务)→ 验收(收口复查 → 冒烟 → 独立验收 → 评审)→ 合并收口**。小改跳过立项直接修;重大级先 RFC。每步把一句短语发给 AI 即可(见下表):
```

### 1.2 提示词段整体替换(解决发现一 / 二 / 四 / 五的提示词面)

现行六个多行提示词块(① 探索 / ② 立项与重大分支 / ③ 施工 / ④ 三段 / 中断恢复)整体替换为一张动作表:

```markdown
提示词即「动作 + 参数」,读什么文档、做什么判断由 AGENTS.md 路由承担(工具自动加载 AGENTS.md;不自动加载的工具在指令前加「阅读 AGENTS.md」):

| 你想做什么 | 发给 AI |
|---|---|
| 不确定怎么做,先摆方案 | `探索 <问题一句话>` |
| 立项(产出 brief(自发可免)/ spec / tasks 与开工提示词) | `立项 <需求一句话>` |
| 重大级先写提案(AI 判重大后会停下引导) | `起草 RFC <主题一句话>` |
| 按任务清单实施 | `施工 SPEC-NNNN` |
| 独立验收(未参与实现的会话执行) | `验收 SPEC-NNNN` |
| 人工评审 PR | `评审 SPEC-NNNN` |
| 合并后收口回填 | `收口 SPEC-NNNN` |
| 中断后继续 | `继续` |

**小改**:直接说「修 <问题描述>」,AI 自行判级、直接实现,commit 写清缘由,走 PR(分级声明选小改)。
```

规范细节全部退出提示词:探索边界与方案数由动作映射承载,分级声明由既有协议强制,逐份确认由新协议(1.4)承接,开工评审由 workflow 3.4 模板随立项交付输出,独立验收与收口由路由行指向 workflow 3.5/3.6。

### 1.3 AGENTS.md 第 2 节:用户指令动作映射(新增,路由表之前)

```markdown
用户指令按动作词识别(README「日常使用」的短语即此形态),识别后按下方任务类型表加载:

| 动作 | 路由 |
|---|---|
| 立项 <需求> | 「新功能立项」行 |
| 起草 RFC <主题> | workflow.md 第 4 节 |
| 施工 SPEC-NNNN | 「施工 / 改代码」行 |
| 验收 SPEC-NNNN | 「验收 / 评审 PR」行(独立验收角色,workflow.md 3.5) |
| 评审 SPEC-NNNN | 「验收 / 评审 PR」行(人工评审角色,两遍法) |
| 收口 SPEC-NNNN | workflow.md 3.6 节 |
| 探索 <问题> | workflow.md 第 2 节探索(不产正式文档、不改代码,方案 2-3 个) |
| 继续 | 先读 STATUS.md 工作日志最后一条定位进度,再按所在阶段路由 |
```

### 1.4 AGENTS.md 第 3 节:产出物确认协议(新增,分级声明协议之后)

```markdown
**产出物确认协议**:立项产出 brief / spec / tasks 时逐份提请用户确认后再写下一份;与分级声明协议同构,AI 只有建议权,确认权在人。用户在指令中声明连续产出(如「立项 X,一口气出完」)时 MAY 连续产出后一并提请确认,spec 转 Active 前仍 MUST 取得确认(workflow.md 3.2 通过标准不豁免)。
```

原 README 提示词中的「每份给我确认后再写下一份」偏好由此上收系统侧,短提示词不丢交互语义。

### 1.11 install.md 删除语义收口(并入 D;三处联动)

按「模板自举文件,使命完成即删」原则收口为两场景初始化后都删除 install.md:

- **install.md 第 8 步**,现行「场景一的项目删除本文件(install.md)与 `meta/`、`manifest.txt`(三者均为模板自举文件,使命完成即删;删除 `meta/` 与 `manifest.txt` 与删本文件是同一步)。场景二没有本文件与 meta/,跳过。」改为:「删除本文件(install.md);场景一同时删除 `meta/` 与 `manifest.txt`(同为模板自举文件)。场景二未复制过 `meta/` 与 `manifest.txt`,无此步。建议提交:`chore: initialize from ai-dev-template`(此句为原文保留)。」
- **README 目录树 install.md 行**:「(场景一项目初始化后删除)」→「(初始化完成后删除)」。
- **structure.md 第 2 节 install.md 行**:「场景一项目初始化完成后删除」→「初始化完成后删除」。

理由:install.md 必须在场景二留存到初始化时点(支持「安装」「初始化」两动词分步执行),但初始化完成后留存即垃圾(后续会话可能误读其自举指令);「使命完成即删」是文件自述原则,场景二不应例外。

## 影响与风险

- **verify-docs**:零改动零影响(无新增链接目标;AGENTS.md 行数实测低于上限)。
