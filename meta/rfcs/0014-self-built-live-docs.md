## 摘要

模板明文允许自建目录(structure.md 第 5 节决策树:docs/deploy/、docs/design/、docs/plan/),其内容按第 3 节判据属活文档类;但全部更新义务与门禁只为四类对象设防(注册表、STATUS.md、tech/ 三件套、spec),自建活文档落在所有防线之外。某下游项目自建 docs/plan/(roadmap + milestones)后,两次批量交付合并当天 milestones 对应条目漏勾,次日人工盘点「随盘发现」才补平,第二次补漏又漏掉 roadmap 两条已交付项至今未勾 —— 机制必然而非纪律偶发:逐关核对(DoD 第 4 条、TF1、workflow.md 3.6、PR 自检、verify-docs)均不覆盖计划文档,没有任何角色有勾选义务。本提案三件捆绑:① workflow.md 第 6 节新增自建活文档登记与维护义务(6.3),载体是 docs/README.md 新增「自建活文档清单」(decisions.md 第 3 节 tech/ 行预设的「项目 README 自建清单」由此兑现);② DoD 第 4 条 / TF1 / PR 自检枚举泛化接线(「登记的自建活文档如有」);③ verify-docs 新增检查 8 双向兜底(登记→存在、存在→登记,登记即合法),`--template` 模式新增检查 9 兜 meta/rfcs 注册表登记(模板仓自查实测漏登 RFC-0013,同机制在本仓复现)。勾选状态与交付的一致性不做机器强制(语义映射,机器无从建立),由枚举泛化在合入前以人在场提醒承担。

## 背景与动机

### 下游漂移实例(实测,泛化表述)

某下游项目按决策树自建 docs/plan/(roadmap.md + milestones.md)。三个功能交付并合并进主分支当天,milestones 对应条目漏勾;次日人工盘点发现后补平,同一次补漏又漏掉 roadmap,两条已交付项至今未勾。两次漂移全部靠人工盘点触发,无任何机制报警;第二次补漏本身再漏,说明没有清单兜底的人工补漏同样不可靠。

放大因素:STATUS 会话协议(6.2)很强,部分替代了进度记录职能,自建计划文档进一步「想不起来」;计划文档是交接链一环 —— STATUS「下一步」与 DoR 开工核对依赖账面口径,账面失真则开工判断失真。

### 模板仓自身同机制复现

meta/rfcs/ 的 RFC 注册表(meta/README.md)漏登 RFC-0013(文件已创建、git 已记录 Accepted,注册表无该行)。检查 6 对 docs/README.md research 清单有「漏登即失败」兜底,meta/rfcs 注册表无对应物(verify-docs `--template` 模式只查 manifest 路径存在性与根目录白名单,不查注册表完整性)—— 同一机制(人工维护清单、无兜底)在维护者自己身上、在本 RFC 讨论期间发生。

### 逐关核对(均不覆盖自建活文档)

| 关卡 | 位置 | 现状 |
|---|---|---|
| DoD 第 4 条「相关文档已同步」 | dev-standards.md 第 10 节 | 枚举仅 tech-stack.md / architecture.md / 受影响的 spec |
| tasks 固定收尾 TF1 / TF2 | tasks-template.md | TF1 同上枚举;TF2 仅注册表 |
| merge MUST 完成 | workflow.md 第 3.6 节 | tasks 勾选 + spec 转 Implemented + 注册表 + RFC 回填,不含计划文档 |
| PR 模板提交者自检 | PULL_REQUEST_TEMPLATE.md | 「相关文档已同步」为泛指,无枚举无核对点 |
| verify-docs 检查 6 | research 清单登记 | 自建目录的清单登记无对应检查 |

### 预设悬空

decisions.md 第 3 节 tech/ 增补行的「未采用」列写明:动态清单不延伸覆盖自建目录,理由是「自建目录自治,**登记义务由项目 README 自建清单承担**」—— 该清单从未被建出来,预设停留在字面。本 RFC 补建之,属兑现既有决策而非新增机制。

## 目标

- 自建活文档有登记义务与登记载体:docs/README.md「自建活文档清单」,登记时点与 6.1/6.2 对齐(与文件创建同一 commit)。
- 收尾路径接线:DoD 第 4 条、TF1、PR 自检的枚举覆盖「登记的自建活文档(如有)」。
- 机器兜底:检查 8 双向校验(登记的路径存在 + 存在的活文档已登记);检查 9(`--template`)兜 meta/rfcs 注册表。
- 无自建目录的项目零增量(枚举带「如有」,检查 8 空载)。

## 非目标

- 不做勾选状态与交付一致性的机器强制:「PR 合入对应 roadmap 哪条目」是语义映射,机器无从建立;自动勾选会勾错,假绿比漏勾更危险。合入前核对由 TF1 枚举泛化以人在场提醒承担。
- 不改 tech/ 增补机制(testing.md 走 tech-stack.md「项目惯用法」声明 + `--strict` 活文档清单动态收集,先例机制不动,避免双查)。
- 不改编号设计稿的不入注册表规则(RFC-0004:由来源 spec「接口设计」节链接检索;仅改 5.1 中持久参考活文档「不入注册表」的表述)。
- 不在 tasks-template 增设独立收尾任务(对无自建目录的项目是纯噪音,枚举泛化足以承载)。
- 不设固定目录词汇清单(docs/plan/、docs/deploy/ 等):「自建」意味着目录名开放,固定词汇把本次要修的枚举盲区原样搬进机器检查,且与 design/ 既有规则冲突、对存量项目批量误报。
- AGENTS.md 零改动:R5 的权威版本指向 dev-standards.md 第 10 节,泛化在规范内部完成,不挤占 150 行上限。

## 提案详述

### 1.1 workflow.md 第 6 节新增 6.3(6.2 之后)

```
### 6.3 自建活文档(deploy/design/plan 等自建目录)

按 [structure.md](structure.md) 第 5 节决策树自建的目录,其内容属活文档类(structure.md 第 3 节判据),登记与维护义务:

| 时点 | 动作 |
|---|---|
| 创建自建目录或其中文件时 | 在 docs/README.md「自建活文档清单」登记一行(与文件创建同一 commit) |
| 任务完成 / PR 合入时 | 更新受影响条目(时点对齐 6.1 / 6.2) |
| PR 合入时 | 核对清单与实际文件一致 |

清单不审内容,登记即合法(docs/ 下活文档进入体系的唯一通道);漏登视为未完成(对称 research 清单,verify-docs 检查 8 双向校验)。条目勾选状态与交付的一致性不做机器强制,由 tasks 收尾任务 TF1 在合入前核对。
```

### 1.2 dev-standards.md DoD 第 4 条(泛化)

```
4. 相关文档已同步:tech-stack.md(新增依赖/命令/惯例)、architecture.md(结构变化)、受影响的 spec,以及 docs/README.md「自建活文档清单」中受影响的条目(如有)。
```

### 1.3 tasks-template.md TF1(泛化)

```
- [ ] **TF1**:更新相关文档(tech-stack.md / architecture.md / 受影响的 spec;登记的自建活文档如有)
```

### 1.4 PULL_REQUEST_TEMPLATE.md 提交者自检对应项(同步泛化)

```
- [ ] 相关文档已同步(tech-stack.md / architecture.md / 受影响的 spec;登记的自建活文档如有)
```

### 1.5 docs/README.md 新增「自建活文档清单」节(research 文件清单之后、阅读矩阵之前)

```
## 自建活文档清单

按 [conventions/structure.md](conventions/structure.md) 第 5 节决策树自建的目录(docs/deploy/、docs/design/、docs/plan/ 等)中的活文档,每份 MUST 在本表登记一行(与文件创建同一 commit,义务见 [conventions/workflow.md](conventions/workflow.md) 6.3)—— 登记即合法,漏登视为未完成(verify-docs 双向校验)。

|---|---|
| (示例行,首次使用时删除)plan/roadmap.md | 版本路线:已交付项随 merge 勾选 |
```

```
自建目录(docs/deploy/、docs/design/、docs/plan/)中的活文档 MUST 在 docs/README.md 自建活文档清单登记(与文件创建同一 commit),维护义务见 [workflow.md](workflow.md) 第 6.3 节。
```


### 1.7 verify-docs.mjs 检查 8:自建活文档登记(默认模式)

双向校验,对称检查 6 的结构(`checkResearchRegistry` 镜像):

- **方向 1(登记→存在)**:docs/README.md「自建活文档清单」节范围内逐表格行提取第一列路径(相对 docs/,过滤「示例行」),路径必须存在;失败消息:`清单登记的文件不存在:plan/roadmap.md(删除该行或修正路径,docs/README.md 自建活文档清单)`。
- **方向 2(存在→登记)**:扫描 docs/ 下对象集,未登记即失败;失败消息:`自建活文档未登记:docs/plan/roadmap.md(登记到 docs/README.md 自建活文档清单,义务见 workflow.md 6.3)` —— 失败消息必须含可直接执行的修复动作,修复成本 < 忽略成本。

对象集与排除集(与 structure.md 第 2 节目录表同源,模板未来新增固定目录时同步):

| 对象 | 处理 |
|---|---|
| docs/ 顶层固定文件(STATUS.md、README.md、decisions.md) | 不查 |
| 固定子目录 briefs/specs/rfcs/adr | 不查(编号产物归四张注册表;检查 7 管命名) |
| design/ | **仅查顶层**(对称检查 7 口径):编号文件与 -template 不查;无编号非 template .md 须登记(5.1 改口后的持久参考;assets/ 归 5.1 资产清单约束) |
| research/ | 不查(检查 6 管辖,证据目录另有结构豁免) |
| tech/ | 不查(liveDocPaths 管辖,登记载体是 tech-stack.md 声明,不双查) |
| conventions/、archive/ | 不查(规范类 / 已归档产物) |
| 自建目录(固定集合之外的目录)内全部 .md、docs/ 顶层散 .md | 须登记(登记即合法,不做格式判断,单一职责) |

清单解析采用**节内表格提取**而非全局正则:README 中 md 路径引用遍布各节,全局匹配任意 `.md` 路径必误伤(检查 6 可全局是因为 `research/` 前缀唯一)。

### 1.8 verify-docs.mjs 检查 9:meta/rfcs 注册表登记(仅 `--template` 模式)

meta/ 不随模板分发,该检查挂 `when: isTemplate`(与检查 5 同模式),对下游零成本:

- meta/rfcs/ 下每份 `NNNN-*.md` 必须在 meta/README.md RFC 注册表登记一行(按编号匹配),注册表链接路径必须存在;失败消息对称检查 6/8,含修复动作。
- 头部注释检查项清单追加 8/9 两项说明,CHECKS 数组加两行;检查编号 [1]-[9] 即输出顺序,[9] 仅 `--template` 运行。

### 配套修改(落地时同步)

- **docs/decisions.md** 第 3 节机制设计加行(登记义务 + 枚举泛化 + 双向兜底捆绑;四项未采用备选留痕,见备选方案节)。
- **meta/README.md**:RFC 注册表加行(随本 RFC 同一 commit);落地 commit 内一并补登漏掉的 RFC-0013 行。
- **根 README**:模板版本 v2.2.0 条目(minor:纯新增义务与检查,无自建目录的项目不受影响)。
- **docs/STATUS.md**:零改动(分发模板文件,保持未初始化占位;模板自身变更记录的载体是根 README 模板版本节与 meta/ 治理档案,模板仓不按 6.2 记开发日志 —— 起草时此行为误判,落地执行时修正)。
- manifest.txt 零改动(分发面文件集合不变,均为已登记文件的内容修改)。

## 备选方案

| 维度 | 方案 A(本提案:义务 + 接线 + 兜底捆绑) | 方案 B:仅枚举泛化与义务条款 | 方案 C:仅机器兜底 | 维持现状 |
|---|---|---|---|---|
| 成本 | 一次性实现约半天;下游登记一份一行 | 最小(纯措辞改动) | 脚本 + README 新节 | 零(人工盘点买单) |
| 拦「过期」(文件在、条目漏勾) | TF1/DoD 枚举在合入前拦截 | 同 A(其全部收益所在) | 不拦截 | 不拦截 |
| 拦「失踪」(文件/清单不完整) | CI 当场 | 无(登记义务无人核对) | CI 当场 | 不拦截 |
| 首因环节(登记) | 有兜底 | 漏洞:目录自建不经收尾任务,清单可为空 | 有兜底 | 盲区全开 |
| 可逆性 | 高(删检查与条款即回退) | 高 | 高 | — |

**方案 B** 未入选:登记发生在「目录自建那一刻」,通常是任意会话的小改,不经过任何收尾任务 —— 首因环节无兜底,TF1 泛化扫到的清单可能从未建立,防线从第一天是开的;且登记写 MUST 而无核对点,违反模板「每条 MUST 有承载」的既有风格(DoR / TF / PR 自检 / verify-docs 四种承载之一)。

**方案 C** 未入选:下游实测漂移形态是「过期」(文件在、条目漏勾)而非「失踪」;C 拦失踪不拦过期,修不了已发生的病灶。A/B 与 C 是互补关系不是替代关系 —— 过期靠枚举泛化的人在在场提醒,失踪靠 CI,各管一段。

**方案 D:计划职能并入 STATUS.md(不设 docs/plan/)** 未入选:只消解 plan,deploy/design 不适用,不完整;STATUS 是「现在」的快照,roadmap 需跨季度时间线,粒度与受众不匹配;强制合并是收窄决策树能力,塞不下会逼出「另建文件」的地下行为,回到更糟的盲区。

**维持现状** 未入选:五道关卡全盲是机制必然(非纪律偶发),人工盘点已实证不可靠(补漏再漏);decisions.md 预设的「README 自建清单」悬空未建,现状连既有决策都未兑现;同机制已在模板仓自身复现(RFC-0013 注册表漏登)。

## 影响与风险

- **模板仓库自身**:检查 8 在模板仓当前空载(docs/ 无自建目录,示例行过滤;模板仓自身自建目录时同样须登记),零行为变化;检查 9 首跑即暴露 meta/rfcs 注册表漏登(RFC-0013)—— 落地 commit 内补登,验证口径覆盖。
- **下游存量项目**:升级后检查 8 首跑可能报「未登记」—— 预期对账动作而非破坏(每份登记一行,失败消息含修复动作);无自建目录的项目零动作。
- **误报风险**:「存在→登记」的排除集是白名单逻辑,模板未来新增固定目录时须同步排除集 —— 缓解:排除集与 structure.md 第 2 节目录表同源并在脚本头部注释注明联动;「登记即合法」是最终逃生阀,任何正当文件登记一行即合法,不引入第二机制(豁免注释等,RFC-0010 教训:豁免逻辑越少越好)。
- **狼来了风险**:检查 8/9 只报「可一行修复」的问题,无灰区;失败消息带动作,修复成本 < 忽略成本。
- **预期管理**:防线效果是发现时点前移(人工盘点 T+1 → 合入前 + CI 当场)与漂移面收窄,不是零漂移 —— 勾选一致性的语义判断仍依赖 TF1 在场核对。
- **认知成本**:执行 AI 多读一个枚举项(「如有」零噪音);规范体量 +1 小节(6.3 一表一义务一时点,引用不复述)。

## 迁移与回滚计划

非破坏性变更:文件格式、目录结构、既有检查语义全部不变,纯新增义务与检查。回滚 = 还原各文件条款文本、删除检查 8/9 与 README 清单节;曾被要求登记的文件回到无义务状态,无数据迁移。下游迁移:存量自建目录项目按失败消息逐条登记(一次性);无强制时点,按各自升级节奏 cherry-pick(README FAQ 升级惯例)。

**验证口径**:① 模板仓库默认与 `--template` 双模式全绿(meta/rfcs 补登后);② 临时构造 docs/plan/roadmap.md 未登记 → 检查 8 报「未登记」且消息含修复动作;登记后 → 全绿;登记行指向不存在路径 → 报「不存在」;清理复原;③ design/ 下临时构造无编号 md 未登记 → 检查 8 报,编号 md 不报;tech/ 下构造 testing.md → 检查 8 不报(不双查);清理复原;④ meta/rfcs 临时新增未登记文件 → `--template` 模式报,默认模式不报;清理复原;⑤ 全部失败消息含可执行修复动作(人工过目)。

## 开放问题

- [x] 机器识别源选哪个:README 清单 / tech-stack 声明 / 固定目录词汇?→ docs/README.md 自建清单,一源两用(义务载体兼解析源,对称检查 6):固定词汇重演枚举盲区且与 5.1 冲突、对存量批量误报;tech-stack 是代码侧语义位且自由文本机器可读性差(2026-09-04 起草时定)。
