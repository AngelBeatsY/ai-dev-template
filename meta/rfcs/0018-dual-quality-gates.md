## 摘要

体系存在两处结构同型的「自报链」:spec 层 —— workflow.md 第 3.2 节评审清单的通过判定人没有独立于作者(spec 负责人撰写并自查,AI 代笔时撰写与评审同会话),而 spec 缺陷是最高成本级:实现建立在错误基准上,出口的独立验收以 spec 为验收基准,基准错则验收通过「正确实现的错误产物」;实现层 —— 第 3.5 节双检制的 AI 自检由实现会话执行,同一上下文既产生声明又验证声明,核对的是「记忆中的产物」而非产物本身,声明与产物脱节、幻觉产物、编造交付记录、自证测试等 AI 高发失效模式恰是同上下文检查结构性查不出的,且交付记录 hash 无来源纪律;人工评审两遍法是体系唯一独立眼,README FAQ「纯个人项目」条豁免后归零(本仓 meta RFC 治理实践即长期运行在豁免态)。本提案以两道门断链,机制形态已由双线索在下游独立验证:某下游项目实践分域独立验收(未参与施工的主体执行,输入为从计划文档交付记录提取的声明点清单,逐条附 `file:line` 证据,结论分级 PASS/PARTIAL/FAIL,复跑门禁、实测核对 hash,缺陷分级 MED/LOW/OBS 附触发路径,只读不修复);维护者本人的会话编排习惯(立项会话产出 spec/tasks → 新会话施工 → 施工自查 → 回立项会话验收 → 授权合并)与之同构收敛 —— 独立性来自「没写代码的主体拿着意图清单核对产物」,不来自特定工具。① 开工评审:第 3.4 节 DoR 从形式核对升级为读者视角的正确性与可实施性评审(现状盘点证据抽查、FR 无矛盾、ER 覆盖、FR↔任务映射),结论逐项落档 tasks 新增「开工评审」节,实质问题修订 spec 后方可开工(R1 的「就绪」收紧为此定义);② 独立验收:第 3.5 节在实现方自检与人工评审之间新增独立层 —— 未参与实现的主体执行,不信任施工自报(测试与 lint MUST 复跑、hash 以 git 实测核对)、逐条声明点附证据下 PASS/PARTIAL/FAIL、只读纪律与缺陷分级、结论落档 tasks 新增「独立验收」节,常规级及以上为请求合并的前置;纯个人项目豁免人工评审时为补偿性检查、不在可调参数放宽范围。配套:dev-standards.md 第 5 节自证测试判据、执行协议 hash 来源纪律、AGENTS.md R1 修订与新增 R11、PR 模板两处、可调参数拨盘一行。载体无关:本提案规定角色与纪律,不规定实现工具 —— 会话编排或独立代理均可,不随模板分发任何代理配置(decisions.md 第 4 节「subagent 派发不进模板」的既定边界不触碰)。补充范围以「独立验收三条件」的交集筛选(产物是下游基准、自检存在结构性盲区、人工评审缺位),非目标节逐环节记录不补理由。

## 背景与动机

**证据一(spec 层自报链,形式核对冒充正确性评审)**:workflow.md 第 3.2 节评审清单(FR 可测、现状盘点有证据、ER 显式列举)的执行人是 spec 负责人本人;第 7 节角色职责表的 spec 评审人列在单人项目即作者。第 3.4 节 DoR(开工就绪)虽由施工会话执行,但七项核对全部是形式与存在性核对(状态值、证据字段在不在、任务带没带验收点、登记在不在、测试跑不跑得通):「spec 每条 FR/ER 可判对错;现状盘点有证据」核对的是字段存在,不是证据属实;FR 内部矛盾、ER 覆盖缺口、任务拆分拼不出 FR,均不在核对深度内;核对结论无输出载体,发现问题的唯一出口是「停下报告」。spec 缺陷的代价结构最差:开工前发现 = 修订一次文档;施工中发现 = 返工 + spec 修订;验收中发现 = 最贵,且常发现不了(验收以 spec 为基准)。

**证据二(实现层自检自报 + 唯一独立眼单点)**:第 3.5 节双检制中 AI 自检由实现会话按 PR 模板清单核对 —— 同一上下文产生的记忆会替代对产物的核对。交付记录要求回填 commit hash 与测试结果,hash 无来源纪律(凭记忆构造无条款拦截)。人工评审两遍法是体系唯一独立检查,README FAQ「纯个人项目」条豁免后归零 —— 本仓自身治理(meta RFC 系列)即运行在豁免态;豁免的初衷是降低流程成本,代价是质量保证完全落在自检上。

**证据三(下游双线索验证)**:某下游项目实践了分域独立验收(载体为三张只读验收卡,按数据 / 业务逻辑 / 前端分域并行),并与机械回填代理分工(验收判断与账本回填分离);维护者本人在下游的会话编排习惯与之同构。两条线索独立收敛于同一机制形态,验证了可行性与成本量级。模板吸收的是会话无关的角色协议与纪律;工具载体(代理卡、模型路由、并发编排、机械回填代理)属实例配置,不进模板 —— 与 decisions.md 第 4 节「git worktree、subagent 派发」不采纳条的边界一致:该条拒绝的是工具技巧条款,本提案是协作契约(角色义务与合并前置条件)。

## 目标

- 断开 spec 层自报链:施工会话开工前以读者视角完成正确性与可实施性评审,结论落档;实质问题修订 spec 后方可开工。
- 断开实现层自报链:常规级及以上任务合并前经独立验收 —— 未参与实现的主体、不信任自报、证据分级结论、只读纪律。
- 补两条纪律缺口:交付记录 hash 来源纪律;自证测试判据(测试锚定被测行为)。
- 纯个人项目豁免人工评审时,独立验收 MUST 保留为补偿性检查。
- 全部结论有落档载体(tasks 新增两节),义务有核对点承载(吸收 RFC-0014 的教训:无核对点的 MUST 必然漂移)。

## 非目标

补充范围按「独立验收三条件」筛选:① 产物是后续环节的基准,错误会被放大;② 生产者自检存在结构性盲区(同会话既生产又验证);③ 人工评审不在场或被豁免。三条同时成立才值得设独立验收。体系的验收覆盖本分三层 —— verify-docs 机器门禁管结构面、清单与自查管流程面、人工评审与决议管语义面,缺口集中在第三层;本提案只补第三层中被三条件筛出的环节(spec / tasks、实现 / 测试 / 账本),其余环节逐类记录不补理由,避免覆盖面被当作遗漏重复提案:

- 不吸收工具载体:不分发代理配置、模型路由、并发编排、机械回填代理;载体(立项会话 / 新会话 / 独立代理)由实例自选。
- 不新增 verify-docs 机器检查:开工评审与独立验收是过程纪律,静态工具无执行视图,不可校验;兜底由落档义务 + PR 自检勾选 + 人工评审监督承担(与 RFC-0014 机器兜底的分野:那是文档结构事实,可静态判定)。
- 不改变人工评审的职责与豁免规则:团队项目中人工评审照旧(独立验收是其前置输入);豁免规则仍归 README FAQ。
- 不约束小改级:小改无 spec/tasks,开工评审不适用;独立验收豁免(自检 + 授权即可)。
- 不回溯存量:在途 spec/tasks 不强制补做开工评审;独立验收自落地后的下一次验收起适用。
- 不为 brief 补验收:止损点近 —— brief 的错误在 spec 阶段即被纠正,淘汰成本低;第 7 节角色表 brief 行无评审人是既有设计而非遗漏。
- 不为 design 补验收:定稿即 spec 转 Active 的前置,视觉判断权本质在用户,AI 独立验收无位;实现偏离由实现回标两级处理兜住。
- 不为 RFC / ADR 补验收:产物是「决定」,决定权在人 —— 单人豁免评审的实质是人自己审,属授权权在人的固有属性而非自检盲区;ADR 另有复核人与 append-only 约束。
- 不为 research 补产出门禁:验证后置到消费时点更经济 —— 调研大部分内容不被引用,全量门禁是浪费;防线由 spec 引用时立项侧核对、开工评审证据抽查与独立验收出口承担。
- 不为 STATUS.md 与过程产物补语义验收:STATUS 止损即时 —— 任何会话开始先读它恢复上下文,漂移在下一个消费点即暴露,纠错成本低;注册表与自建活文档登记已有 verify-docs 机器双向核对(检查 6 / 8 / 9);commit / PR 文本由提交自查、PR 模板必填项与评审「规范符合性」覆盖;分级声明、开工提示词等过程产物以用户在场确认为门。
- 不为 verify-docs 自身补自动化回归:历次 RFC 落地的「验证口径」手工回归已成惯例(RFC-0017 六条先例),检查项变更稀疏,脚本化的维护成本现阶段高于收益;出现回归事故再立项。

## 提案详述

### 1.1 workflow.md 第 3.4 节:DoR 升级为「开工就绪 + 开工评审」

原 DoR 七项中第 2 项(「spec 每条 FR/ER 可判对错;现状盘点有证据」)并入开工评审深化,其余六项不动。DoR 块之后新增:

```text
**开工评审**(常规级及以上;施工会话以读者视角对 spec 与 tasks 做一遍正确性与
可实施性评审,结论记入 tasks「开工评审」节,续作会话不重填):

- 现状盘点证据抽查:覆盖每条 FR 依赖的现状至少抽查一条,亲眼核对 file:line 或
  research/ 落档结论与 spec 记载一致 —— 证据字段存在不等于证据属实。
- 正确性:FR 之间无矛盾;ER 覆盖主要错误路径,无「异常情况酌情处理」类表述;
  每条验收标准可判对错。
- 可实施性:每条 FR/ER 映射至少一个任务;Phase 依赖顺序成立;测试任务在列。
- 结论逐项落档:通过 / 疑义(写明问题与涉及条目)。疑义按 AGENTS.md 第 7 节停下
  询问;实质问题(契约矛盾、验收标准不可测、现状盘点失实)MUST 修订 spec 后复核
  再开工 —— 就绪以开工评审通过为准(AGENTS.md R1)。
```

开工提示词模板同步改为:「先完成 workflow.md 第 3.4 节的开工就绪核对与开工评审(含现状盘点漂移检查),再开始第一个任务。」

### 1.2 workflow.md 第 3.5 节:新增独立验收层

插入位置:实现方自检类条款(自检 / 冒烟 / 收口复查)之后、「人工评审两遍法」之前。首行「双检制」表述改为「实现方自检 + 独立验收(常规级及以上) + 人工评审」三层,豁免语义不变;新增条款:

```text
- **独立验收**(常规级及以上;小改豁免):由未参与本任务实现的主体(验收人)对
  交付物做独立核对 —— 立项会话、新开会话、独立代理均可担任,载体自选;实现者
  MUST NOT 自任验收人。
  - 输入:声明点清单,从 tasks 交付记录与 spec 验收标准提取;未随验收请求提供时
    验收人自取,报告注明来源。
  - 不信任施工自报:测试与 lint MUST 复跑并记录结果;交付记录中的 commit hash 以
    git log / git show 实测核对;冒烟关键链路 MAY 抽验。
  - 逐条核对附证据:每条声明点给 file:line 或实测输出,结论分级 PASS / PARTIAL /
    FAIL —— PARTIAL 表示证据不足,写明缺口;禁止凭印象下 PASS。
  - 只读纪律(至结论落档):验收过程中验收人不修改代码,只执行只读命令,不
    commit、不 push;缺陷分级 MED(阻塞合并)/ LOW / OBS(观察记录),附触发路径
    或反例,回实现方修复后复验,验收人不自行修复。结论落档后验收即完成,验收人
    经用户当次授权执行合并与后续 git 动作,与任意会话同权 —— 只读纪律的目的
    (不污染验证过程)随结论落档完成使命,合并归既有授权模型管。
  - 结论落档:结论表记入 tasks「独立验收」节,作为人工评审的输入;验收通过前不得
    请求合并。
  - 验收对照修订后的 spec(实现期实质偏离已按第 3.4 节修订);发现 spec 自身缺陷时
    停下按修订流程处理,不以实现迁就 spec。
  - 团队项目中独立验收不替代人工评审,是其前置;纯个人项目豁免人工评审时,本条为
    补偿性检查,不在可调参数放宽范围。
```

### 1.3 tasks 模板:新增两节

「开工评审」节置于字段表之后、「任务清单」之前;「独立验收」节置于「Spec 自检表」之后 —— 与实现方的自检表对称(同为结论表,填写者不同)。

```text
## 开工评审

<!-- 施工会话开工前填写(workflow.md 第 3.4 节)。全部通过写「通过」;有疑义逐条
列出。续作会话不重填。 -->

- DoR 核对:<通过 / 不满足项>
- 证据抽查:<抽查的声明点与核对结果(file:line)>
- 正确性与可实施性:<结论>
- 疑义清单:<无 / 逐条:问题、涉及条目、处置>

## 独立验收

<!-- 验收人填写(workflow.md 第 3.5 节);常规级及以上必做,小改删除本节。 -->

| # | 声明点 | 结论(PASS/PARTIAL/FAIL) | 证据(file:line / 实测输出) | 备注 |
|---|---|---|---|---|

- 复跑记录:<测试与 lint 复跑结果;交付记录 hash 实测核对结果>
- 缺陷清单:<无 / MED / LOW / OBS 逐条,含触发路径>
```

### 1.4 dev-standards.md 第 5 节:自证测试判据

测试策略追加一条:

```text
- 测试 MUST 锚定被测行为:破坏或替换被测实现时测试 MUST 变红;由测试自建对象、
  仅验证自身设定的自证测试不算覆盖。
```

### 1.5 workflow.md 第 3.4 节执行协议:hash 来源纪律

执行协议「交付记录」条追加一句:

```text
交付记录中的 commit hash MUST 取自 git 实际输出(git rev-parse / git log)或用户
提供的值,禁止凭记忆构造;无法取得时留空并注明,不猜测填充。
```

### 1.6 配套修改

- **AGENTS.md**:R1 修订 ——「spec 与 tasks 就绪前不写实现代码」后追加「(就绪即第 3.4 节开工评审通过)」;新增 R11「常规级及以上任务,独立验收通过并落档前不得请求合并;独立验收人 MUST NOT 参与本任务实现」;第 5 节摘要追加一行「常规级以上:开工评审与独立验收结论落档 tasks,验收人不参与实现,测试与 lint 以复跑为准」;头部「最后更新」随落地更新(98 → 约 101 行,低于 150 行上限)。
- **workflow.md 第 7 节**:角色职责表 review 行「实现者」列改为「AI 自检;独立验收(未参与实现的主体)」。
- **workflow.md 第 8 节**:可调参数加一行「独立验收适用范围 | 常规级及以上(小改豁免) | 团队项目 MAY 放宽至仅重大级(人工评审在位时);纯个人项目豁免人工评审的,常规级以上独立验收 MUST 保留,不在放宽范围」。
- **workflow.md 第 3.6 节**:「合同时 MUST 完成」的回填时序条款化 —— 收口回填(tasks 尾勾、spec 状态转 Implemented、注册表、RFC 决议回填)以 PR 尾部 docs commit 随分支合入,合并由 AI 会话执行或人在平台侧执行均适用;PR 已合入后发现回填遗漏,以新分支 docs PR 补救(小改流程)。回填的角色归属不变(第 7 节角色表:实现者勾选 tasks、spec 负责人更新状态),与合并执行者解耦。
- **git-workflow.md 第 5 节**:合并后清理条追加半句 —— 合并由人在平台侧执行时,后续会话在下次开工核对(DoR)前先同步本地主分支、清理已合并的本地分支。
- **.github/PULL_REQUEST_TEMPLATE.md**:提交者自检追加「常规级以上:独立验收已通过,结论落档 tasks『独立验收』节(小改不适用)」;评审者清单「测试充分性」条追加「无自证测试(Fake 自建自验)」。
- **docs/decisions.md**:第 3 节机制设计加行(双门 + 判据 + hash 纪律;理由与未采用备选见备选方案节)。
- **根 README**:FAQ「纯个人项目」条追加「常规级以上任务的独立验收不随评审豁免而省略,它是被豁免的人工评审的补偿性检查」;模板版本条目 v2.6.0(落地时)。
- **meta/README.md**:RFC 注册表加行(与本 RFC 同一 commit)。

| 可逆性 | 高(删条还原,已落档结论表留存不失效) | 高 | 高 | — |

**方案 B(独立会话承担 spec 评审与实现验收)**:未入选。spec 层的全量上下文重建买不来对等收益 —— 独立评审人的发现最终仍需施工会话再读一遍消化,而「能否照着做」的最佳裁判就是即将照着做的人,其困惑本身即测试信号;独立性预算集中在实现层(独立验收)已覆盖最贵的失效面。spec 层的强对抗性评审需求由重大级既有的 RFC 评审(≥2 名评审人)承担。
**方案 C(仅做独立验收)**:未入选。出口门管不了入口货 —— 独立验收以 spec 为基准,基准错误时验收通过的是正确实现的错误产物;开工评审以近零边际成本封住最贵的缺陷类别,砍掉它省下的钱买回最贵的风险。
**维持现状**:未入选。spec 层撰写即评审、实现层自检自报、豁免态零独立眼的三重缺口不因不立项而消失;下游双线索已验证机制可行,不吸收的机会成本是同类缺陷继续由人工评审单点(或无人)承担。

## 影响与风险

- **每任务线性成本(token 与时间)**:验收人需重读 spec/tasks、复跑门禁、读 diff。缓解:载体自由(立项会话兼任验收时 spec/tasks 上下文已热,重建成本最低);小改豁免;第 8 节拨盘(团队)。
- **关键路径变长**:验收插在实现与合并之间,缺陷回修 + 复验是一轮会话往返。缓解:开工评审前置减少中途返工与验收期缺陷;缺陷分级使 OBS / LOW 不阻塞;MED 显式定义为阻塞合并,避免争议。
- **验收员误判与同源模型相关失效(如实声明)**:验收员也是 AI,存在 false pass(走过场)与 false fail(误判缺陷制造无谓循环);实施与验收同源模型时存在系统性误读相关 —— 本机制降低的是自检盲区的重叠概率,不是归零。缓解:证据纪律(file:line + 复跑)压缩走过场空间;结论落档可追溯,人工评审对验收报告有复核位;验收对照产物而非对照实现者陈述,切断主要相关源。
- **规范复杂度**:五处文件改动 + 一个新角色,学习成本一次性。缓解:条款集中在 workflow.md 两节与 tasks 模板两节;AGENTS.md 只进 R1 半句、R11 一条、摘要一行(98 → 约 101 行,余量充足)。
- **角色边界争议(团队)**:独立验收与人工评审职责重叠,可能「都以为对方看了」。缓解:分工条款化 —— 验收管「实现与 spec 对应性 + 自报核验」并出证据表;人工评审两遍法照旧(正确性复核 + 可维护性),输入从裸 diff 变为带验收报告。
- **仪式化风险**:价值按抓到的缺陷计、成本按任务计,长期零发现则退化为纯开销 —— 这是所有验收机制的通病。缓解:第 8 节拨盘是团队场景的显式出口;纯个人豁免态的补偿性验收不在放宽范围,该场景下机制的价值前提(零独立眼)不随时间变化。
- **与 decisions.md 第 4 节的一致性**:「subagent 派发」不采纳条拒绝的是工具技巧条款进模板;本提案是协作契约(角色义务与合并前置),不分发任何代理配置,边界不冲突,落地时在该条备注处不加改动。
