## 摘要

RFC-0021 的审计确认:spec 来源值域「无(自发)」(RFC-0011 落地)使 brief 成为可选前置,README 入门面已在 0021 收口;但 **workflow.md 内部五处流程表述仍把 brief 呈现为无条件必产**——摘要「常规级先写 brief」、流程总览 mermaid 节点、2.2 流程行、3.3 立项交付「brief 已 Accepted」、3.4 DoR 首项「brief 状态 Accepted」,AGENTS 分级速查表与 writing-style 统一用词表「立项」行同(第七处系第三轮审计并入)。规范面自身的不自洽:同一文件 3.2 支持「来源 = 无」,其余章节不认。本提案把七处表述收口为「brief(自发可免)」口径,DoR 与立项交付补自发立项的核对方式。同案并入八项独立小勘误:统一用词表「收口」定义比实际用法偏窄、DoR 测试基线对照项缺续作限定、AGENTS R4 状态枚举跨类型并集且 brief 缺席、PR 模板「spec 已就绪」的「就绪」无定义支撑,以及第三轮审计并入四项——workflow 3.3 固定收尾枚举停在 v2.7.0 前形态、6.2 维护时点「PR 合入时」未跟 RFC-0019「合入前」口径、「常规级以上/及以上」全仓混用、tech-stack 维护规则漏「升级」;第四轮决议并入四项——分级声明协议补「超出小改」限定、squash 分界改挂交付记录(初版「单任务」措辞经维护者澄清不准确,decisions.md 承载面同步)、breaking commit 记法显式化、预设节删除治理定性。本提案**唯一新增规范语义**是 brief 经 Accepted 后正文冻结(2.10),**唯一行为性修正**是 squash 分界(2.18),其余均为既有语义的表述收口,逐项标注。

## 背景与动机

**brief 无条件化(主项,证据)**:

- workflow 摘要:「常规级先写 brief 再写 spec 与 tasks」;
- 流程总览 mermaid:`B -->|常规| D[brief 需求简报]`,无条件节点;
- 2.2 常规流程行:「流程:brief → spec → tasks → 实现 → review」;
- 3.3 立项交付自查:「brief 已 Accepted、spec 已 Active、tasks 就绪……」—— 自发 spec 立项时该项无核对对象;
- 3.4 DoR 首项:「brief 状态 Accepted,spec 状态 Active」—— 同上,且施工会话按「任一不满足 MUST 停下报告」执行时会字面卡死;
- AGENTS 分级速查表常规行:「brief → spec → tasks → 实现」。
- writing-style 第 5 节统一用词表「立项」行:「brief → spec → tasks 的产出过程」—— 防漂移权威表自身也无「自发可免」出口(第三轮审计并入,第七处)。

而 workflow 3.2「谁写」与 spec-template 来源值域均支持「无(自发)」,RFC-0011 更记录「spec 常从 RFC 或讨论直接立项」为维护者多项目常态实践。**根因与 RFC-0021 发现一同构:规范演进只落权威节,周边表述不跟** —— RFC-0011 改了取号与关联机制(3.2 + spec-template),流程章节的 brief 表述未同步。0021 落地后 README 显示「自发可免」,AI 读 workflow 仍撞五处无条件表述,AGENTS 速查与统一用词表再各撞一处,轻则反复询问、重则 DoR 字面卡死。

**四项小勘误(证据)**:

- **G(用词表定义偏窄)**:writing-style 第 5 节统一用词表把「收口」定义为「全部任务完成后的复查与文档回填」,只覆盖收口复查与状态收口两类;实际用法还有 Phase 收口(3.3「每组收口时系统 MUST 可运行」)、工作区收口(git-workflow 第 1 节)、收口即终态(6.3)。用词表自身是防漂移权威,定义与用法不符即权威失准。
- **H(DoR 基线对照缺限定)**:DoR「全量测试已实测跑通并记录 passed 基线;与 tasks 文档记录的数字不一致时以开工实测为准」—— 首次开工时 tasks 无任何数字可比(基线恰是开工实测后才记入首个交付记录),对照条件实际只适用于续作,未写明。
- **I(R4 枚举含混)**:AGENTS R4「不修改状态为 Accepted/Active/Implemented 的 spec/RFC 与 ADR 正文」—— Accepted 是 brief/RFC/ADR 的状态,Active/Implemented 是 spec 的,读者须自行做类型-状态匹配;且 brief 缺席:brief 经 Accepted 进入 spec 后正文可否修改无任何条款。
- **J(「就绪」无支撑)**:PR 模板分级声明「常规(Standard,spec 已就绪)」——「就绪」的定义在 AGENTS R1(= 开工评审通过),PR 模板处无指引,评审时点读者易读成「状态 Active」。

**第三轮审计并入项(L-O 与主项第七处,经维护者决议并入)**:

- **L(3.3 固定收尾枚举旧形态)**:workflow 3.3 末条「更新 `docs/README.md` 注册表」—— v2.7.0 已将 tasks-template TF2 字面改为「spec 状态收口四动作(文件头状态行 / 变更记录迁移行 / 更新日期 / 注册表行同步)」,规范侧枚举未跟(复述面漂移,与 0021 根因同构)。
- **M(6.2 合入时点未跟)**:workflow 6.2 维护时点表「PR 合入时 | 更新『当前状态』……」—— RFC-0019 落地口径为「合入前」(dev-standards DoD 第 10 条与 PR 模板自检均写「合入前」,回填以 PR 尾部 docs commit 随分支合入);6.2 字面读作合并后主分支 commit,是未跟面。
- **N(量词混用)**:「常规级以上」与「常规级及以上」全仓混用(grep 实证:「以上」五处待改 —— AGENTS 第 5 节摘要、PR 模板自检行、README FAQ 两处、workflow 3.8 可调参数表说明列;workflow 3.8 同一行内两种写法并存,版本历史条目不追改);「以上」的含/不含本级歧义违反精确性要求,统一为「及以上」。
- **O(tech-stack 维护规则漏「升级」)**:tech-stack.md 维护规则「新增运行时依赖 MUST 先有 Accepted 的 RFC」—— 权威面 dev-standards 第 7 节为「新增**或升级**运行时依赖属于重大级」;按 tech-stack 字面,升级运行时依赖不触发 RFC。复述面漏抄,纯字面对齐。

**第四轮决议并入项(P-S,经维护者决议并入)**:

- **P(分级声明缺限定)**:workflow 2.5 元规则 2「AI 开工前 MUST 向用户输出……并等待确认」无限定,字面覆盖小改;AGENTS 第 3 节同协议带「超出小改标准的任务」限定,workflow 2.1 小改流程是「直接实现」,README 小改行是「AI 自行判级、直接实现」—— 权威节为最重读法,与三面口径不一致;0021 落地后 README 动作表小改行与此形成新的入门面字面冲突。
- **Q(squash 分界变量错位)**:git-workflow 第 5 节「小改与单任务 PR 用 squash merge」—— 失效不变式在同节第二 bullet 自载(「squash 会使回填失效」,挂在交付记录回填上),分界变量却写任务数;常规级 tasks 恒含 TF1-TF3 固定收尾(≥ 4 任务、逐任务交付记录回填),模板机制下「单任务 PR」实际即小改;被读成「常规级单实现任务 PR」时交付 hash 全部悬空,自毁交付记录与 DoR/独立验收的 hash 实测核对。维护者澄清:该措辞系初版制定、本身不准确(非深思熟虑的设计意图);正确形态由自载不变式决定,分界挂交付记录,decisions.md 第 3 节合并策略行的「多任务/小改」任务数口径同步收口。
- **R(breaking 记法缺位)**:PR 模板变更类型含 `breaking 破坏性变更`,git-workflow 第 2 节 commit 类型表无破坏性记法(`!` 与 `BREAKING CHANGE` footer)指引 —— 文件已声明遵循 Conventional Commits,记法是该标准自带;无字面依据时 AI 对勾选 breaking 的 PR 大概率自造 `breaking:` 无效类型。
- **S(预设节删除治理定性缺位)**:git-workflow 第 6 节与 dev-standards 第 8 节「不采用的(团队/项目)删除本节」—— 按 R8 与 structure 第 3 节字面,删 conventions 正文属重大级,指令读起来却是随手合法动作;两读均荒谬(执行预设开关须先立 RFC),缺「预设开关属项目级配置,不算规范修订」的定性。

## 目标

- workflow 五处 + AGENTS 速查表 + writing-style 统一用词表「立项」行(第七处)收口为「brief(自发可免)」口径;DoR 与立项交付补自发立项核对方式;元规则 3「补 brief / spec」斜杠消歧。
- 十四项勘误与修正落地:初稿四项(用词表「收口」行、DoR 基线限定、R4 重写、PR 模板表述)+ 第三轮四项(3.3 固定收尾枚举、6.2 合入时点、量词统一、tech-stack 补「升级」)+ 第四轮四项(分级声明限定、squash 分界修正、breaking 记法、预设节删除定性)+ 第五轮两项(2.21 三路径加注、2.22 行内代码空格)。
- 新增规范语义仅 2.10(brief 冻结)一处;行为性修正仅 2.18(squash 分界)一处;其余零语义变化,逐项在提案详述标注。

## 非目标

- 不动 README 入门面与 AGENTS 动作映射(RFC-0021 范围,两案无行级冲突;2.14 量词统一触 README FAQ 两行与 AGENTS 第 5 节摘要一行,均非 0021 改写面,无行级冲突)。
- 不改 spec 来源机制本身(RFC-0011 已定;本提案只是流程表述跟上既有语义)。
- 不动 verify-docs(纯表述收口,无呈现面新增,「呈现面 = 核对面」原则不触发)。
- 不改 design / tasks 相关流程(0021 已覆盖其入门面;规范面本次审计未发现新问题)。
- 不重设计合并策略:小改 squash / 带交付记录 PR merge commit 的二分与「已推送不 rebase/amend」配套不变,2.18 只修正分界变量(挂交付记录而非任务数);decisions.md 第 3 节决策本体不动,合并策略行左列随 2.18 同步为交付记录口径(理由列锚本就是交付记录,零改动)。

## 提案详述

### 2.1 workflow.md 摘要(表述收口)

「所有改动先分级 —— 小改直接进入实现;常规级先写 brief 再写 spec 与 tasks;……」改为:

```
所有改动先分级 —— 小改直接进入实现;常规级经 brief(自发可免,spec 来源填「无」)再写 spec 与 tasks;……
```

### 2.2 workflow.md 流程总览 mermaid(表述收口)

`B -->|常规| D[brief 需求简报]` 改为 `B -->|常规| D["brief 需求简报(自发可免)"]`(节点文本含全角括号,加引号防解析歧义)。图后文字摘要随 2.1 同步。

### 2.3 workflow.md 2.2 流程行(表述收口)

「流程:brief → spec → tasks → 实现 → review」改为「流程:brief(自发可免)→ spec → tasks → 实现 → review」。

### 2.4 workflow.md 3.3 立项交付(核对口径)

「立项会话结束前自查 —— brief 已 Accepted、spec 已 Active、tasks 就绪、注册表与 STATUS 已登记、开工提示词已输出」改为:

```
立项会话结束前自查 —— brief 已 Accepted(自发立项时无 brief,注册表「来源」列记「无」)、spec 已 Active、tasks 就绪、注册表与 STATUS 已登记、开工提示词已输出。
```

### 2.5 workflow.md 3.4 DoR 首项(核对口径)

「[ ] brief 状态 Accepted,spec 状态 Active(评审清单已全绿)。」改为:

```
- [ ] brief 状态 Accepted(自发立项时无此核对项,以注册表「来源」列记「无」为凭),spec 状态 Active(评审清单已全绿)。
```

### 2.6 workflow.md 2.5 元规则 3 斜杠消歧(表述收口)

「MUST 停下来补 brief / spec」改为「MUST 停下来补 spec(需求动机复杂、目标非目标未对齐时先补 brief)」—— 累计升级的交付契约在 spec 层(RFC-0013),brief 按需。

### 2.7 AGENTS.md 分级速查表常规行(表述收口)

「brief → spec → tasks → 实现」改为「brief(自发可免)→ spec → tasks → 实现」。

### 2.8 writing-style.md 统一用词表「收口」行(勘误:定义与用法对齐)

| 统一用词 | 含义(改后) | 弃用的近义表述 |
|---|---|---|
| 收口 | 阶段的工作与账面结清到终态、不留中间态:Phase 收口(可运行关口)、收口复查(送审前)、状态收口四动作与回填(合并时)、工作区收口(会话结束) | 收尾、结项 |

### 2.9 workflow.md 3.4 DoR 基线对照项(勘误:补适用条件)

「全量测试已实测跑通并记录 passed 基线;与 tasks 文档记录的数字不一致时以开工实测为准,首个交付记录注明」改为:

```
全量测试已实测跑通并记录 passed 基线(记入首个交付记录);续作时与 tasks 既有交付记录的数字对照,不一致以本次实测为准并在本次交付记录注明。
```

### 2.10 AGENTS.md R4 重写(**本提案唯一新增语义**)

现行「不修改状态为 Accepted/Active/Implemented 的 spec/RFC 与 ADR 正文;需要变更时走修订流程或新提案」改为:

```
- **R4** 不修改已定稿文档的正文:brief 经 Accepted、RFC 经 Accepted、spec 经 Active、ADR 经 Accepted 即冻结;需要变更时走修订流程或新提案(brief 的需求演化由 spec 修订承载,不回改 brief)。
```

新增语义的理由:brief 是提出时点的捕获记录,Accepted 后其内容已转入 spec,演化在 spec 侧进行;回改 brief 会造成「同一需求两个可变版本」。与 RFC-0011/0013 的张力澄清:brief 独立累积发生在 Proposed 期,不受影响;Proposed 期修改自由不变。备选(不冻结 brief,仅按类型重排枚举)未入选:缺席问题依旧,定义真空保留。

### 2.18 squash 分界修正:git-workflow 第 5 节 + decisions.md 第 3 节合并策略行(**行为性条目,评审重点**;并入 Q)

git-workflow 第 5 节,现行:

```
- 小改与单任务 PR 用 **squash merge**:压缩为单个 commit,历史干净。
- 多任务 PR(有交付记录回填)用 **merge commit**:保留每个任务的 commit —— 交付记录回填的 hash 以此为据,squash 会使回填失效。
```

改为:

```
- 无交付记录回填的 PR(小改)用 **squash merge**:压缩为单个 commit,历史干净。
- 有交付记录回填的 PR(常规级及以上,含仅单个实现任务的)用 **merge commit**:保留每个任务的 commit —— 交付记录回填的 hash 以此为据,squash 会使回填失效。
```

「小改与单任务」系初版制定措辞,经维护者澄清本身不准确(非深思熟虑的设计意图):模板机制下常规级 tasks 恒含 TF1-TF3 与逐任务交付记录回填,「单任务 PR」实际即小改(同义反复);而它被读成「常规级单实现任务 PR」时 squash 使交付 hash 全部悬空。正确形态由同节自载的失效不变式决定,不由初版措辞决定。

decisions.md 第 3 节合并策略行左列同步为交付记录口径(消除最后一个任务数口径承载面,与 git-workflow 单一口径):

```
| 带交付记录回填的 PR 用 merge commit,无回填的 PR(小改)用 squash | 交付记录回填的 commit hash 依赖任务粒度,squash 压扁使回填失效;与「已推送不 rebase/amend」配套 |
```

理由列锚本就是交付记录,左列同步后判据与承载面单一;决策本体(二分结构 + 已推送不 rebase 配套)不变。**行为性说明**:行为变化仅出现在按原字面把「常规级单实现任务 PR」归入 squash 的错误路径上(新字面走 merge commit 保 hash);按不变式正确执行的路径行为不变,历史 PR 不追溯。

### 2.19 git-workflow.md 第 2 节补 breaking commit 记法(显式化既有标准自带记法;并入 R)

「格式:`type(scope): subject`。scope 可选,为模块名。」条后追加:

```
- 破坏性变更:type 后加 `!`(如 `feat!:`),并在 body 加 `BREAKING CHANGE: <影响与迁移要点>` —— Conventional Commits 自带记法,与 PR 模板 breaking 变更类型对应。
```

文件已声明「使用 Conventional Commits」,本条零新增义务,只把标准自带记法显式化,堵住自造 `breaking:` 类型的路径。

### 2.20 预设节删除治理定性(消歧括注,两处联动;并入 S)

- git-workflow 第 6 节「采用本节的项目按以下约定,不采用的团队删除本节:」改为「采用本节的项目按以下约定;不采用的团队删除本节(预设开关,删除属项目级配置而非规范修订,恢复从模板仓库取回):」。
- dev-standards 第 8 节「……无持久化 schema 的项目删除本节,并在 tech-stack.md「项目惯用法」中省略对应声明。」句末加「(删除属项目级配置而非规范修订)」。

按字面反推,「删节须先走重大级 RFC」使指令自身荒谬,指令本意只能是配置动作;workflow 第 8 节「可调参数,团队按需只改本节」已确立「项目级裁剪 ≠ 规范修订」精神,括注将其显式化。零语义新增。

### 2.21 decisions.md 第 3 节「UI 设计三路径」第三路径加注(消歧;第五轮自检并入)

设计与开发同会话 → tasks 的 P0(首个 Phase 的实践称呼,Phase 分组条款已承载,无需专门条款;FR 依赖视觉细节时不适用 —— 设计稿定稿仍先于 spec Active,workflow.md 第 3.2 节)
