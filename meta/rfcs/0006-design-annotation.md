## 摘要

design-template.md 是轻量骨架,但存在两处缺口:其一,**标注质量无纪律** —— 「视觉规格」节指导语无精度要求,「组件与交互」表对状态粒度无约束,设计稿作为「FR 依赖视觉细节时」的定稿前置,自身却无「可判定」纪律,验收链在最视觉化的一环失准;其二,**定稿即终点** —— 字段表状态仅 Draft,变更记录注释只覆盖设计迭代,实现阶段的偏离(组件移除、交互变化)无处落档,设计文档随实现漂移。本提案吸收一份外部项目 UI 设计交付规范中的两条机制:**标注纪律**(视觉值落到可判定粒度,「与现有组件一致」必须指到具体 class / token / 章节号)与**实现回标**(实现偏离设计稿时不删原稿、就近加「实现说明」标注、变更记录补行),落 design-template.md 注释指导语并新增「实现回标」节;workflow.md 第 3.4 节偏离两级处理补一句衔接,明确设计稿偏离不适用 spec 修订。回标做两级处理,纯视觉微调记一行即可,匹配模板轻量定位。来源项目特定内容不采纳:页面类型骨架、图标清单规格、设计系统 token 表。

## 背景与动机

**证据一(标注无纪律)**:design-template.md「视觉规格」节指导语仅「可选:颜色、字号、间距等。有设计系统时引用系统 token,不重复定义」—— 无精度、无引用要求;「组件与交互」表(组件 / 作用 / 交互 / 状态)对状态列无粒度约束。对照 workflow.md 第 3.2 节对 spec 验收标准「可判对错」的要求:设计稿定稿是此类 spec 转 Active 的前置,而前置物自身的视觉标注却可以模糊到无法验收 —— 「与现有登录页一致」类表述无据可查。

**证据二(定稿即终点)**:design-template.md 字段表状态仅 Draft;「变更记录」节注释「设计迭代在此记行:日期、改了什么、原因。定稿后由 spec『接口设计』节链接本文件」—— 生命周期止于定稿。对照 spec 侧:已 Implemented 的 spec 被部分修改时有「文件头状态区记一行『部分行为被 SPEC-NNNN 修改』」的注记机制(workflow.md 第 3.2 节);设计稿无对应物 —— 实现砍掉或替换了设计的某组件后,设计文档保持定稿原样,后续引用它的人拿到过期视觉事实。

**证据三(触发源)**:维护者调研一份外部项目的 UI 设计交付规范,其中「标注铁律」(没有标注的设计稿不算交付;「与现有 xx 一致」必须指到 class 名或设计系统章节号;实现偏离必须回标 —— 不删原稿,受影响小节加实现说明引用块并在变更记录补行,设计文档随实现演进、不是一次性交付)两条机制系项目无关的通用实践,提炼为本提案主体;绑定其项目形态的部分(页面类型骨架、图标清单、状态色值总表规格)不采纳。

## 目标

- 视觉标注落到可判定粒度:颜色写 token 或色值、间距写 px、字号写 px + 字重,引用既有样式必须指到具体对象 —— 与 spec FR「可判对错」纪律对齐。
- 设计文档获得实现阶段的演进义务:实质偏离就近回标、变更记录留痕,与 spec 的行为变更注记机制同构。
- 匹配轻量定位:回标两级处理,FR 不受影响的视觉微调不逐节标注。

## 非目标

- 不引入设计系统规范:token 表、组件规范归项目自建活文档,structure.md 第 5.1 节「原型与生产分离」(生产 token 落代码目录)不变。
- 不给 design-template 增加「Implemented」状态机:设计稿的检索入口是来源 spec 链接(RFC-0004 已定),状态机归 spec。
- 存量设计文档不追溯回填,义务对新产出的设计文档生效。

## 提案详述

### 1.1 design-template.md「组件与交互」节指导语增强

现指导语「必填:涉及哪些组件、它们的交互行为。轻量设计可只写交互要点。」替换为:

```markdown
<!-- 必填:涉及哪些组件、它们的交互行为。
交互状态写全:默认 / hover / active(focus) / disabled;有过渡动画的注明时长与缓动。
「与现有组件一致」必须指到具体组件名 / class 名或设计系统文档章节,不允许无据引用。
轻量设计可合并相近状态描述,可交互元素的 hover 与 disabled 不可省略。 -->
```

### 1.2 design-template.md「视觉规格」节指导语增强

现指导语「可选:颜色、字号、间距等。有设计系统时引用系统 token,不重复定义。」替换为:

```markdown
<!-- FR 依赖视觉细节(颜色 / 间距 / 字号)时必填,其余可选。
标注纪律:颜色写 token 或色值,间距写 px,字号写 px + 字重;不写「美观」「协调」类不可判定描述。
引用既有样式 MUST 指到 token 名 / class 名 / 组件名。
确需设计系统之外的新值时标注为新提案,由实现任务落地,不在本文档维护第二份规范(structure.md 第 5.1 节「原型与生产分离」)。 -->
```

### 1.3 design-template.md 新增「实现回标」节(置于「资产清单」与「变更记录」之间)

```markdown
## 实现回标

<!-- 实现与设计稿不一致时,设计文档的更新义务,两级处理:
- 轻微(间距、色值等视觉微调,FR 不受影响):在「变更记录」记一行即可,不逐节标注。
- 实质(组件移除 / 替换、交互行为变化、影响 FR):不删原稿,在受影响小节加「> 实现说明:…」引用块
  (说明已移除 / 已废弃 / 未落地,附替代方案或 SPEC 编号),并在「变更记录」补行。
纯新增内容(实现补齐了设计未覆盖的状态)在「变更记录」记一行即可。
设计文档随实现演进,不是一次性交付。 -->
```

### 1.4 workflow.md 第 3.4 节偏离两级处理句补衔接

现句「偏离两级处理:轻微偏离(实现细节、补测试)记入偏差记录即可;实质偏离(契约、数据结构、边界、范围)MUST 先修订 spec 再继续。」其后追加:

```markdown
实现与设计稿的视觉偏离不适用 spec 修订 —— 按 design-template.md「实现回标」节的两级处理执行;触及 FR 的偏离仍按实质偏离修订 spec。
```

## 备选方案

| 维度 | 方案 A(本提案:模板指导语 + 回标节 + workflow 衔接句) | 方案 B:回标义务全部写入 workflow.md 第 3.4 节 | 方案 C:维持现状(变更记录承担一切) | 方案 D:独立设计状态活文档 |
|---|---|---|---|---|
| 成本 | 模板注释改写 + 新节 + workflow 一句 | workflow +10 行 | 零 | 新文件 + 登记义务 |
| 风险 | 低:条文与既有两级处理同构 | 中:文档结构义务进流程规范,表单模板自带指导语的先例被架空 | 高:偏离不可见 —— 实现者倾向直接改正稿,定稿历史丢失 | 高:第二份要维护的文档,与 decisions.md 不采纳 reviews/ 同理由 |
| 迁移代价 | 零(注释替换) | 零 | 零 | 全部新建 |
| 可逆性 | 高 | 高 | — | 高 |

**方案 B(义务全上收 workflow)**:未入选。workflow.md 是流程规范,设计稿的文档结构义务归模板本身 —— 表单模板自带指导语是既有先例(spec-template 的 ER 与测试计划指导语、design-template 的响应式断点表);放 workflow 还会使该文件继续膨胀(已 296 行)。

**方案 C(维持现状)**:未入选。「不删原稿」的义务不存在时,实现者的自然行为是直接改正文,定稿与实现的偏离过程丢失;标注无纪律使「设计稿定稿是 spec 转 Active 的前置」这道门形同虚设。

**方案 D(独立状态文档)**:未入选。decisions.md 第 4 节不采纳 reviews/ 的理由同样适用:结论应沉淀进既有载体(设计稿的变更记录),独立成档必漂移。

## 影响与风险

- **design-template.md 行数**:约 +10 行(注释为主);新节为指导语注释,实例化时按需保留,不强制空节。
- **存量设计稿**:不追溯回填;已初始化项目升级后对新设计文档生效,与 RFC-0005「无库项目删除本节」的豁免思路一致(存量豁免,增量生效)。
- **两级判据依赖实现者判断「FR 是否受影响」**:与 workflow.md 第 3.4 节偏离两级处理同源,风险一致(拿不准升一级);触及 FR 的偏离被 workflow 衔接句显式拉回 spec 修订通道,不留套利空间。

## 迁移与回滚计划

不适用(非破坏性变更):全部为注释指导语替换、新增注释节与一句衔接;回滚 = revert 对应 commit。
